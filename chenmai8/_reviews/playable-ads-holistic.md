## 二、裁剪建议

先保「1 个模板 × 3 个已打通渠道 × 中英两种文案 × 手机二维码 × 质检报告」。这是未来 7 天的全部范围。

应该砍掉或降到报名之后的：

- director、repair-loop、训练脚本、抠图模型、Qwen-Image。路径 B 在开发指令里已经标成不阻塞主路径，却仍占着里程碑 D4、D5。
- 同时开 merge、pullpin、sort。第二条模板最多留一个，而且排在主路径彩排通过之后。
- 48 包全矩阵、六语言字体子集、图集、ffmpeg 转码、30% 体积指标。这些是 assetkit 的验收线，不是演示线。
- 用上游打包器再做一轮交叉验证。Phase 0 的对照包已经完成它的任务。
- 「规范变化只改配置、打包器不改代码」这个承诺。包形态可以配置驱动；退出接口仍要改 `channels.ts`。不要为了圆这个承诺去把六个渠道都接进桥里。

划对了、应继续守住的红线：

- 不做一句话生成完整游戏，不依赖 GameCoder-27B，不执行训练。
- 不把 Cocos 工程当输入。
- ironSource 不列入渠道。
- 质检失败就没有可交付产物；演示另备一份预构建静态件。
- 试玩包体内零外链、首点前静音、30 秒体验预算。这三条是广告可投放性，不是风格偏好。
- 路径 B 若以后做，界面上必须标 DEMO。

划错了、应该改写的红线：

- 「10 天内 4 模板 × 6 渠道 × 6 语言」写成了必做范围。它把验收标准定在了演示日之后才能稳定的规模上。开发指令 §11 的砍序（先全绿再语言、再界面、再路径 B）是对的，日程却把二维码放在 D7、把 48 包放在 D6，顺序反了。
- 公开仓库禁止出现引擎、字体、素材包的名字，并用改名通过检索。面向海南企业和计算所、上研院评委，正确的红线是：保留许可证声明，不把研究许可的模型权重打进交付物。
- 语言表锁死 en/ja/ko/pt-BR/de/ar，没有中文。系统字体在国产手机上能显示中文，这个改动不依赖字体子集。海南现场的默认语言应是中文，阿拉伯语只作为 RTL 的一个证明，不作为第二优先级。
- 微信试玩不进这 10 天的代码，这个判断对。对外叙事里把它说成「同一套规则库的下一条渠道」，而不是「我们不做国内渠道」。

## 三、模块切分质量

十二个模块对一条流水线来说太多。边界清晰、值得留下的是五个：规格（M1）、运行时桥（M2）、模板插件（M3）、打包器（M4）、质检器（M8）。渠道规则是数据文件，不是一个需要排期的模块。

建议合并：

- M6、M7、M11 合成一个「模型适配器」。现在三个模块、零个生产调用方。`llmgw` 保持一个库文件即可。
- M9 和 M10 合成一个编排器：命令行是主体，网页只是上传和二维码。先有命令，再包一层页面。
- M5 先做成构建时的一个函数（读入一张用户 PNG，写进包体）。等第二条流水线真的调用它，再独立成素材管线。

建议拆开的只有一处：可解性算法不该住在 M1 里。match3 的「有没有一步可走」用的是校验器自己的 LCG；模板里的补位随机流是另一个盐值 `0x51ed270b`。两套规则已经分叉。每个模板应导出自己的 `check(spec)`，校验器只负责结构和调用。否则每加一个玩法都要改所谓已冻结的核心，Python 与 JavaScript 还要各改一次。

会在加渠道、改版时疼的契约：

- 模板名和渠道名是封闭枚举，`additionalProperties: false`。加微信、巨量或第五个玩法就是一次 schema 破坏。
- 文案被固定成五个键：`cta`、`tutorial`、`win`、`lose`、`score`。结束页要加副标题、年龄分级、商店徽标时没处放。`variants`、`difficulty`、`ctaStyle` 已在 schema 里，没有任何构建步骤读取。
- 开发指令要求 CHK06 断言「退出调用的参数等于 landingUrl」。Meta 的 `onComplete()`、Google 的 `ExitApi.exit()`、TikTok 的 `openAppStore()` 都不接收 URL。这条验收标准按字面实现就会永远失败。
- 规则 JSON 里的 `call` 是给人读的字符串，不是可执行适配器。新渠道至少要改两处：`channel-rules.json` 和 `channels.ts`。「只改配置」在退出路由上不成立。
- 素材路径是必填字符串，但缺失文件不报错，构建直接忽略。评委按 schema 准备素材，会得到一张与素材无关的程序化画面。
- 质检钩子 `hint()` 的 `type` 只有交换和点击。拧螺丝、拔针没有手势词汇表。第二个模板会各自发明一套。
- `durationBudgetSec.max ≤ 30` 只在校验器里检查。质检用的是 45 秒自动试玩预算，模板也不按 30 秒收束。
- 产物形态有两套。模板 `build.mjs` 直接吐出单文件 HTML；打包器要的是带 `index.html`、css、js、png 的目录，然后再内联一次。两条路径都会「打包」，没有一份文档说明谁是唯一的内联者。
- 命令名已经漂了：规格写 `pfcore make`，实现是未完成的 `run`。

## 五、商业与路演视角

技术评委最容易质疑的三点：

**第一，开源叙事和仓库事实相反。** README 的定位是开源、可私有化。三消 README 写明：引擎打成单文件后去掉许可证注释，再做全局改名，直到大小写不敏感检索零命中；来源只记在不入库的 `_vendor/NOTES.md`。计算所或上研院的评委会打开那个约 1.2 MB 的 `engine.js`。MIT 类许可证要求保留版权与许可声明。改名躲过检索，会被理解成隐瞒来源，而不是工程洁癖。同时根 README 用现在时列出合成、拔针、拧螺丝、六渠道、截图生成和 Cocos 接入。这些在仓库里是空壳或明确出范围。评委对照仓库读 README 时，信任会先于技术问题崩掉。

**第二，「全渠道质检通过」没有工程事实。** 能玩的那份 HTML 只在 preview 渠道上跑过，而且 10 项里有 3 项跳过。打出来的渠道包是 2 KB 的占位工程，里面没有游戏。质检器拒绝 zip。退出接口没有断言。规则库缺一半渠道。官方预览工具还没跑。自动试玩依赖模板自己提供的 `hint()`：这可以作为回归测试向评委解释，但不能说成「广告平台已经认可」。

**第三，商业数字和 AI 贡献都还没有测量。** 「7 天 / 500 美元变成几分钟」需要一次墙钟计时：从改完 spec 到二维码可扫。这个计时不存在，因为中间的命令不存在。已有的 26.6 秒是游戏被自动玩完的时间，不是生产线的时间。AI 部分是一个没有调用方的 HTTP 客户端。若路演主标题是「AI 生成试玩广告」，现场会被问倒。站得住的标题是：规格驱动的试玩广告工厂，质检是裁判，模型接口可替换，今天演示的是确定性主路径。

可以直接写进 PPT 的工程事实（每条都带限定语）：

- 一份 schema v1 的 JSON 能描述玩法、文案、渠道和质检预算；6 个坏样本会被拒，错误信息带字段路径。双校验（JSON Schema 与 Python 模型）已接在 `pfcore validate` 上。
- 三消预览包在一次留档运行中：1.24 MB，低于 Meta 内部 3 MB 线和各渠道 5 MB 线；本地加载 572 ms；首交互前静音；横竖屏都有画面；22 次真实指针手势后 26.6 秒胜利并出现结束页；除本地页面外零请求。限定语：preview 渠道、程序化贴图、系统字体、三项检查未实现。
- 渠道包形态有实测依据：AppLovin 与 Meta 是单 HTML；Mintegral 是 zip，内含 `build.js` 与 `Template.html`。限定语：此形态来自 Phase 0 对照工程和规则库注释；自研打包器已能按这个结构出包，但出的还是占位工程，不是三消本体。
- 运行时桥用测试覆盖六个渠道的退出路由和静音策略，零运行时第三方依赖。限定语：这是单元测试里的桩，不是广告平台回执。
- LLM 网关由环境变量决定地址和模型名，离线 mock 覆盖了对话、JSON、图片、超时和降级。限定语：没有业务调用方，不构成「AI 产出了广告」。
