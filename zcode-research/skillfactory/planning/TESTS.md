## 0. 目的、总原则与 PLAN 映射

### 0.1 目的

给 PLAN v1.1 的 14 个工作流（阶段与编号已按 v1.1 重排）配一套**可执行、可判定、有取舍留痕**的测试体系，验证五件人类意图（v1.1 口径）：
a) 任务类型 + bench + 资产交付质量；b) 内部交付：资产使用内部指南可照做、模拟真实任务包与任意输入验收尺可用；c) skill/MCP 符合国际通行标准；d) 普通模型（GLM-5.3-Flash、Step-3.7-Flash、MiniMax-M3.1-Flash、MiniMax-M3）真实任务增益真实可复现；e) 防过拟合——防**我们自己迭代过拟合 dev 题**（bench 内部 holdout 纪律保留；班级向反作弊随课堂出范围，owner 自理区）。

### 0.2 资产内测面的第一句话（全文档最重要的事实）

> **资产内测面当前缺的不是测试，是被测对象。** PLAN v1.1 §6.3 的「任意输入验收尺」（对未见输入的产物判 绿/红/无法判定）在四个首发相关 runner 中均不存在（证据：`dist/meeting-minutes-skill/eval/runner.py:239,173-176,210-231`、`dist/office-templates-skill/eval/runner.py:58,408`、`v5/assets/speaker-mapping/eval/runner.py:65+` 四张全文常量表、`v5/assets/hotwords/eval/runner.py:356` 54 文件逐字节对参照；轨迹8 实跑 C1–C3/C6）。验收尺是 WS7 的**前置交付物**，AR 组测试测的就是它（轨迹8 结论 1/2，置信度高）。照既有 runner 的字面写「跑 hotwords runner 得 4/4」这类测试是必然通过但毫无意义的——它测的是 oracle 复现，不是任意输入验收（轨迹8 撰写建议 9；v1 §6.8 两句验收口径的修正见附录 7.3-7）。

### 0.3 总原则（七条，全部测试组共用）

1. **可见/holdout 分界——凡随机化的藏，凡判据的亮**（轨迹7 RC-7，与轨迹8 链 G、轨迹9 链 G 三方独立收敛）：
   - 藏：题面实例、nonce 值、暗桩内容、裁判身份与复评时点、抽审抽样时点、holdout 缺陷注入样本（验收尺注入样本见 HO-18）；
   - 亮：阈值、rubric、门禁语言、复合线三条件、难度带定义——**判据公开是公平的前提，藏判据只会催生猜谜式开发**（EVAL-SPEC E-1 披露哲学同构）。
   - 两个辅助判据：**真值锚在不可篡改历史（git blob/冻结登记）的测试可完全公开**（轨迹9 链 G）；**「调过就会变好但变得不真实」的输入进 holdout**（轨迹8 链 G）。三把尺子同一指向，逐组标注见各章。
   - **显式警告**（轨迹8 撰写建议 7）：「验收尺相关测试均 holdout」是一句会真实阻塞 WS2/WS7 的误判——**验收尺本身必须开发者可见（它是尺子），验收尺的缺陷注入样本必须 holdout（它是答案）**。两者不得合并表述。
2. **fail-closed 一票制**：外部校验器不可用、数据缺值、装置不完整时，门必须红，不得静默通过（v5 红路纪律；轨迹6 链 C「工具没装被当验证通过」、轨迹10 RC-10-4「S4 缺值 fail-closed」）。
3. **变形测试优先于样例断言**：delta/winRate/reverseTasks 类统计必须用标签互换等变形不变量测（轨迹9 链 E：仓库实测过一次 `(better==='a')!==swap` 符号反转 bug，污染三份文件的 majority/winRate/reverseTasks/accepted 而**均值与 delta 毫发无损**——「均分对不对」抓不到它）。
4. **缺陷标本库三层用法**：真实事故（T1 墙钟戳/T2 `--out` 回显/T3 路径形态/T4 参照侧损坏）沉淀为标本，用于**重放**（历史判定不得翻转）、**盲桩**（混入暗桩测抽审流程）、**口径对齐**（归因三分类与标本库定义对表）——纯单元测试拦不住口径类事故（轨迹7 RC-1）。
5. **负控（negative controls）**：MVP/装置验收 = **负控全红 + 正常臂不误报**，不是「跑通了」。恒返回绿的 harness 与正确的 harness 在跑通型判据下不可区分（轨迹9 链 F 之 E7）。
6. **红路先跑；人工门只签事实；不信任自报**（三条仓内先例直接抄）：验收顺序红路→绿路→三齐→彩排→人工（TASK.md:46）；人工门证据只有 `{签署人, 日期, 被签对象 sha256}`、无 `passed` 字段（publish-approval-REQUEST.md:3）；每条门行必须自带 `{command, exit_code, ts, evidence_sha256}` 五字段，缺任一由 runner 判红（TASK.md:70）。
7. **注入实验只在 scratch 副本**：一切生成/注入实验的第一动作 = 记录 oracle 树哈希，结束再验一次；退出码无管道捕获；落盘一律 Python `open(..., encoding="utf-8", newline="\n")`（轨迹7 §1.3 末「主动未执行」示范 + 轨迹9 弯路 3/4 + 轨迹10 弯路 4；PLAN R-7）。

### 2.0 威胁模型与可见性总规则（先写威胁模型再写测试）

**物理形态的实测结论**（轨迹10 RC-1，A 级三步闭环）：本机 dev agent 与 harness 同为 Administrator 且持 SeBackupPrivilege——`robocopy /B` 可直接拷出 deny 目录内容（实测）。**DACL 不是保密边界**。holdout 纪律的正确表述=**构造不可达（不在任何 dev 工作树/cwd/搜索根）+ nonce 过期（一次性，泄漏快照下轮即失效）+ 扫描可检测（转录/产物/资产树三处）**；权限位降级为「绊线」（越界发生时立刻炸出证据）。

### 4.2 角色与独立性（规格首条纪律）

> **验收测试的作者 ≠ 资产的作者 ≠ 裁判的作者。** 整套 holdout 体系的有效性最终取决于没有一个人同时握有出题、调参、判分、验收四把钥匙（TASK.md:69-74 角色禁止列的测试侧延伸；轨迹10 撰写建议 12，置信度高）。

- **开发 agent**：写资产、跑日常红绿；不得改门与阈值（TASK.md:76）、不得见 holdout/暗桩/注入样本。
- **主 agent**：组织跑批（意图 5）、收口验收、里程碑汇总、交付打包（WS14）。
- **bench 侧角色**（与资产作者不同人/不同会话）：holdout 生成、暗桩投放、缺陷注入样本构造、抽审执行。
- **owner**：保留决断（第 5 章 11 项）、K-5 亲签（若决定发布）、交付签收、「进入真实人类使用」决策（O-12 已裁定，决策权留 owner）。
- **人类讲师（owner 侧）**：内部指南与模拟任务包的最终使用者；课堂侧彩排（L1/L3）owner 自理，不在本体系测试角色内。

### 4.3 红路纪律与留档格式

- 红路先跑，任一红即中止；门禁语言沿用 v5：绿路（exit 0）/红路（exit 1）/用法（exit 2）/fail-closed；红路永远不许修成 exit 0，红路验证纳入每批评测（TASK.md:24）。
- 门行五字段：`{id, kind: deterministic|holdout|human|unjudgeable, command, expected, evidence:{exit_code, ts, sha256}}`；缺字段判红（MT-5）。
- 留档形态对齐 v5 eval-round：逐门 stdout/stderr + results.tsv + keyfiles.sha256 + 三段诊断（先归因再聚合）；REGISTRY 式台账只追加不改行（R2 更正先例）。
- 负控输出（`nc-` 前缀）禁入 REGISTRY 与 baseline/<family>/。

### 4.4 落盘纪律（Windows 事故族，全部有前科）

Python `open(..., encoding="utf-8", newline="\n")` 一律显式；不用 shell 重定向（NUL 事故+非纯 JSON 前科）；退出码无管道捕获（Git Bash 管道尾 `$?` 是 tail 的退出码）；命令输出解码显式（本机中文 Windows cp936）；注入实验前先记 oracle 树哈希（scratch 纪律）；Mimosa hook 对 run 输出目录放行在 WS1 开工前确认（R-6，有误伤只读前科）。
