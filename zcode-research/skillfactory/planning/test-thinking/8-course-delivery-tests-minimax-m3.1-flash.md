## 2. 关键推理链

### 2.1 推理链 A：「机器判绿」今天判不了学员的素材——这是本镜头的第一性障碍

**命题**：PLAN §6.1:375 的新判据是「学员用自己的素材做出一件自己的事，且被机器判绿」。要让这句话成为可执行测试，前提是存在一把能对**任意学员素材**判绿的尺子。我去查这把尺子。

**证据链**（全部本次会话实读/实跑）：

1. `dist/meeting-minutes-skill/eval/runner.py:239` —— `cases = [item["case"] for item in golden.get("eval_inputs", [])]`。**用例清单写死在 golden.json 的 4 个 case（case1–case4）**，不可传参、不可扩展。学员自己的第 5 份转写稿，runner 根本不会看。
2. 同文件 `:173-176` —— 溯源检查 `ref_root = os.path.dirname(os.path.abspath(ref_dir))`、`transcript_path = os.path.join(ref_root, "inputs", case + ".txt")`。**溯源基准是「参照目录的兄弟目录 inputs/」，不是学员的输入文件**。我的 C3 实验把 reference 指向另一个包，溯源检查立刻报 `无法定位转写稿`。
3. 同文件 `:210-231` —— `entry_counts_within_tolerance_of_reference` 比的是**参照产物的 summary.json 条数**。学员素材没有参照产物。C3 实验里它报 `参照产物不可用: 缺 summary.json`。
4. `dist/office-templates-skill/eval/runner.py:58` —— `EXPECTED_UNITS = ["%s/%s" % (t, c) for t in TEMPLATES for c in CASES]`，TEMPLATES×CASES 写死 4×2=8 个单元；`:408` `missing = [u for u in EXPECTED_UNITS if u not in tested_units]`。**学员只交一份周报 → `units_found` 直接 FAIL**。
5. `v5/assets/speaker-mapping/eval/runner.py:65,168,181,188` —— `EXPECTED_TXT` / `EXPECTED_WARNINGS` / `EXPECTED_UNUSED` / `EXPECTED_DISCOVER` 四张**全文常量表**写在 runner 源码里，绑定 normal/partial/empty × m_full/m_partial/m_empty 九宫格。学员的会议稿不在表里。
6. `v5/assets/hotwords/eval/runner.py:356` —— `def check_consistency(cand_out, ref_out)`，54 文件**逐字节**比参照，一致率必须 100%。

**结论（高置信）**：**四个首发相关 runner，没有一个能对「学员自带素材」判绿。**它们全部是「对固定 oracle 的确定性门」，不是「对任意输入的业务判据门」。PLAN §6.1 的转向在判据层面是正确的（业务判据 ≠ 逐字节一致），但**判据的机器实现还不存在**。

**这意味着什么（对本镜头的测试设计的直接后果）**：

- 「机器判绿」这件事本身必须被**测试**，而且是最先被测的那一条。它不是 WS5 之后自然会出现的东西，它是一个**待建的测试装置**（我称之为「课堂尺」），WS5 的验收门必须包含「课堂尺存在且对学员素材判绿」这一条，而不只是 PLAN WS5:461 写的「L0 三条退出码 + L1 零讲稿可执行」。
- 更精确地说，PLAN §6.8:437 写「验收 = runner 4/4 + 自己的 funasr 导出文件」「验收单用 meeting-minutes eval 5 项翻译白话」——**这两句在今天都是不成立的**：hotwords runner 4/4 的第 4 项是 54 文件逐字节对 oracle（我的证据 6），learner 的 funasr 导出文件根本不在那 54 个文件里；meeting-minutes eval 5 项里的第 4、5 项依赖参照物（我的证据 2、3）。**PLAN 在此处把「已有资产门的通过」误当成了「学员素材的验收尺」，这是一个必须被测试面显式点名的缺口。**

**被否决的分支**：
- **分支 A1：把课堂尺做成「oracle 自适应」**——即学员交什么，runner 就把什么当参照。**否决**：这等于取消判据（任何产物都能给自己当 oracle，必然全绿）。而且违反「runner 零改动铁律」（PLAN §3.3:181）。真正要改的是**新增一把课��尺**，不是改旧 runner。
- **分支 A2：课堂验收只做人工签字不做机器判绿**。**否决**：这直接违反 PLAN §6.1 的判据本身（"被机器判绿"是判据的组成部分，不是修饰词），也违反 owner 意图「课堂高度确定性」（TASK.md:4）。
- **分支 A3：课堂尺 = 把 L2 bench 的题换皮**。**部分否决**：L2 题（`v2/evalbench-v02/meeting-minutes/tasks.json` 的 t1–t8）有完整 rubric 但没有课堂尺形态（无逐字溯源检查、无三态退出码约定、无学员素材入口）。且 §2.3 后面会讲，模拟任务集与 L2 题集**必须解耦**。

### 2.2 推理链 B：课堂尺应该长什么样——从「对 oracle 的 5 项」反推「对学员素材的业务判据」

**命题**：既然不能复用旧 runner，那课堂尺的检查项应该是什么？

**方法**：把 mm runner 的 5 项按「是否依赖参照物」拆开，看哪几项的判据其实是**内容无关的**（只看产物自身结构 + 只看学员自己的输入）。

| mm 5 项 | 依赖什么 | 对学员素材是否可用 |
|---|---|---|
| 1 `docx_opens_with_three_sections` | 只看 docx 自身三节标题（runner.py:126-133） | **可用**（内容无关） |
| 2 `todo_is_table_with_owner_deadline_columns` | 只看 docx 表头含负责人/期限（:150-157） | **可用**（内容无关） |
| 3 `summary_counts_match_docx` | summary.json vs docx 实际条数（:160-190）——**自洽性**，不碰参照 | **可用**（自洽判据，最有价值的一条） |
| 4 `no_fabricated_entries` | 需要「学员自己的转写稿」当溯源基准（:173-199） | **可用，但溯源基准必须换成学员输入**（不是参照目录兄弟） |
| 5 `entry_counts_within_tolerance_of_reference` | 参照产物 summary（:210-231） | **不可用**（学员没有参照）——**必须替换** |

**这是本次会话最有操作价值的一张表**（证据全部来自 runner.py 行号，见 §3）。

**由此得到课堂尺的设计原则**（三条）：

1. **溯源基准 = 学员自己的输入文件**。检查 4 的机制完全可复用（每条目在输入稿里逐字找出处 + 时间/说话人核对），只需把 `transcript_path` 的解析根从「参照目录兄弟」改成「本次任务的 inputs 目录」。这是**判据的正确迁移**，不是判据的放松——它反而**更严**：学员不能编造，但也不能靠「和范例一样」过关。
2. **第 5 项必须换掉，不能保留也不能删**。删掉它 = 少一道门（学员只要结构对就能过，条数全错也判绿）。保留它 = 逻辑不通（学员没有 oracle）。**替换物是什么，是本镜头最需要人决断的技术问题之一**（见 §5 未决问题 1）。我倾向的方向是「**自洽 + 上界**」：summary 四键与 docx 一致（已有第 3 项）+ 待办表每行的负责人/期限非空或明写「待定」（SKILL.md:87 红线「不确定如实填待定」）。但这是 [假设]，需要首期班实测校准。
3. **红路必须保留且必须能造**。mm runner 的红路设计（`check_case` 在 doc 缺失时把 5 项全判 fail，runner.py:104-121）是可复用的。但课堂尺的红路不能用「不存在的目录」这种假红路——**课堂尺的红路必须是「学员交了一份看起来对、实际有编造/漏条的产物」**，这才是学员会真实踩的坑。PLAN §6.3:395 说「红路必须保留」是继承自 hooks.md:48 的仪式，但**仪式和判据是两件事**：仪式是讲师演示，判据是 G0-2 的 exit 1。课堂尺也要有自己的 exit 1。

**另一个跨资产通用观察（同样来自实跑）**：C6 实验显示 `deploy-pack` 的 `validate.py --pack oracle/out/pack-subset --services todo` 能对**与 oracle 不同的内容**判出结构化的结论——`compose_safe_load` PASS（识别出服务=['asr','todo']）、`env_consistent` PASS（8 引用/8 定义双向一致）、`services_exact` FAIL（多=['asr']）。**这说明 deploy-pack 的 C1/C3 是真正内容无关的结构判据，C2 是可参数化的**。它比 mm 更接近「课堂尺」的形态。反过来说，**deploy-pack 是三个 v5 资产里最适合当第一把课堂尺的**（C1–C6 六项里五项内容无关），而 PLAN §6.8:434 把样例课 B（hotwords）排在第一位——**hotwords 的 4/4 里第 4 项是 54 文件逐字节对 oracle（我的证据 6），是三课里最难做课堂尺的**。这个排序与「第一把尺子该做在哪个资产上」是冲突的，需要点出来（§5 未决问题 3）。

### 2.3 推理链 C：四层彩排的「通过判据怎么机器化」——逐层拆，分清「能机判」与「只能半机判」

PLAN §6.3:388-395 的四层表给了每层的「唯一能抓到的失败模式」。这一层我要做的是：**把每层的通过判据拆成「可机判部分」与「只能留痕部分」**。

#### L0 资产机检（产线 agent）
- PLAN 判据：G0-1 绿门 / G0-2 红路 exit 1 / 打包 conformance，三条退出码符合预期。
- **可完全机判，且今天就有**。这是四层里唯一「零新增装置」的一层。
- 但**测试面要加一条 PLAN 没写的**：L0 判的是「资产没坏」，**不判「资产能被学员用」**。证据：record.md:28 的第 3 课交付物是 `out/oracle_student/out/`——**把 oracle 复制一份再跑**，runbook 层全绿。这正是 PLAN §6.1 要废掉的「复现 oracle」判据。**L0 若不加约束，会系统性地把「复现 oracle」训练成课堂的默认动作**（轨迹4 R6「教学惯性防线」的仓内实证）。所以 L0 的测试要有一条**边界断言**：L0 的执行上下文必须与学员上下文物理隔离，且 L0 的产物路径不得出现在任何学员交付物章节里（这条可以机判：扫 walkthrough/handbook 的学员章节，出现 `oracle_student` / `student_run1` 复现路径即红）。

#### L1 备份讲师零讲稿
- PLAN 判据：不看讲稿能带完 + 记录每步耗时。
- **「能带完」不可机判，「带完的过程中踩了哪几个坑」半机判**。我想到的机制：讲师兜底/翻手册/问 owner's 次数，本身就是可数的**事件**，只要强制它**留痕**就可机判计数。PLAN §6.3:393 对 L3 写了「讲师兜底次数 ≤3」，但**对 L1 没写任何可数判据**——这是一个缺口（§5 未决问题 2）。
- 「每步耗时」可机判（讲师带计时器跑一遍，产出 step_timing 表），但**它只能是数据不是门**——耗时超预算不等于不可复制。
- **L1 的真正可机判面是手册本身**：手册里引用的每个文件路径 / 行号 / 命令参数**必须真实存在且参数名正确**。这是 PLAN §5.3:326「过程轨 · 引引面（手册引用的行号/路径必须真实存在→拦 D5）」的课程版。D5 的实证在 record.md:44（REGISTRY 行号误指 dist 包行）。**手册引用完整性检查是一条零人工、可重复、可进 CI 的测试**，而它恰好能拦 PLAN §6.3:395 自己点名的 handbook 乱码缺陷——**不对，乱码拦不住，路径检查只能拦「引用了不存在的东西」，拦不住「这句话本身是乱的」**。这是一个重要的区分（见下）。
- **关于 handbook 乱码的实测（我的 C7）**：8 行全部含可读语义但语句破碎。逐行看：
  - `:44` 「2. 输出红路不是 ❌ 1 而是 ❌ 0：停课修评测器（不过你答应过复盘）；」——「（不过你答应过复盘）」是**语义倒错的插入语**，与前半句矛盾。
  - `:46` 「4. 不要绕路**：**手工拍 ∙ oracle 并不等于走通了；随机 walkthrough 则不算交付。」——**残留的 Markdown 加粗标记 `**` 没有闭合**，且「随机 walkthrough」疑为「按 walkthrough」。
  - `:54` 「**症状**：5.2 步**不评估绿路**评**绿路**走**绿路**绿路**，绿路exit 0；」——「5.2 步」编号错（5.2 是下一节），且「不评估绿路/评/走」四段破碎。
  - `:56` 「**原因**：能是 接受了 一个变动了 runner 的同学（赔罪钱包）改过 oracle 期望。」——「能是 接受了」「赔罪钱包」是随机插入的乱码串，**这段是学员遇到红路 exit 0 时唯一能读到的原因说明**。
  - `:74` 「**原因**：`oracle/out/` 被人清了，者仓库克隆不完整。」——「被人清了，者」断裂。
  - `:88` 「…都能由本手册 + walkthrough.md 完成。**不在场任何任何需要「手工跑某个含密钥的命令」「手动联系某某」的步骤**。」——「不在场任何任何」重复词损坏。
- **这些缺陷的性质决定了它们能被什么测试拦住**：
  - 「**未闭合的 Markdown 标记**」（`:46`）→ **可机判**：跑一个 Markdown 结构 linter（标记配对检查）。这是一条零人工的测试，且它拦的是一整类（夜间自动生成 + 无人工通读 →PLAN.md 的轨迹4 R7）。
  - 「**随机乱码串**」（`:56` 赔罪钱包、`:54` 碎片）→ **可机判但需要判据**：词典/语言模型异常检测，或更笨但更可靠的办法——**要求手册的每个「原因：」段落必须能被一名零上下文 agent 复述成一句因果句**。这其实就是 L2。
  - 「**语义倒错**」（`:44` 红路不是 1 而是 0 —— 这条本身在 walkthrough.md:44,49 里是对的，但 handbook 复述成了「不是 ❌ 1 而是 ❌ 0」）→ **只能靠 L1/L3 真人彩排拦**。这是轨迹4 结论 8 的核心，PLAN §6.3:395 也复述了它（「正是 L2 拦不住、只有 L1/L3 真人彩排能拦的系统性缺陷」）——**PLAN 在这一点上是对的，我的实测支持它**。
- **所以 L1 的测试设计结论**：L1 分两半——**手册静态层**（可机判：Markdown 结构、引用完整性、命令参数与 `--help` 一致、命令可执行性）交给机器，**手册语义层**（可机判的极限是「零上下文 agent 能否照手册跑完」，这其实是 L2）交给 L2，**只有「零讲稿真讲」这一件事不可替代地需要人**。PLAN §6.3:391 说 L1 唯一能抓的是「手册不可照读」——我的拆解是：「不可照读」= 静态层坏了（机判）+ 语义层坏了（L2 代理）+ 读起来别扭（L1 真人，兜底计数）。

#### L2 零上下文 agent
- PLAN 判据：逐步 PASS + 交付物 + 缺陷清单。沿用 K-3（record.md）。
- **可机判，且今天就有**：逐步 PASS/FAIL、退出码、产物存在性。record.md 的格式（每步 PASS + 交付物路径 + 缺陷表）本身就是机器可解析的。
- **但 L2 今天测的是错的东西**。证据：record.md 的「学员」是「zcode 主会话以零上下文姿态执行」（:3），环境是开发机（:4），交付物是 `student_run1` / `student_pack1` / `oracle_student`（:17,:24,:31）——**全是 oracle 复现物**。所以 L2 现在通过，证明的是「零上下文 agent 能复现 oracle」，不是「零上下文 agent 能用资产做出自己的事」。
- **PLAN §6.3:392 写「L2 沿用现有 K-3」是一个未消化的继承**。L2 必须**换交付物定义**（学员素材 + 课堂尺），否则它测的是旧判据。**测试面的断言**：L2 的 record 必须包含「学员素材来源」字段（自采/合成/adversarial/自带，四选一，见 §2.4），且当来源为「自带」时，交付物不得是任何 oracle 复现物。**这条可以机判**：比对交付物 sha256 与 oracle 树 sha256，命中即红（复用 PLAN §3.3:179 的 oracle 哈希门机制）。

#### L3 真人非技术
- PLAN 判据：通过率 + **讲师兜底次数 ≤3** + 卡点清单；且「判失败的是手册不是学员」（:395）。
- **这是四层里最难机判的一层，而且 PLAN 对它的可数性要求是含糊的**。核心问题（§5 未决问题 2）：**「兜底」怎么计数？**
  - 我能想到的三个候选口径，各有致命缺陷：
    - (i) 讲师**替学员操作键盘/鼠标**的次数 → 可数，但漏掉「口头指挥」这种最常见的兜底。
    - (ii) 学员**提问**的次数 → 可数，但把「学员主动追问业务」也算成兜底（那是产品的正常用法，不是缺陷）。
    - (iii) 讲师**不得不放弃原步骤、改用备用路径**的次数 → 最接近「手册不可照读」的真实含义，但判定主观。
  - **我的建议是把这三者分别记、分别报、不合并成一个数**。理由：合并成一个「兜底次数」数字，会让讲师在课堂上**倾向于少记**（记多了自己挂），这是典型的「指标被优化者操纵」。分开记反而让操纵无收益——因为三个数一起看的时候，「操作次数低但提问次数高」是一个可解释的模式，不是一个可藏的数。**这条是本镜头我最想标高置信度的一条设计主张**（依据是 §1.3 C7 实证的 handbook 缺陷性质：学员卡住时手册给不出可用答案 → 讲师必然口头兜底 → 口头兜底不计数 = 缺陷被隐藏）。
  - **「判失败的是手册不是学员」怎么变成测试**：它不是一个测试，是一条**归因纪律**，但它可以被测试——**归因五分类（PLAN §6.9:443：环境/理解/输入脏/资产缺陷/验收口径）的分类器必须能复现人的归因，且分类错误的代价不对称**：把「资产缺陷」误分类为「学员理解」会让缺陷永远进不了 backlog（PLAN §6.9:443 明写「只有『资产缺陷』进 backlog」）。**测试面应该有一条：五分类的混淆矩阵必须留档，且「资产缺陷→非资产缺陷」的漏检率要被单独统计**（因为这个方向的漏检是致命的，反方向的误报只是浪费工时）。
- **L3 的一致性问题（PLAN 没说）**：L3 是真人彩排，**真人之间差异极大**。「兜底 ≤3」在 5 人小班（O-15 建议默认值）和 20 人大班之间不是同一个门。PLAN §6.7:415 说「零配额消耗 → 可开大班」，但**兜底次数随班型上升**（巡场密度下降）。**测试面应该断言：兜底门必须按班型分别校准，且第一期（O-15 的 5 人）的数字不能直接用于第二期**。这与 PLAN §3.7 S2 阈值的「[假设] 待首两轮校准」是同一种纪律，PLAN 在 bench 侧写了，在课程侧没写。

### 2.4 推理链 D：模拟真实任务集的「真实性」怎么测——与 L2 题集解耦 + 防背题

PLAN §6.4:399-405 定义了 4 类 × 5 条 = 20 条。我关心的是**「真实性」这个属性怎么被测试**，以及它与 L2 题集的关系。

#### 先核实素材是否真的存在（PLAN §6.4:400-402 的可行性）
- 类 2「用 gotchas 表做退化注入」——**素材在仓内**：`dist/meeting-minutes-skill/SKILL.md:34-47` 的 11 关键词优先级表 + 「已知可接受的『错』」两条 + `:80-86` 的 gotchas 五条。我在本次会话实读了 SKILL.md:25-95 全文，**这些表确实存在且确实是「可机械转成退化用例」的形态**（关键词是闭集、优先级是全序、已列的错是可枚举的）。**这条 PLAN 主张成立**（置信度高）。
- 类 3「现有 4 个 red fixtures 正式命名为 adversarial」——**素材在仓内**：我 `ls` 到 `v5/assets/deploy-pack/oracle/fixtures/` 下确有 `red-bad-yaml / red-env-drift / red-hardcoded-secret / red-missing-service` 四个 + `services-{canonical,invalid,subset}.txt` 三个。**存在性成立**（置信度高）。
- 类 1「真实素材自采」——**素材不在仓内，需要新采**，且受 O-9 合规边界约束（PLAN §8:503：书面同意+脱敏、只进 dev/train、同意载体=报名单勾选条款）。**我 grep 过 `报名单|同意书|脱敏`，仓内零命中课程侧同意载体**（`plan/GOVERNANCE.md:85` 有 consent ledger 设计但那是 skilldock 治理包，不是课堂）。**所以 O-9 的「同意载体」在仓内是零实现**。
- 类 4「学员现场自带」——**一次性，不进 bench**（PLAN §6.4:403）。这条设计我认同且它有一个测试含义：**它必须进课堂验收单**（PLAN 明写），而验收单模板不存在（我的 C8）。

#### 「真实性」不能直接测——能测的是「退化覆盖率」与「合成痕迹残留」
「真实」是一个关于**来源**的属性，机器判不了。但有两件可测的：

**(1) 退化覆盖率**：gotchas 表里的每一条，模拟任务集里**是否至少有一条对应的任务**。这是可机判的**双向覆盖检查**（表 → 题集，且题集 → 表反向也要查，防止注水的假 gotcha）。仓内现状：mm SKILL.md 有 2 条「已知可接受的错」+ 5 条 gotchas，**共 7 个可退化点**；4 类 × 5 条 = 20 条任务里，PLAN 没写哪 7 条对哪 7 点。**测试面应该断言这个映射表存在且双向闭合**。

**(2) 合成痕迹残留**：合成脏输入（类 2/3）本质是**从资产自己的 gotchas 表反向生成的**——这有一个致命的循环风险：**资产说「本周五之前」会提取成「周五之前」，于是我们造一条含「本周五之前」的脏输入；资产于是「正确处理」了它；题目于是「通过」了。**这道题测的不是真实能力，是**资产对自己已知坑的复述**。这就是「防背题」在课程侧的具体形态，而且它**不是学员背题，是题目背资产**。
- **这个风险的判据是可测的**：一道模拟任务题的「通过」是否**可由资产自身文档推出**。具体化：如果一道题的正确答案完全写在 SKILL.md 里（关键词表、已列的错、gotchas），那它对「资产是否真的帮学员做事」零信息量。**测试面应该要求每条模拟任务标注它测的是「资产文档里写过的规则」还是「资产文档里没写、需要推断的规则」**，并统计后者占比。**这个比例是模拟任务集质量的唯一可机判代理指标**（真实素材占比上不去时，至少知道合成题里有几成是「复述题」）。
- **类 3（red fixtures）在这条轴上是最干净的**：4 个 red fixture 测的是「校验器会不会放过坏东西」，**正确答案不在 SKILL.md 里**（在 `oracle/fixtures/` 里）。它们是真正的对抗题。**PLAN §6.4:402 说「成本接近零，改个定位就行」——我同意，而且我认为类 3 应该占的比重高于 4×5 的均分（1/4）**，理由是它是四类里唯一不受「资产自证」污染的一类。这是我的一个 [假设] 级建议。

#### 与 L2 题集的关系——必须解耦，理由是 nonce 与泄漏路径不同
PLAN §6.4:399 说 20 条「进 bench（train 侧）」，§3.4 有 holdout 层。**那么模拟任务集和 L2 dev 题集是同一批还是两批？**
- PLAN 的措辞（「进 bench（train 侧）」）读起来像是**同一批**。**我认为必须拆开**，理由：
  - **消费方不同**：L2 题由 harness 自动跑、判分器是 oracle/rubric；课堂模拟任务由讲师在课堂上用、要能被白话讲出来、要能在 30 分钟内做完。同一批题会同时被两种判据要求，**结果是两边都不合格**（比如 mm 的 t1–t8 每题转写稿 13–14 行，逐条溯源要人工核 6–7 条，30 分钟内做不完）。
  - **泄漏路径不同**：L2 题的泄漏是「资产作者看到题→照着题改资产」（EVAL-SPEC §4.3-3 转录扫描拦）；课堂模拟任务的泄漏是「**学员提前看到题**」（学员拿到讲义/物料包，里面有样例素材）。
  - **我给不出「两批各多少条」的数字**（无实测）。但我有一条结构性主张：**课堂模拟任务集里凡是会发给学员的（演示素材、跟做填空版），必须是 nonce 化的每次新生成，不是仓内固定文件**——否则讲义一印刷就等于泄题。PLAN §3.5:203 已经有 nonce 化机制（"每题关键实体生成时注入一次性随机值"），**课程侧应该复用同一机制而不是新造**。

### 2.5 推理链 E：课堂故障预案的演练测试（拔网线 / 配额耗尽）——PLAN §6.5 的四条预案里只有一条真的需要演练

PLAN §6.5:409-415 的四条预案，前提是「实测依赖面：v5 三资产零网络、零 GPU、零 Docker、零模型调用、零 API key，第三方依赖只有 PyYAML」。

**我要在这里加一条我自己做的核实**（因为它是这四条预案的全部依据，而它可以被独立验证）：我 grep 了四个 dist 包与五个 v5 资产的 python 入口。**我在本次会话没有重跑轨迹4 的 C3 命令**（我 grep 的是 runner/main 的 argparse 与 import，范围比轨迹4 窄）。所以**依赖面结论我采信轨迹4，不冒充自己验证过**。但我注意到 PLAN §6.5:409 写「v5 三资产」，而**课程要用的三个首发资产是 dist 三包（meeting-minutes / office-templates / hot-templates）**，不是 v5 三资产（SM/DP/HW）。**dist 包的依赖面与 v5 资产不是一回事**：

- 我实测 C10：python-docx 1.2.0 在位。mm runner `from docx import Document`（runner.py:25）——**所以 mm 包的确定性门依赖 python-docx，不是零依赖**。

**四条预案各自的「演练测试」该怎么设计**（我的拆解）：

| 预案 | PLAN 出处 | 演练测试形态 | 机判度 |
|---|---|---|---|

| ④ 讲师机课前当场重装 | §6.5:413 | **不可测**（这是纪律不是行为）。可测的替身：讲师手册第 ① 段速查卡里必须有一条「重装已完成 + 时间戳」的签到位 | 半机判（签到位存在性） |

**但这四条都不是本镜头最该测的。** 我认为**真正该测的第五条预案 PLAN 没写**：**课堂尺自己坏了怎么办**。理由：
- PLAN §6.9:443 的五类归因里，「验收口径」是一类，出口是「改 oracle 或改课程承诺」。这意味着**PLAN 已经预期课堂尺会判错**。
- 但 PLAN 没有「判错时的现场处置」。而课堂尺判错的概率**远高于**资产坏：课堂尺要在**学员的、非预设的、脏的**素材上跑，它遇到未见过的输入形态时会怎么表现？今天没人知道。
- **测试面应该断言：课堂尺有一条「未知输入」行为契约**——不是 exit 0 也不是 exit 1，而是**一个专属的第三态**（比如 exit 3 = 「无法判定，请人工介入」）。**理由**：PLAN §6.5:415 说讲师只要会「当场判定 exit 0/1/2 三态」（这条来自轨迹4 §2.6:161，引 `deploy-pack/eval/runner.py:29-31`）。**如果课堂尺引入第四态，讲师的会/不会清单就必须同步扩**；如果不引入第三态，**课堂尺遇到没见过的素材就会给出一个假的红或假的绿**——前者冤枉学员（违反 PLAN §6.3:395「判失败的是手册不是学员」的精神），后者是更糟的：假绿会让一个不合格的交付物流进收费闭环。
- **这是一个真实的、当前无人负责的失败模式，且它同时是「假绿」风险**。我给它的置信度是**中**（我确认了 PLAN 与现有 runner 都没有这个态：deploy-pack `validate.py:23` 明确「0=全过/1=有失败/2=参数非法」，mm runner `:234` `return 2` 仅用于用法错，speaker-mapping runner 同）。

### 2.6 推理链 F：讲师手册的可执行性测试——「零讲稿者能否只靠手册跑完」的机器化尝试与它的天花板

**命题**：PLAN §6.3:391 的 L1 通过标准是「不看讲稿能带完」，§6.6:419 定义四段式手册。测试面要回答：这条能测吗？

**我的拆解：L1 其实是三个独立的断言，PLAN 把它们压成了一句话。**

| 子断言 | 能否机判 | 依据 |
|---|---|---|
| L1-a 手册里引用的每个路径/行号/参数**真实存在且正确** | **能，全自动** | D5 实证（record.md:44）；PLAN §5.3:326 已把「引引面」写进过程轨 |
| L1-b 手册里的命令**逐条可执行且退出码符合手册所述** | **能，半自动** | 抽出所有代码块逐条跑，对比手册写的预期输出。风险：有些命令依赖学员环境（讲师机有、学员机未必有） |
| L1-c **不看讲稿**能带完 | **不能** | 这是「零上下文 agent 能否照手册跑完」= L2 的定义（PLAN §6.3:392）。**L1-c 与 L2 在可测性上是同一件事，区别只在执行者是人还是 agent** |
| L1-d 带完之后**每步耗时**可记录 | **能（记录），不能（判门）** | 超时不等于不可复制 |

**所以我的核心主张**：**PLAN 的 L1 与 L2 边界画错了。** PLAN §6.3:391 说 L1 抓「手册不可照读」、L2 抓「文档缺步骤」——**这两个失败模式在机判层面无法区分**：「不可照读」和「缺步骤」都会表现为「零执行者卡在某一步」。**唯一能区分它们的是执行者是不是人**（人能靠常识绕过，人绕不过的地方才是真「缺步骤」；agent 绕不过的地方，人可能靠经验绕）。
- **这不意味着两层冗余**，而意味着**L2 可以替 L1 承担 L1-a/L1-b/L1-c 的机器部分，只把「真·人读起来别扭」这一件事留给 L1**。
- **这个主张的实践后果**：L1 的 2 小时（PLAN §6.3:391）里，可以先花 30 分钟跑 L1-a/L1-b 的自动检查（开发 agent 做），剩下 90 分钟给真人。**这直接降低 O-14（讲师来源）的阻塞成本**——不需要先找到备份讲师才能开始修手册。这是一个有实用价值的推论（置信度中，依赖「L1-a/L1-b 的自动检查能在 30 分钟内建起来」这个前提，**未验证**）。

**手册四段式（PLAN §6.6:419）里，测试面最该盯的是第 ④ 段**。理由：PLAN 自己说第 ④ 段是「现有 handbook.md:92-99 完全空白的部分」。我实读了 handbook.md:92-99：内容是「把 record.md 抄给 owner 看 / 在 worklog.md 追加一行 / 把三份交付物路径发给 owner」——**确实是写给彩排 agent 的**。而 PLAN §6.7:428 说「第一阶段物理形态 = 课后 24 小时内人工发一个 zip + 人工转账，写进讲师手册第 ④ 段」。
- **第 ④ 段的可执行性有一个特别好的机判点**：**发出去的 zip 里应该有什么、不该有什么**。
  - 该有：资产包（含 eval/，因为 learner 变体不剥离 eval/，PLAN §4.3:271）、安装指引、版本号 + sha256 指纹（PLAN §6.7:427）。
  - **不该有**：oracle/（学员不需要参照物，且给了就等于给了「标准答案」——学员会对着改，正好回到 §6.1 要废的判据）、`classroom-v0.1` 的讲义材料（防转拷，PLAN §6.7:427 私域自持）。
  - **「不该有 oracle」是一条可完全机判的发布门**：`zip -l` 清单里出现 `oracle/` 即红。这条测试的价值在于——**它是「交付物 = 学员自己的东西」这个判据在分发侧的守门人**。如果学员包里带着参照物，学员就会做出「和参照一样」的东西，然后 §6.1 的判据在最后一公里被悄悄架空。
  - **我没有找到任何现成机制做这件事**（C8：仓内唯一的 checklist 是 `v3/report/DISTRIBUTION-CHECKLIST.md`，它管的是 dist 包上架，不管课堂发包）。**这是一个零成本的、开发者可见的高价值测试**。

### 2.7 推理链 G：哪些课堂测试开发者可见、哪些 holdout——边界怎么划

**先说结论性的划分原则**（我认为是本镜头最需要写清的一条）：

> **holdout 的定义不是「难」，是「调过就会变好但变得不真实」。**
> 判据是：**如果开发者读过这条测试的输入，他写出的资产会不会因此更可能通过它？**会 → holdout。不会 → 开发者可见。

按这条原则逐个判：

| 测试 | 开发者可见？ | 理由 |
|---|---|---|
| **L0 资产机检（G0-1/G0-2/conformance）** | **可见** | 它测的是资产自己的正确性，开发者当然要能跑能修。**这不是「答案」是「尺子」** |
| **手册静态检查（引用完整性/Markdown 结构/命令参数）** | **可见** | 同上，是尺子不是答案 |
| **课堂尺本身（对学员素材判绿的 5 项检查）** | **可见** | **必须可见**——它是尺子。开发者要能拿它调资产。**但这带来一个真实的作弊面，见 §2.8** |
| **模拟任务集（类 1/2/3 的具体题面）** | **半可见** | 类 2/3 的**生成规则**可见（gotchas 表、red fixtures 本来就在仓内），**具体题面实例**应 holdout。理由：开发者知道「会考『本周五之前』」就能针对性优化 SKILL.md 的这段说明——**这正是资产该做的优化（真的更好了），但它让课堂尺不再度量真实能力**。PLAN §3.5:203 的 nonce 化正是解药 |
| **学员现场自带素材（类 4）** | **天然 holdout** | PLAN §6.4:403 已定「一次性不进 bench」——**PLAN 在这一点上是对的** |
| **L3 真人彩排的原始卡点记录** | **半可见** | 归因后的「资产缺陷」类要进 backlog（PLAN §6.9:443），所以开发者会看到。但**原始记录的「讲师兜底次数」如果提前给开发者，会诱发手册写成「针对这个人的补丁」**。建议：**兜底计数与卡点清单在归因前对开发者不可见**（[假设]，因为还没有这套流程，我无法验证它可行） |
| **新学员现场任务库（ask 明确点名的 holdout 候选）** | **holdout** | 这是本镜头最核心的 holdout 对象。理由：它是课程交付质量的**唯一不可替代的度量**——L0/L1/L2 全是「我们自己能测的」，只有「真人第一次用会不会卡死」测不了（PLAN §6.3:393 的原话） |
| **红路 demo 脚本（hooks.md:48 的 exit 1 画面）** | **可见** | 它是仪式也是教学材料，不泄答案 |

**一个 PLAN 没写但我认为是必需的 holdout**：**「课堂尺的假绿率」**。
- 定义：在课堂尺上跑一批**已知不合格**的产物（人工注入缺陷：编造的条目、漏掉的节、把待办负责人猜成真名而原文没有、summary 数字对不上），看课堂尺判红的比例。
- 这就是 PLAN §3.8:232 的「checker 对拍」（准确率/召回各自 ≥95%）在课堂尺上的应用——**PLAN 把它排给了 office-eval-suite（WS3），但没有排给课堂尺**。
- **为什么它必须 holdout**：缺陷注入的样本如果由开发者设计，开发者会注入「自己知道能被抓到」的缺陷。召回率会虚高。
- **它拦谁**：拦「课堂尺看起来很严谨、实际上一抓一个漏」的不诚实。这正是 owner 意图 e「防过拟合/防作弊」在课程侧的形态。

### 2.8 一个我在拆解过程中撞到的真实作弊面（PLAN 完全没有覆盖）

PLAN §6.1 的判据是「学员用自己的素材做出一件自己的事，且被机器判绿」。**这句话有一个隐含的、可被合法利用的漏洞：开发者可以把课堂尺调到「学员用自己的素材也能过」，而调它的方式是让课堂尺足够宽松。**

具体形态：
1. 课堂尺的检查项从 5 项减到 3 项（把溯源检查去掉——因为学员的素材更脏，溯源更容易红）；
2. 课堂尺的容差从 ±2 放宽到「不检查条数」；
3. 课堂尺改成「只判格式不判内容」。

**这三种改动都能让「课堂红率」这个先行指标（PLAN §1.2:57、§6.9:444）变好看，而资产能力一点没变。** 因为课堂红率是唯一的课堂侧先行指标，**指标好看 → 决策者以为资产覆盖在改善 → 继续迭代而不修尺子**。这与 PLAN §3.6:209 自己诊断的 bench 侧病灶（「失败不是模型不行，是尺子坏了」）**同构**。

**测试面应该断言的东西（这是本轨迹我最想留下的一条）**：
> **课堂尺的检查项集合与容差，必须像 runner 一样受「零改动铁律」保护，且每次改动必须留痕、必须 bump 版本、必须重跑红绿双路。**

- 具体形态：课堂尺的检查项清单**冻结在 SPEC 里**（不是写在代码注释里），改动走版本号；课堂尺改动后**必须重跑「已知不合格样本对拍」**（§2.7 的 holdout）并留档；**红路必须仍是 exit 1**（PLAN §6.5 已有「红路必须保留」的仪式，缺的是它的门禁化）。
- **这与 PLAN §3.3:181 的 runner 零改动铁律是同一个道理，只是对象从「v5 runner」换成「课堂尺」**。PLAN 把铁律写给了 bench 侧和 v5 侧，**课程侧漏了**。我认为这是本镜头对 PLAN 最有价值的一处补漏。
- 置信度：**中高**。推理基于 PLAN §3.6 的自诊断（尺子坏了但数字好看）+ PLAN §1.2 把课堂红率列为先行指标 + 现有 runner 已有零改动先例（TASK.md:76 红线）+ 我实测的 mm runner 溯源检查对参照侧输入目录的绑定（说明这类绑定很容易被「改路径」顺手改掉）。

1. **PLAN §6.1 的新判据在今天的仓库里没有对应的机器实现——四个首发相关 runner 全部是对固定 oracle 的确定性门，没有一个能对学员自带素材判绿。**（置信度：**高**。§3.1 六条 runner 源码证据 + C3/C6 实跑。这是本镜头最重要的事实。）

5. **PLAN §6.3 对 L1/L2 的失败模式切分在机判层面无法区分**——「手册不可照读」与「文档缺步骤」都表现为「零执行者卡在某一步」。唯一区别是执行者是人还是 agent。**实践后果：L1 的 2 小时里约 30 分钟可由自动检查替代（引用完整性 + 命令可执行性），这降低 O-14（讲师来源）的阻塞成本。**（置信度：**中**。切分不成立的部分推理清晰；但「30 分钟够不够建起来」**未验证**。）

6. **handbook.md 的乱码分三类，各由不同的测试拦**：(a) 未闭合 Markdown 标记（`:46`）→ Markdown 结构 linter 可全机判；(b) 随机乱码串（`:54,:56,:74,:88`）→ 需要判据，可由「零上下文 agent 能否复述成因果句」代理；(c) 语义倒错（`:44` 红路 exit 语义被复述反）→ **只有真人彩排能拦，机器拦不了**。**这为 PLAN §6.3:395「L2 拦不住、只有 L1/L3 能拦」提供了机制层面的解释，而不只是断言。**（置信度：**中高**。C7 逐行实读是 A 级；(a)(b) 的可机判性是我的设计主张，**未实现未验证**。）

## 6. 给测试撰写者（GLM-5.3）的具体建议

1. **测试文档的第一句就该是结论 1，而不是任何用例。** 建议写成：「**课程交付测试面当前缺的不是测试，是被测对象。** PLAN §6.1 的判据依赖一把『课堂尺』（对学员自带素材判业务绿），该装置在四个首发 runner 中均不存在（证据：`mm/eval/runner.py:239,173-176,210-231`、`ot/eval/runner.py:58`、`sm/eval/runner.py:65+`、`hw/eval/runner.py:356`）。本面的测试分两部分：**(A) 课堂尺自身的测试**（它是首要交付物）；**(B) 课程流程的测试**（L0–L3、发包、故障预案）。」

2. **把「课堂尺」当成一个待建装置来设计测试，不要把它当成已有工具来调用。** 它的测试应包含至少这五条（每条拦的具体不诚实我写在括号里）：
   - **SC-1 正例绿**：对一份人工确认合格的学员素材产物判绿（拦：尺子根本没实现，或实现即全红）。
   - **SC-2 溯源基准正确性**：把学员输入换成另一份转写稿，尺子必须**跟着换基准**（拦：实现时把基准写死成某个路径——这是最容易犯的错，因为 mm runner 原型就是绑参照侧目录的，C3 已证）。
   - **SC-3 红路 exit 1**：注入已知缺陷的产物必须判红，且**红的原因信息可读**（拦：尺子只会判红但说不出哪里错，学员和讲师都无法用）。
   - **SC-4 未知输入第三态**：喂一份形态没见过的素材，尺子必须给「无法判定」而不是假绿/假红（拦：§4 结论 13 的假绿，**这是最危险的一条**）。
   - **SC-5 假绿率对拍（holdout）**：人工注入 N 类缺陷，统计召回（§2.7）。**这条是 holdout，注入样本不对开发者可见。**

3. **把「交付物 ≠ oracle 复现物」做成一条独立的、可复用的机检门。** 机制：比对交付物树 sha256 与 oracle 树 sha256，命中即红（PLAN §3.3:179 已有 oracle 哈希门的先例，直接复用）。**它同时是 L0 的边界断言、L2 的交付物断言、和发包清单的门**——一个机制三处用，投产比最高。

4. **讲师手册的测试分两层写，机器层给足，人力层别装。** 机器层：Markdown 结构（拦 handbook.md:46 的未闭合 `**`）、引用完整性（拦 D5，record.md:44）、命令参数与 `--help` 一致、命令可执行且退出码符合手册所述。人力层：**只留一条**——「零讲稿真人带一遍，三类兜底分别计数」。**不要试图把「可执行性」全部机判化**（§2.3 结论 6c：语义倒错只有人能拦）。

5. **「讲师兜底」写成三个字段而不是一个数字**，并在验收单上留三个独立签名位。建议字段名直接用 §2.3 的三个口径。**在测试文档里写明为什么不合并且不合并的收益**（防止后来者「优化」成一个数）。

6. **故障演练测试按「预案 → 可测形态」逐条给，不要按「演练脚本」给。** 我在 §2.5 已经把 PLAN 四条预案的演练形态和机判度列成表了，直接用。**并补 PLAN 缺的那条：课堂尺坏了怎么办**——这应该成为第五条预案，且它的演练就是 SC-4（第三态测试）。

7. **holdout 边界用「调过就会变好但变得不真实」这条原则写进测试文档，不要用「难/不难」写。** 然后按 §2.7 的表逐条标 visible/holdout。**特别提醒撰写者：课堂尺本身必须对开发者可见**（它是尺子），**但课堂尺的缺陷注入样本必须 holdout**（它是答案）。这两条在同一份文档里容易被合并成一句「课堂尺相关测试均 holdout」，那样会直接卡死 WS2/WS5——**这是一个会真实阻塞项目的误判，值得在文档里显式警告。**

8. **把 §4 结论 14（课堂尺零改动铁律）作为一条独立的「门禁纪律」测试写进去**，形式对齐 PLAN §3.3:181 的 runner 零改动铁律：课堂尺的检查项清单冻结在 SPEC、修改走版本号、改后重跑红绿 + 重跑对拍并留档。**理由写在文档里**（§2.8 全文），因为这是本面对 PLAN 最有价值的一处补漏，撰写者如果不知道为什么，很容易在压缩篇幅时把它当「纪律性文字」删掉。

9. **测试文档里显式标注 §4 结论 3（PLAN §6.8 的两句验收口径今天不成立）。** 撰写者如果照 PLAN §6.8 写测试用例，会写出「跑 hotwords runner 得 4/4」这种**必然通过但毫无意义**的测试——它测的是 oracle 复现，不是学员交付。**这一条是本面最容易犯的错误，且 PLAN 的措辞会诱导它。**

10. **保留本轨迹 §3.3 的「未跑」清单。** 我没跑 v5 三资产的 runner、没读 dist 的 requirements.txt、没做任何真人彩排、没装 skills-ref。**测试文档里的任何数字都不能建立在我没跑过的东西上。**
