## 1. 展开方法与信息源

### 1.1 我怎么拆这个问题

「尺子是准的」这句话拆开是四个可测对象，而不是一个口号：

1. **尺子的刻度**（checker/runner 的判定逻辑）——给已知对错的东西，它判得对吗？→ 对拍与缺陷注入；
2. **尺子的安装**（harness 的装配逻辑：臂隔离、nonce 分发、oracle 哈希门、pin 记账）——尺子被正确装到被测物上了吗？→ 公平性与隔离的机检；
3. **尺子的读数**（聚合层：delta_vs_prev、饱和判定、缺陷率、四信号）——读出来的数字和被测现实一致吗？→ 合成向量单测 + 边界用例；
4. **读尺子的流程**（抽审 20%/5 题下限、污染处置、门禁签核）——人/流程会不会在尺子坏时发现尺子坏了？→ 流程执行测试 + 盲桩。

再往上一层是元问题：**测尺子的测试也是尺子**——扫描器、聚合器、信号门各自都会坏，所以每个测试装置自己必须落在「确定性可重放」的框架里（红绿自检、同输入逐字节复现），否则测试体系自我膨胀成一堆没人测的裁判。这条贯穿全文（推理链 C/RC-6'）。

## 2. 关键推理链（含被否决分支）

### RC-1：三类尺子事故必须升级为「缺陷标本库」，而标本库要测的是流程不是代码

**推理**：scorecard 一轮 41 门 3 FAIL，3/3 全部诊断为 bench 侧（PLAN §3.6:209 自己的判语是「失败不是模型不行，是尺子坏了」）。三起事故的形态各异：

| 标本 | 事故机制 | 当年怎么被发现的 | 沉淀为什么标本 |
|---|---|---|---|
| T1 墙钟戳 | dp01b 门把 `started_at/duration_s/generated_at`（非冻结面）纳入逐字节比对，口径过严（scorecard.md:73,78） | worker-B 人工诊断「本台账自设口径过严」 | 一份「含时钟字段的产物 + 一个逐字节比对门」→ 期望：判定为**装置问题**且被门禁放行为「非资产缺陷」 |
| T2 回显 | hw07：带 `--out` 的 run 在 stdout 尾部多一行「报告: <路径>」，跨口径比对 stdout 炸（scorecard.md:84-85；本次 E4 实证未修复但可绕过） | worker-B 双跑对比定位 | 一对「同题同参、仅 --out 有无不同」的 run → 期望：比对口径归一后不产生假红 |
| T3 路径形态 | sm05：Windows 纪基线 `fixtures\normal.txt` vs POSIX 重生成 `fixtures/normal.txt`（scorecard.md:80-82） | judge 亲 diff 实锤后裁定 A-2 归一（HANDOFF-A2B-R1.md:49,73） | 一对「仅路径分隔符不同」的产物对 → 期望：窄域对称归一后判绿，9 个 txt 仍逐字节 |

关键判断：**这三起都是人发现的**。worker-B 恰好是个靠谱的验收角色，读出了「台账自设口径过严」。但 PLAN 把宝押在流程上（§3.6 抽审纪律），所以测试面要回答的问题是：**当没有那个人在的时候，流程能不能抓住下一把坏尺子？** 这决定了标本库的用法不是「单元测试夹具」（那只能测 checker 代码），而是三层：

1. **重放层**：每次 checker/runner/harness 变更后，标本库全量重放，历史判定不得翻转（T1–T3 的期望结论钉死）；
2. **盲桩层**：每轮 L2 里混入 1–2 道只有 bench 侧知道的暗桩题（故意带已知缺陷的失败），验收时核对抽审流程有没有把它们正确归因为「题面/装置问题」——**暗桩内容对被测开发 agent 保密**，否则抽审执行测试失去盲测意义；
3. **口径层**：抽审记录的缺陷三分类（模型/题面/装置）必须与标本库的三分类定义逐条对得上——防止「归因」变成随手打标签。

**拦的是谁**：抽审流程的无能（形同虚设、抽样不足额）、开发者的自欺（把尺子错误记成模型失败，反过来也成立——把模型失败洗成装置问题刷缺陷率）。

**被否决分支**：(a)「把三类事故各写一个单元测试」→ 否决。T1 的本质是**口径**事故不是代码 bug，单测永远绿；T2/T3 的修复在比对口径层（EVAL-SPEC §3.8-7 端态判定原则），单测覆盖不了「哪个口径被用在哪个轮次」。(b)「等真的又出一次事故再补标本」→ 否决，TB4.0 是发布前修 19 题（thinking/3 RC-8 转引），事后标本只防同一种复发，防不了新形态。

### RC-2：抽审 20% 下限的执行测试——先测「关门」，再测「审得对」

**推理**：PLAN §3.6 规定「每轮抽 20% 的失败题（绝对下限 5 题）…题面缺陷率 >10% 时该轮分数不得对外」。这条纪律目前只存在于文字里，没有任何机器执行物。测试设计必须拆成两段：

1. **关门测试**（便宜、确定性）：一轮结束时，harness 检查抽审记录文件——样本量 ≥ max(0.2×失败题数, 5)、每条含三分类归因与判定人、缺陷率已算出。**构造一个失败 30 题但抽审记录只有 4 条的轮 → 收口动作必须被拒绝**（对应 PLAN §3.6「该轮分数不得用于对外声明」的机器形态：轮报告带 `external_use=false` 标志，看板层拒绝渲染对外口径）。
2. **审得对测试**（盲桩驱动）：见 RC-1 盲桩层。核对三件事：暗桩被抽中率是否符合抽样实现（纯随机抽样下暗桩可能没被抽中——**抽样器需要分层保证**：暗桩应被保证抽中，否则执行测试本身不可复现；这是一个容易被漏掉的实现细节，置信中）、归因正确、缺陷率分母口径正确。

**分母口径是一个真实的坑**：PLAN §1.2 写「每轮抽审失败题的归因中『题面问题』占比」，§3.6 写「抽 20% 的失败题」。占比的分母是**抽审集合**还是**全部失败题**？两种口径在「抽样不足额」时数值差数倍。我在 PLAN 里没有找到钉死的定义（见 §5 未决问题 1）——撰写者必须选一个写进测试判据，否则 10% 红线的执行会各轮漂移。

**拦的是谁**：产线 agent 的偷懒（不抽审就收口）与Owner 决断 O-18 的边界——「中期信号可用于方向性讨论」不等于「没抽审的轮可以对外」。

### RC-3：三臂 harness 的正确性靠合成向量单测，不靠真跑批

**推理**：harness 的读数层（delta 三个字段、任务级胜负、饱和分带）是纯函数：输入分数向量，输出结论。纯函数的正确性测试不应当用真模型跑批来验证（慢、随机、不可复现），应当用**合成向量**打边界：

- **delta_vs_prev 计算正确性**：构造 A_new/A_old/none 三组已知分数，断言三个 delta 字段逐位等于手算值。边界用例：A_old 缺席（首轮两臂，`delta_vs_prev` 必须为 null 而非 0——PLAN §3.2:157「首轮基线轮为两臂」）；任务 ID 非连续（配对必须按 task id，不许按数组下标——EVAL-SPEC §1.1:49 那次「旧轮逐任务行按同序排列推断对齐」的事故就是位置配对的教训）；负增益（A_new < none 时三个 delta 全负、reverse_tasks 计数正确——历史锚点 paper-to-skill Δ−0.5，REGISTRY.md:28）。
- **臂间公平性**（同题同 nonce）：harness 逐 run 校验四样东西逐字节/逐值相等：①两臂 brief.md（PLAN §3.3:168「两臂逐字相同」）；②inputs/ 目录树哈希；③model_pin.json 除 arm 字段外五元组逐字节相等（**大小写敏感判等**——PLAN §5.1:313 钉版纪律点名 `Minimax-`/`MiniMax-` 两种拼法都解析成功过，大小写不敏感的判等会让「同模型」主张在两臂静默地假）；④采样参数。唯一允许不同的字段 = 臂标识 + 臂产物。
- **nonce 矩阵**：同任务同重复内，各臂 nonce 相同（否则 oracle 配对失效）；同任务跨重复，nonce 必须不同（否则背题防御失效）；同种子重跑，实例 + oracle 逐字节复现（EVAL-SPEC §5.1 L2-2）。这是一张 2×2 真值表，每个格子一条测试。
- **饱和检测**：E5 实证了输入条件（8×treatMean=10）。测试断言：这样的题集产出**降饱和动作**（进轮换池标记 + 报告出「天花板」口径），而不是 accepted/good verdict。PLAN §3.2:162 已经把三种「没差异」分开（真无差异/测不出/不可判），测试要逐字段验证这三分法在输出里真的分开——特别是「treatment 全满 + baseline 也满」应判「真无差异或天花板」，而「treatment 全满 + baseline 低」应判「饱和，该加题」，两者走不同的后续动作。
- **难度带分拣**：treatment 通过率 >90%/60–90%/<60% 三带的分拣路由各给一条合成用例（PLAN §3.2:161，数值本身是 [假设]，测试应把阈值做成可注入参数——阈值改了测试不用改）。
- **跨族不可比**（PLAN §5.5:347）：喂两条不同族的行给聚合器 → 必须拒绝产出跨族 Δ，而不是除一下完事。同理跨 evalbench 版本（EVAL-SPEC §4.4-2「禁止并列比较或合并披露」）——报告层构造一个新旧版本混排的输入 → 拒绝。
- **真跑批只做端到端抽验**：一次最小真跑（PLAN §5.4 MVP 四步）用来验证「合成测试里 mock 的接口形状和真实接口一致」，其结论按 §5.4 纪律只能叫「管线验证信号」。

**拦的是谁**：harness 开发者的无能（算错 Δ、按位置配对、大小写折叠 pin）；资产开发者的不诚实（拿 `delta_vs_none` 冒充 `delta_vs_prev` 宣传「本轮迭代有效」——这是三臂设计里最容易被营销话术偷换的一个数字，测试必须让三个字段在报告里物理分开且各自有出处）。

**被否决分支**：(a)「用一次真跑批的全量结果做金标」→ 否决：真跑结果本身就是被测系统的输出，用它测自己循环论证；且按 O-18，n 小的真跑不得当验收结论，更不能当测试金标。(b)「delta 计算写完靠 code review 保证」→ 否决：EVAL-SPEC §1.1 的 2.66 极差教训就是「看起来对」的统计代码在边界上翻转叙事。

### RC-4：fail-closed 的「方向」必须被测试——exit 1 是共同的，含义不是

**推理**：E2/E6 两个实验给出了一对镜像事实：被测目录不存在 → exit 1（红路正确）；**参照目录不存在 → 同样 exit 1**，而且 detail 打出「与参照产物一致 12/12（100%）…参照产物缺失/损坏」这种红行里嵌绿话术的自相矛盾文本。runner 这么写没有错（TASK.md:76 红线：runner 一个字不改，它 fail-closed 是对的），**但 L2 harness 不能把 exit 1 一律记成「资产失败」**——按 EVAL-SPEC §3.5，参照区坏了是 infra_error，不进统计、单独披露。所以 harness 的红路测试矩阵必须包含**双向**：

1. **坏被测**（资产致害方向）：空目录/截断文件/坏编码/篡改行 → exit 1 且 detail 指向被测侧。这一组 v5 已有先例（BASELINE §2-20 篡改副本法；deploy-pack 六红矩阵 empty/bad-yaml/missing-service/env-drift/hardcoded-secret/subset，REGISTRY.md:163），新 harness 直接继承并在 L2 任务包上重演。
2. **坏参照**（尺子致害方向）：参照缺失/参照被写坏/参照哈希不匹配 → harness 必须判 infra_error 而非资产失败。**判定的第一道闸不应是解析 runner 的 detail 字符串**（脆弱，且 detail 本身有「12/12 100%」的误导话术），而应是 harness 自己的 **oracle 哈希前置门**（E3 已证 stdlib 可实现：跑前算一次、跑后再算一次，不一致即 abort——PLAN §3.3:179 原文就这么要求）。detail 解析只作第二道冗余。
3. **「资产致害」的可见性**（本题面点名项）：负增益不是假想。arXiv:2608.11888 的 182 例效率回退在两臂框架里不可见（PLAN §3.2:159；thinking/3 RC-4），三臂就是为此而生。测试：构造 A_new 臂 token 数为 none 臂 3 倍、分数持平的合成 run → matrix.json 必须让效率门（token 比率 ≤2.0，EVAL-SPEC §7.1 门 3 / PLAN §5.5:361）亮红 + 决策表路由到「资产调查」。**负增益不可见 = 尺子单向偏置**，这是 L2 红路的本义，与 L1 红路（exit 1）并列。

**拦的是谁**：harness 开发者的无能（把 infra_error 记成资产失败，错杀资产）；资产维护者的侥幸（效率回退被均分掩盖）。

**被否决分支**：(a)「给 runner 加 exit 3 表示参照坏了」→ 否决，违反 runner 零改动铁律（PLAN §3.3:181，TASK.md:76）；改口径必须走 contract/spec/runner 三方同步版本化先例（HANDOFF-A2B-R1.md:49），而这里根本不需要——前置门在 harness 层就能闭合。(b)「detail 字符串解析做分诊」→ 否决为主：E6 证明 detail 在参照侧损坏时还会打印 100% 一致的话术，正则解析将脆弱地依赖一个已知有毛病的输出格式；只作冗余校验。

### RC-5：防污染三件套各自的验证测试，和「扫描器本身是新的尺子」的元回归问题

**推理**：PLAN §3.5 的三件套 + 断网，每一件的失败模式不同，验证方式必须分别设计：

1. **nonce 化**（防模型背题）：
   - 生成器红绿自检（EVAL-SPEC §5.1 L2-3 继承）：对 oracle 跑 checker 全绿、对损坏输入全红，不过则禁止投产——这是现成语言，测试直接引用；
   - **陈旧 oracle 必须红**：用 nonce-A 生成的 oracle 去判 nonce-B 的实例 → 必须判失败。这一条是「背题防御」的直接测试：模型从上一轮记住的答案，在本轮实例上必须不得分。若这条不测，nonce 机制可能悄悄退化成「生成时注入、判分时忘记」的装饰品；
   - nonce 熵与唯一性：抽 K 个 nonce 断言零重复（廉价，防随机源退化）。
2. **holdout 物理隔离 + 转录扫描**（防双向往漏）：
   - 隔离探针（PLAN §5.4:338 step 1 的现成模式）：跑批前置 walk 基线臂目录树，摸到任何 SKILL.md/oracle/holdout 文件即 abort——测试用一棵「故意藏了资产文件的树」验证探针真的拦；
   - 转录扫描注入实验（题面点名项）：故意放一道转录里含资产正文片段的假 run → 扫描器必须命中 → 该题两臂作废；再放第二道 → 整轮无效（EVAL-SPEC §4.3-3 升级阶梯，两档都要测）；
   - **误报治理是另一半**：转录里合法提及资产名（比如 brief 里就写着任务背景）不应触发 void。测试集必须同时含阳性（真泄漏）与阴性（良性提及）样本，扫描器两类的表现都要记录——只测阳性的扫描器会在第一轮误报 void 掉好几个真题后被静默调松，松到失效；
   - **我方新增主张（PLAN 未覆盖，标 [假设]）**：现有扫描方向只有「资产片段 → 模型转录」（PLAN §3.4:194），反方向「开发者看了 holdout 题 → 把题面知识写进资产」只靠访问纪律。**nonce 值是完美的双向绊线**——每题关键实体都是一次性随机值，对每轮资产的 git diff 扫描 nonce 表，命中即资产已被污染，开发者不自觉的泄漏（题面进了他的上下文顺手写进 SKILL.md）也会被抓。成本近零，建议纳入。
3. **断网跑**（防外网取解，ForgeCode 式）： hardest to test cheaply。务实做法：harness 逐 run 记录网络访问面 + 资产链零网络已是实测事实（PLAN §6.5:409），测试退化为「断网环境下全绿路重演一次」+「转录命令面断言：出现 curl/wget/网络 API 调用即红」（PLAN §5.3:326 过程轨命令面断言的自然扩展）。
4. **元回归**：转录扫描器自己坏了怎么办？扫描器是确定性片段匹配时，可进标本库重放（RC-1 框架）；若用 LLM 做语义判污染，它就成了不可重放的新裁判——见被否决分支。

**拦的是谁**：资产开发者的不诚实（背题、把 holdout 知识煮进资产）；harness 开发者的无能（扫描器阈值拍脑袋、误报后静默调松）。

**被否决分支**：(a)「污染判定交给 LLM 读转录做语义审计」→ 否决为主：①不可逐字节复现，违反本仓「同输入同输出」的测试装置纪律（runner.py:30 的自述就是范本）；②LLM 审计员自己会漏报/误报，且无法用标本库重放校准；③与「程序化判分优先」（EVAL-SPEC §5.1 L3-2）哲学冲突。LLM 只可做抽检复核第二意见并落盘，不作 void 依据。(b)「holdout 对开发者加密/DRM」→ 否决：防的是无意识污染与顺手抄题，不是防贼；独立目录 + 访问纪律 + 扫描兜底（PLAN §8 O-11 默认值）已覆盖威胁模型，加密徒增流程摩擦——与 PLAN §6.7「明确不做 DRM」是同一个判断在 bench 侧的投影。

### RC-6：四信号门 = 机器算一半 + 人签另一半，测试两头都要管

**推理**：PLAN §3.7:216-225 与 thinking/3 RC-13 把「切真实人类」定义为 S1∧S2∧S3∧S4 + ≥2 里程碑 + owner 签字（O-12 双钥匙）。拆解可测性：

- **S1 饱和**：可全机判，前提是 L2 并置的任务级二元 pass/fail 真的落盘（PLAN §3.2:162）。测试：构造 5/5 全过与 4/5 的题各一 → 分带正确；「移出迭代池」必须真的发生在池状态文件里（下一轮选题器不再选它），不只是报告里一句话。
- **S2 边际**：依赖 ≥3 轮 delta_vs_prev 历史。测试用**合成历史表**驱动：恰好 0.10、0.099、方向翻转、第 3 轮反弹等边界，判定表逐一断言。**前置依赖**：题目池轮换（§3.8 通胀对策新增 N 退役 M）之后，delta_vs_prev 的配对语义是什么（同题配对？池级聚合？）PLAN 没有定义到可机检粒度——这是 S2 的地基，必须先钉（见 §5 未决问题 6）。
- **S3 反向**：≤1 的判定直接来自任务级均分比较（EVAL-SPEC §3.6③ 同源），合成用例平凡；要测的是它与复合线③的一致性（同一份数据两个门读出的反向计数必须相等）。
- **S4 题面可信**：来自 RC-2 的抽审记录，测试复用。
- **双钥匙的机器侧**：信号全绿后，gate 只能产出「qualified-pending-signoff」状态 + 一份引用全部输入文件 sha256 的判定表；**owner 签字文件缺失时，下游（L3 试点启动器）必须拒绝启动**。测试：①缺签字 → 拒绝；②签字文件在、但某轮输入文件的 sha256 与判定表记录不符（事后有人改了历史轮数据）→ 拒绝并报篡改。留痕先例是 K-5 的 evidence/publish-approval REQUEST（REGISTRY.md:203「未代签未发布」）——「机器永代签」这个红线在 bench 侧的镜像。
- **留痕**：每轮四信号判定表落盘（PLAN WS12:480），每格可溯源到源产物文件。

**拦的是谁**：产线的急躁（没到极限就切真实人类，把「尺子到顶」当「资产到顶」——thinking/3 RC-13 的核心警告）；agent 的越权（代签 owner 决断，TASK.md:74「其他角色不可代签」红线）。

**被否决分支**：(a)「四信号全绿自动切 L3」→ 否决，违反 O-12 双钥匙默认值；测试反而要把「自动切」做成必须失败的反向用例。(b)「S2 用绝对 Δ 阈值」→ 已被 PLAN 否决（Δ 被难度/裁判/模型版本混淆，EVAL-SPEC §1.1 实测 2.66 极差），不再重复。

### RC-7：开发者可见 vs holdout 的划分——按「作弊面」切，不按「保密等级」切

**推理**：划分的目的不是保密，是让三类作弊面失效。逐面盘点：

| 作弊面 | 作弊动作 | 必须隐藏的尺子细节 | 依据 |
|---|---|---|---|
| 背题 | 资产/开发者记忆 holdout 题面与答案 | holdout 题面、输入、oracle、nonce 表、holdout 生成器 | PLAN §3.4:194 holdout 纪律；§3.3:174 oracle 不入包 |
| 裁判迎合 | 开发者知道裁判是谁/怎么打分，把产物朝裁判偏好优化 | 裁判身份、裁判 prompt 版本、复评抽检的发生时机 | EVAL-SPEC §3.4-4 盲态；PLAN §5.3:327 裁判禁读资产正文与 oracle |
| 门禁迎合 | 开发者只优化被抽审的题 | 抽审样本选择（暗桩尤其） | RC-2 盲桩保密 |
| 阈值凑绿 | 看到难度带/复合线阈值后把题「调」到带内 | 无——**阈值应该公开**：判据公开是公平的前提，藏判据只会催生猜谜 | 本仓先例：接口常量全文披露（EVAL-SPEC 增补条款 E-1 的同构逻辑） |

最后一条是我的关键立场：**藏「考题」，公开「考纲」**。EVAL-SPEC E-1 已确立「凡 eval 对常量做比对者，常量全集必须全文披露」——那是防实现者瞎猜；bench 侧同构的原则是：判定规则、阈值、rubric 全部公开可查，随机化（nonce、暗桩、抽检时点）全部保密。这条线划清后，「哪些细节对开发者隐藏」就不需要逐项拍脑袋：**凡属随机化的藏，凡属判据的亮**。

执行机制（无 ACL 基建的现实下）：独立目录（O-11）+ 每轮 harness 前置探针 + 双向 nonce 扫描（RC-5 新增主张）+ git 卫生（holdout 不入任何工作树，连 .gitignore 都不需要——物理上就不在仓库里）。测试即：以「开发者角色」的配置跑一次 harness → 对 holdout 路径的任何读尝试必须留下违规记录且中止；再以「开发者身份」提交一份含 holdout nonce 值的资产 diff → 扫描绊线必须红。

**拦的是谁**：迭代开发者的无意识污染（不是贼，是顺手的读者）与有意识作弊（把 holdout 煮进资产）；同时拦产线的过度防卫（把判据也藏起来，制造猜谜式开发）。

**被否决分支**：见 RC-5(b) DRM 分支，不重复。

## 4. 倾向性结论（每条标置信度）

1. **三类尺子事故必须沉淀为标本库并以「重放 + 盲桩 + 口径对齐」三层使用；纯单元测试拦不住其中口径类事故。**（置信度高：scorecard 3/3 归因 + T1 的口径本质）
2. **抽审 20%/5 题下限目前无任何机器执行物，「关门测试」（收口前置校验）应先于「审得对测试」建设，且暗桩必须保密、抽样器必须分层保证暗桩被抽中。**（置信度高：PLAN §3.6 只有文字；分层保证是我方推论，置信中）
3. **三臂聚合层是纯函数，正确性测试应以合成向量为主、真跑批只做端到端抽验；delta_vs_prev 与 delta_vs_none 必须在报告里物理分开，防营销偷换。**（置信度高：纯函数性质客观；物理分开是我方设计主张，置信中高）
4. **饱和检测是 L2 上线第一天就必须有的报警器，不是报告美化项；meeting-minutes 8×treatMean=10 是活的输入条件（本次实读）。**（置信度高）
5. **runner 的 exit 1 不能在 L2 里一律记资产失败：参照侧损坏必须由 harness 的 oracle 哈希前置门判 infra_error（E6 实证同码 + 矛盾话术 detail）；runner 本身零改动。**（置信度高：EVAL-SPEC §3.5 + E6 实测）

## 6. 给测试撰写者的建议

1. **优先级**：P0 = 标本库重放（T1/T2/T3）+ oracle 哈希前置门 + 三臂聚合器合成向量单测（delta 三字段/首轮 null/按 id 配对/跨族跨版本拒绝）；P1 = 抽审关门测试 + 盲桩归因测试 + 转录扫描阴阳注入实验 + holdout 隔离探针 + 参照侧损坏 infra_error 分诊；P2 = 四信号门表驱动测试 + 双钥匙拒绝路径 + nonce 双向扫描 + 对拍门/退役比的池状态测试。P0 不做，P1/P2 的结论都建立在没校准的尺子上。
2. **每条测试标注「拦谁的不诚实/谁的无能」**（本轨迹各 RC 已给出，可直接搬）；没有明确拦截对象的测试要么删掉要么降级为信息记录——防「全覆盖」注水。
3. **不变量条款直接引用既有门禁语言**，不要自造词汇：绿路/红路（exit 0/1/2）、确定性门、盲评门复合线三条件、门 5（无恒过/恒败/双臂同过断言——它天然是 checker 测试的生成器：任何恒过或恒败的 check 就是 bug）、钉版五元组、污染即作废两档、回退门三条件。这使测试结果可被 REGISTRY 式台账登记（先例：R2 只追加更正行）。
4. **写入测试文档的硬纪律**（我自己踩过/差点踩过的）：①一切生成/注入只落 evalkit/ scratch，实验前先跑「参照区只读」预检（脚本第一动作 = 记录 oracle 树哈希，结束再验一次——E3 的实现 15 行就够）；②退出码用无管道方式捕获（Git Bash 管道尾 `$?` 是 tail 的退出码，我在 E2 前一次探测里就中招，BASELINE §7-9 早有记载）；③Windows 落盘用 Python `open(..., encoding="utf-8", newline="\n")`（PLAN R-7，hw JSON 前科）。
5. **饱和报警测试直接用 E5 的真实数据当夹具输入**（8×treatMean=10 的 taskAggs 就在盘内），不用伪造数据——真实夹具比合成夹具更难被质疑。
6. **参照侧损坏的 specimen 必须进库**（E6 的新发现）：它同时测两件事——infra_error 分诊正确、以及 runner 矛盾话术（红行内 12/12 100%）不被误读。harness 分诊以自己的哈希门为准，detail 解析只作冗余并断言「解析结果与哈希门一致」。
7. **暗桩保密条款写进测试文档本身**：暗桩的存在可以公开，内容与当轮是否投放必须对开发 agent 保密；测试文档里给出「保密面清单」而非暗桩实例。
8. **裁判侧测试借 n=2 标签互换先例**（REGISTRY.md:191-192 zctl-mcp/acceptor-agent 的两评委双臂盲评）：标签互换后结论必须随之翻转，不翻转 = 裁判在看标签不看产物。加上 EVAL-SPEC §3.4 复评抽检的合成注入（同产物两次评分差 >2 → 换裁判流程被触发）。
9. **不要写「对 runner 增加输出/退出码」类的测试需求**——一律绕开 runner 零改动铁律；需要新信号时在 harness 层加前置门（oracle 哈希、隔离探针、pin 判等），薄封套模式（PLAN §3.3:181）是唯一合法的 runner 接触面。
10. **S2 先钉语义再写测试**（未决问题 6）：题目池轮换下的 delta_vs_prev 配对语义不定，S2 的测试写出来也是悬空的；建议撰写者把「S2 语义钉版」列为 WS12 的前置验收项并在测试文档中留占位。
11. **把「主动未执行」也写进证据**：测试文档里记录「哪些实验因触参照区风险而明确不跑、用什么只读替代」，这本身就是防污染纪律的执行示范（我在 §1.3 末段的做法可作模板）。
