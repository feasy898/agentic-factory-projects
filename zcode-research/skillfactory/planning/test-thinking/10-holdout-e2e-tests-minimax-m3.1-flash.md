### 1.3 走过的弯路（都改变了结论）

- **弯路 1：我差点把 ACL 当成 holdout 的第一道防线写进建议。** 实测发现同一账号用 `robocopy /B` 就能把 deny 目录里的文件原样拷出来（§3.2）。如果我不跑这一步，我会写出一份「权限位已验证」的假验收。**结论从「holdout 靠权限位保护」改成「权限位只做事故预防与绊线，保密性靠 nonce 过期 + 扫描 + 流程」。**
- **弯路 2：我差点把「扫描器零命中」当成扫描器合格。** 跑注入实验才发现：字面量 ID 清单式扫描器对「单行泄漏」「单个 nonce 泄漏」「base64 编码泄漏」三类**查全率为 0**（§3.4）。而仓内两个现存的门（`ci_isolation.py:31`、`acceptor-agent/eval/runner.py:113`）**都是字面量清单式**。这条实测把「查全率必须测」从观点变成了数据。
- **弯路 3：我差点把 Mimosa hook 台账当访问审计的现成底座。** 实读 5 份 hook-status，全部是 `PostToolUse` + `Edit`/`Write`——**只记写，不记读**（§3.5）。holdout 需要的恰恰是「谁读过」。结论：本机现成的审计设施不覆盖这个需求。
- **弯路 4：`cmd /c` 在本环境的直接调用被吞掉**（`whoami /priv`、`cmd /c type` 直接跑都只回 banner），必须经 `python subprocess` 才能拿到输出；另外用 heredoc 往 `/tmp` 写脚本被 Mimosa hook 拦（`无效参数` 之前那条「Hook additional context」）。这与 PLAN §9.1 R-7（落盘一律 Python `open(...newline="\n")`，不用 shell 重定向）同源，且要补一条：**harness 自测脚本不要用 shell 重定向/临时文件管道，用 stdin heredoc 或 python -c**。

## 2. 关键推理链

### RC-1 · holdout 在本机的物理形态不是「权限边界」，是「可检测的流程边界」

**实测（§3.1–§3.2）**：D 盘是 NTFS，ACL 可写（`icacls` 生效）；`icacls /deny BUILTIN\Users:(OI)(CI)(R)` 之后，同一 token 的 Python `open()` 报 `PermissionError`（deny 有效）；但 `takeown /F /R /A` 成功（rc=0），`icacls /reset /T` 成功（rc=0），读又通了；**`robocopy /B` 在 deny 状态下把文件原样拷了出来**。`whoami /priv` 显示 `SeBackupPrivilege` 与 `SeRestorePrivilege` **已启用**。

**结论**：本机跑 dev agent 的账号与跑 harness 的账号是同一个（`Administrator`），且持有备份/还原特权，因此**任何 DACL deny 对同账号进程都不是保密边界**。holdout 的保密性在本机只能由三件事提供：
1. **构造上不可达**：holdout 不在任何 dev 工作树/cwd/搜索根里（这是 MVP 第 1 步 `find` 实测的扩展，PLAN §5.4 步 1）；
2. **过期性**：nonce 一次性，泄露快照下一轮即失效（PLAN §3.5-1）；
3. **可检测性**：转录/产物扫描 + 资产反向扫描（PLAN §3.4）。

**被否决的分支**：
- (a)「给 holdout 目录加 deny ACL 就算物理隔离」→ **否决**。上面 robocopy /B 就是反例。写进验收文档会制造虚假安全感。
- (b)「把 holdout 放到另一台机器 / 另一个 Windows 账号」→ **否决（本期）**：本机只有一台开发机（BASELINE §0.5），且 anolis-gpu-01 是他机（AGENTS.md 机器表），跨机引入会把 WS1 MVP 从「2–3 会话」推到不可控。**留作 O-11 的升级位**：若 owner 日后愿意付出跨机成本，这才是把「隔离」升级为「边界」的最小改动。
- (c)「不做任何物理措施，只靠流程纪律」→ **部分否决**。纯流程在夜班多 agent 接力（REGISTRY L153/L183 记录的模式）下会被绕过；至少要有「撞线」——deny ACL + canary，即使它防不住人，也能**在越界发生时立刻炸出证据**。这是把它保留下来但**降级命名**的理由：叫「绊线（tripwire）」而不是「隔离（isolation）」。

### RC-2 · 「权限位」这一格的测试必须写成行为断言，不能写成命令退出码

**实测（§3.2）**：`icacls /deny ... /T` 的返回码是 **5**，输出是「已成功处理 0 个文件; 处理 1 个文件时失败」——**但 deny 实际生效了**（紧接着的 `open()` 报 PermissionError）。

**这条实测的测试含义**：如果验收门写成「跑 `icacls` 命令，退出码 0 才算过」，它会**假红**；如果写成「用 Python 打开 canary 文件，必须失败」，它才是真的在测权限。同理，任何「设置 X」的验收门，判据都必须是**设置之后的可观测行为**，不是设置命令的 rc。仓库里已有同向先例：门禁的判据一律是「runner 的 exit code」（G0-1/G0-2，TASK.md:23-24），而不是「runner 跑过了吗」。

**另一条实测细节**：`listdir` 在 deny 下**仍然成功**（只列出了子目录名 `oracle`），只有文件内容读被拒。→ 目录名/文件名本身是元数据泄漏面。测试断言必须分开写：*内容读必须失败* 与 *枚举是否允许* 是两条独立的断言，由 owner 显式选择（我建议：holdout 实例目录名用无语义 ID，枚举即使发生也不泄露题型）。

### RC-3 · 访问审计在本机当前配置下不可得（诚实记录 + 替代方案）

**实测（§3.5）**：
- `auditpol /get /category:*` 与三种 subcategory 写法全部返回「参数错误」（中文 locale 参数名不匹配），**我没有读到审计策略的当前值**（如实声明：未测得）。
- Security 日志里确实存在 4663（文件访问）事件（`Get-WinEvent` 命中 5 条），但**我读一个临时 canary 文件没有产生任何指向它的 4663 事件**（只出现了一条指向 `lsass.exe` 的记录）。
- `icacls /audit` 不被支持：四种写法全部 rc=87「无效参数"/audit"」。根因从权限侧得到佐证：`whoami /priv` 显示 **`SeSecurityPrivilege`（管理审核和安全日志）已禁用**——写 SACL 需要这个特权。
- 现成的 Mimosa 台账（`.mimosa/hook-status/*.json`，5 份）字段为 `{sessionId, event:PostToolUse, toolName:Edit|Write, file, outcome, coverage, findingCount}`——**全部是写事件，零条读事件**。

**结论与替代**：本机拿不到「谁读过 holdout」的 OS 级读审计。可落地的替代是**三件套**：
1. **harness 侧读台账**：唯一的合法读者是 harness，它每次读 holdout 实例都追加一行 `{ts, actor, task_id, nonce, file, sha256}`；台账本身 hash 链防篡改（见 RC-9）。
2. **canary 绊线**：每个 holdout 实例内放一个**不参与判分**的 `canary.txt`，内容是本次 nonce 的高熵串；台账 + 转录扫描之外，再加一条「canary 串出现在任何非 harness 路径 ⇒ 红」。
3. **泄漏即证据**：一旦扫描器在转录里命中 holdout 片段，**不需要先证明「谁读的」**——污染事故本身按 EVAL-SPEC §4.3-3 直接作废两臂并留档。审计的缺失不影响止损，只影响事后归因。

**被否决的分支**：
- (a)「把 `icacls /audit` 写进 holdout 建仓步骤」→ **否决（本机不可用，rc=87）**。若 owner 愿意 `whoami /priv /enable:SeSecurityPrivilege` + 改全局审计策略（需重启、需改机器级配置），这是**升级位**不是本期项，写进 PLAN 要标为「需 owner 决断 + 机器级变更」。
- (b)「复用 Mimosa 台账做访问审计」→ **否决**（只记写不记读，见实测）。

### RC-4 · 转录扫描器的查全率必须用「污染注入实验」实测，且必须先声明威胁模型

**注入实验（§3.4）**：取 `dist/meeting-minutes-skill/SKILL.md` 的一段 981 字节真实资产正文作「泄漏源」，构造 9 种变体（verbatim / 单行 / 打乱行序 / 截断加省略号 / 重排版式 / JSON 转义 / 单个实体值 / 同义改写 / base64），用 3 种扫描策略（40 字符 shingle 计数、8-gram 命中率、中文词级 token 重叠）测，**再在 6 个负样本语料**（同域另一资产 SKILL.md、另一资产 contract.md、41 门轮的全部 28 份 stdout、scorecard.md、EVAL-SPEC 散文、同一文件的其他章节）上测误报。

结果（[A]，完整表见 §3.4）：
- 负样本 8-gram 命中数区间 **4–45**（最大来自同域 hot-templates package SKILL.md = 45）；正样本 verbatim = **836**。
- 改写样本 token 重叠 **0.990**；8-gram 命中率 0.763。
- **单行泄漏 8-gram 命中仅 10**；**单个实体值泄漏 = 0**；**base64 泄漏 = 0（三策略全灭）**。

**三条推论**：
1. **「零命中」不是合格证据。** 任何 PR/阶段门报「转录扫描零命中」时，必须同时报「本轮注入实验的逐类召回」与「语料 id + 语料版本」。否则这条门在逻辑上无法区分「没泄漏」和「扫描器瞎了」。
2. **自动作废线只能设在高置信区。** 由数据反推：`sh8_hits ≥ 60` 时，6 个负样本全部零误报（最大 45），且 6/9 变体（含全部打乱/截断/JSON 转义/改写）被判红；`sh8_hits ∈ [20,59]` 是**分诊带**（hot-templates 落在这里），只报「疑似」交人判，**不自动作废**。
3. **三类逃逸必须写进「不在本门覆盖范围」的显式声明**：行级碎片泄漏、单个 nonce/实体值泄漏、编码（base64/hex）泄漏。前两类靠 nonce 过期与「holdout 不在 dev 工作树」兜底，第三类需要扫描器**增加一步「可疑高熵串解码后再扫」**——这是**新增需求**，PLAN §3.5 没写。

**被否决的分支**：
- (a)「沿用 `peidian-agent/scripts/ci_isolation.py` 的字面量正则模式（`PARK-002|TARIFF-2026B|OP-1[0-9]`，:31）」→ **否决**。它对本厂 holdout 的查全率在 V2/V7/V9 三类上是 0；而且我们的泄漏源是**长中文正文**而不是几个 ID，正则根本不是合适的匹配单位。可继承的只有它的**形态**：固定退出码（0/1）、逐命中 `file:line: matched` 报告、扫描目录白名单（:34-45）、「全部文件按文本读，不按后缀过滤」（:50 的注释与实现 :85）。
- (b)「用向量/embedding 相似度做泄漏检测」→ **否决（本期）**：本机 3 个普通模型走 zcode/kimi 通道，把**每轮全量转录**送去做嵌入比对，成本与不确定性都高，且引入模型自身漂移。8-gram + token 重叠两级已经能覆盖 6/9 变体且零误报。
- (c)「扫描对象只限转录」→ **否决**。必须同时扫三处：转录（模型读到了什么）、**臂产物**（模型写出了什么）、**资产树 + git 历史**（开发者是否把答案塞进资产，见 RC-6/C8）。只扫转录会漏掉「资产里预置答案、模型照着写」这条最典型的作弊路径。

### RC-5 · 扫描器必须是两段式（自动作废带 + 人工分诊带），单阈值被实测否掉

见上条推论 2 的数据。补充一个设计后果：**分诊带里的命中必须留下处置记录**（命中位置 / 判为污染或误报 / 判定人 / 时间），并按月统计误报率——因为误报率升高本身就是「扫描器过敏了」或「资产正文与 holdout 语料越走越像」的信号，两者都要处置。仓库里已有同向纪律先例：v5 那一轮 3 个 FAIL 门全部被诊断为「本台账自设口径过严/对比口径问题」而非资产缺陷（scorecard.md:76-86）——**门的误报是要归因、要记账的**。

### RC-6 · 「资产里塞答案」的三条封堵测试（这三条 PLAN 里没有，是本镜头的主要增量）

一个能接触 dev 题集的开发 agent 想让资产在 holdout 上好看，最省力的做法不是改进资产，而是**把 holdout 的规律写进资产**。PLAN §3.5 的三件套（nonce / 隔离 / 断网）防的是「**读题**」，防不住「**背题**」和「**特判**」。需要补三条测试：

1. **反向扫描（拦「背题」）**：用与 RC-4 同一套 shingle 策略，**把 holdout 实例正文当作模式，去扫资产树与 git 历史**。判据 = 命中数 ≥ 自动作废线。对应作弊路径 C1/C3/C8。仓库先例是同构的 `ci_isolation.py`（它扫的是开发仓库对 holdout ID 的零命中，方向相反、机制相同）。
2. **反事实 nonce 复跑（拦「特判」）**：同一题面、**新 nonce**，A_new 必须仍然过。资产是「做对方法的」，两个 nonce 都过；资产是「特判这张表的」，只有一个 nonce 过。这是把「增益真实性」从统计推断变成**成对反事实**的最便宜手段，成本 = 1 个 canary 子集（3 题 × 2 nonce × 1 族 × n=1 = 6 臂），可以进 smoke 层。**PLAN §3.4 的 smoke 行（3 题/1 臂/n=1）目前没有第二个 nonce，建议加一列。**
3. **泛化比门（拦「只在 holdout 好看」）**：断言 `Δ_holdout / Δ_dev` 落在带内。两臂都远大于 0 时比率才有意义；**若 `Δ_dev ≤ 0` 则本门判「不可判」而不是「通过」**——否则会出现「dev 上没增益、holdout 上有增益 = 纯背题」这种最坏情况被判绿。这条同时解决 PLAN 缺的那个洞：四信号里的 S2（边际 Δ）如果只在 holdout 上算，资产作者就会用 holdout 反复迭代（违反「只报不调」），所以**边际 Δ 必须在 dev 上算，holdout 只报比率**。

**被否决的分支**：
- (a)「靠 holdout 分数低来判断是否作弊」→ **否决**。低分与作弊无关（可能就是资产差），高分也不证明没作弊（可能就是题太简单）。必须用**跨 nonce / 跨 split 的一致性**作判据。
- (b)「只在里程碑跑一次反事实 nonce」→ **否决（成本理由不成立）**。6 臂的成本远低于一次 25 题 full 轮（300 臂），放 smoke 层每轮跑才对。

### RC-8 · 轮换、去饱和与泄露应急：三组测试

**去饱和/退役的测试**（PLAN §3.7/§3.8 给了规则，没给测试）：
- T-HO-18 **退役流水线正向**：构造一个 treatment 5/5 的任务 → 跑退役流程 → 断言它从迭代池**和 holdout 池**同时移出（PLAN §3.7 只说移出迭代池；**holdout 保留饱和题是错的**——holdout 也要分辨力，饱和题留在 holdout 等于白烧 10 题里的 1 题）、并写入 CHANGELOG `removed` 且带饱和证据（PLAN §3.8 的三类 CHANGELOG）。
- T-HO-19 **退役流水线反向（防过度退役）**：构造 treatment 60% 的任务 → 断言**不**退役。没有反向测试的退役流程，三个月后 holdout 会空到只剩 3 题。
- T-HO-20 **通胀计数器连续性**：PLAN §3.8 的 N:M=4:1（标了 [假设]）→ 断言「上一轮新增 N、退役 M，N−M 的累计值 ≤ 0 才允许开工下一轮」。这是一条纯计数器断言，防的是「只加不退」这个最常见的 bench 通胀模式。

**泄露应急的测试**（PLAN §3.4 只写了「命中即该题两臂作废」）：
- T-HO-21 **应急演练门**：每个里程碑至少演练一次「发现污染 → 作废 → 换 nonce → 留痕 → 重跑」全链，产物形态对齐 `classroom/rehearsal/round-1/record.md`（逐步 PASS 行 + 缺陷清单 + 红线核查节）。演练的判定不是「演练做了」，而是**演练过程中真的产生了一次作废**（用注入语料），并证明作废后重跑的那一轮**没有被同一段污染文本再次命中**。
- T-HO-22 **应急时限**：作废发生后，同一 nonce **不得**在任何后续轮次被复用（生成器自检：nonce 集合单调不复用；这需要生成器把用过的 nonce 落盘成一个 append-only 账）。

**被否决的分支**：
- (a)「退役与轮换交给人按流程走，不做测试」→ **否决**。这是本仓被证明最不可靠的一环：`record.md:42` 的 D3 事故（学员原地跑生成器清空参照区）就是纯流程失效；纯流程必须配机器断言。
- (b)「holdout 题永不退役（保持不可变）」→ **否决**。holdout 也是尺子，尺子会饱和（PLAN §3.7 自己写了「treatment 打满是该加题了」）。**不可变的是 nonce 账本与已发布数字，不是题目集合。**

### RC-9 · 里程碑验收：把散文拆成四类门（确定性 / holdout / 人工 / 不可判）

**先记一个我在通读时发现的内部不一致**（[A] 读 PLAN.md:188 与 :460）：
- §3.4 分层规模表写 dev = 8 题 × **3 臂** × n=2 × 1–2 族 = **48–96 runs**（该行自洽：25×2×3×2=300、10×2×3×2=120 都对得上）；

两者相差一整臂（A_old）。**对验收测试来说这不是笔误问题**：三臂是主指标 `delta_vs_prev` 的唯一来源（PLAN §3.2），用 2 臂跑 WS4 会让阶段一交付的 dev 轮天然产不出主指标。建议在测试规格里把它钉成「WS4 = 3 臂」，并把这个不一致回抛给规划作者/owner。

**门矩阵（每行 = 一条可执行断言）**：

**三条通用规则（从仓库先例抄来的，不是新发明）**：
1. **顺序：红路先跑。** TASK.md:46「G0-2 红路 → G0-1 评测 → G0-3 三齐 → K-3 彩排 → K-5 人工批准」。⇒ 里程碑 runner 必须**先跑全部红路断言，任一红即中止**，不允许「先跑完再解释」。
2. **人工门只签「事实陈述」，不签「机器可判的量」。** K-5 的产物形态是「批准记录」（`evidence/publish-approval-REQUEST.md:3` 明写「本文件是申请，**不是批准**…任何 agent 不得代签」）。⇒ 测试规格里人工门的证据字段是 `{签署人, 日期, 被签对象的 sha256}`，**没有 `passed: true` 这个字段**。
3. **不信任自报**（TASK.md:70 S-验收角色「不信任自报；与执行不同会话」）。⇒ 每条门行的证据必须自带 `{command, exit_code, ts, evidence_sha256}`，**缺任一字段的门行由 runner 直接判红**（schema 级断言，MT-5）。这一条是整张表最便宜、收益最高的机器门。

**被否决的分支**：
- (a)「里程碑验收 = 跑一遍所有门拿百分比」→ **否决**。v5 的 scorecard 已经演示了失败模式：41 门里 3 个 FAIL 全部是台账自己的口径问题（scorecard.md:76-86），如果只报「38/41 通过」，就会把「尺子坏了」读成「资产还行」。**门的失败必须先归因再聚合**，聚合口径写进 runner 输出。
- (b)「M1 也要跑一次 holdout 以证明机制可用」→ **部分否决**。M1 可以跑 holdout **机制**（目录隔离、扫描器、nonce 生成器），但**不得报 holdout 分数**（n 与题数都不够，且一旦有分数就会有人拿去调）。区分「机制门」与「分数门」是 M1 阶段的关键纪律。
- (c)「三阶段的门可以合并成一张总表」→ **否决**。阶段门的作用是「这一阶段能对外声称什么」；合并会诱导用 dev 数字支撑阶段二的对外声明。

### RC-10 · 「迭代到合成极限」四信号的机器判定：四个不可判定点 + 四个必须补的门

PLAN §3.7 给了四信号表（S1 饱和 / S2 边际 / S3 反向 / S4 题面可信）。我认为它**不能直接机判**，有四个具体断点：

1. **S2 的分母会为零。** 定义是「`delta_vs_prev` 相对变化连续 3 轮 ≤0.10」——当上一轮 Δ≈0 时比率无定义/爆炸（Δ 从 0.02 → 0.015，绝对变化 0.005 是可忽略的噪声，比率却是 0.75，判「未收敛」）。**必须加绝对下限带**：`|·| ≤ max(0.10·|Δ_old|, ε_abs)`。这是判据设计问题，但**测试要能证明它不炸**：T-MT-01 喂入含零分母的合成序列，断言输出是「收敛」或「不可判」，**绝不允许异常/静默通过**。
2. **S2/S1 的轮次必须同装置同题库。** EVAL-SPEC §4.4-2 与 §5.2 都写死「装置/题变更 ⇒ 版本 bump、跨版本禁止比较」。⇒ **PLAN §3.7 缺一条：四信号表的每一轮必须带 `evalbench_version` + `golden_version` + `model_set`；机判时若相邻轮版本不同，判定必须是 `不可判(装置变更)`，而不是「极限到达」。** 这是一条真实的、会造成误判的缺口。
3. **S1 依赖「最新一代模型」，而模型集本身在变。** O-5 决定四族全上，且矩阵会「补列」。⇒ 每轮必须钉住参与饱和判定的模型集合（PIN.md §5.1 的 model_pin 五元组），模型集变化时 S1 必须**重新计算**而非沿用。
4. **S4 的缺值必须 fail-closed。** 「题面缺陷率 ≤10%」在**没抽审**时是「无数据」，不是 0%。⇒ 机判必须把 `S4 = null` 判成「不许切 + 原因：S4 未采审」。同样的 fail-closed 要套到 S1（饱和题清单缺失）上。

**留痕（防事后改判据）**：每轮四信号记录落一份 append-only 记录，**含上一份记录的 sha256**（hash 链）。T-MT-03：篡改任一历史记录 ⇒ 链校验失败 ⇒ 阶段门红。这是对 C10（丢弃难看的轮次）的机器封堵，且成本为零。

**被否决的分支**：
- (a)「让一个 LLM 读四信号表给出『到了极限吗』」→ **否决**。它会把缺值当通过（裁判最常见的失败模式），且引入模型漂移。四信号是**计数与布尔**，必须机判；LLM 只允许在「题面缺陷归因」这一处做辅助（PLAN §3.6 已把归因分三分类，其中「题面问题」子类需要人过）。
- (b)「先不定阈值，等有数据再固化」→ **部分采纳，但必须先写死形式**。S2 的 0.10/3 轮与难度带 60–90% 都是 [假设]（PLAN 自己标了）。测试规格里可以**把阈值做成配置项**（`thresholds.toml`），但**判定的形状与 fail-closed 行为必须现在就写死**——否则首两轮的数据会被「顺手改一下阈值」消化掉，这正是 C9/C12 两条作弊路径的入口。

| MT-6 | **反证探针（falsification probe）**：每批次随机挑 1 门，把 `expected` 改错跑一次，确认它红，然后改回 | 永真门 / 门失效 | 极低（≈ 一次门运行） |

MT-6 是我认为性价比最高的一条：**它不需要任何新设施，只需要「允许自己红一次」的纪律**，而它恰好能抓住所有「写成了永真」的门（最高频的退化）。

**关于「对拍要对拍」的无限回归**：WS3 的 checker 对拍（EVAL-SPEC §6.4-1 ≥95%，REGISTRY L32/L35 已把它列为欠账）要小心递归。**明确裁决：元测试只做一层**——判分器对人工金标（元），不再对「对拍程序」本身做对拍（超元）。更上一层的保证由 MT-4 变异测试承担（它测的是「判分器能不能抓住错的 ground truth」，比再套一层对拍更直接）。

**被否决的分支**：
- (a)「给测试代码本身设覆盖率门槛（如 ≥80%）」→ **否决**。本仓没有覆盖率工具链，且行覆盖率对这类「门禁脚本」几乎无意义（脚本多为胶水，测的是**它是否被正确地触发**而不是行是否被执行）。**替代指标：变异杀死率（killed/planned）+ survivor 数**。这条选择我给了明确的否决理由，不是「不重要」。
- (b)「让被测 agent 自己写自己的验收测试」→ **否决**。TASK.md:69 已经写死 S-执行「不自评达标；不改评测器与阈值」——**写验收测试的人必须在执行之外**。测试规格里应显式写「验收测试的作者 ≠ 资产的作者」，否则整套 holdout 纪律会被一个人的自利视角穿透。

### RC-12 · 测试代码的覆盖率纪律（三条，端口自门 5）

EVAL-SPEC §7.1 门 5「断言复审门：无恒过/恒败/双臂同过断言」是仓内唯一现成的测试代码纪律，直接移植：

## 4. 倾向性结论（每条带置信度）

1. **本机上 holdout 的 DACL 不是保密边界**：同一账号持 SeBackupPrivilege，`robocopy /B` 可直接拷出 deny 目录内容（实测）。holdout 纪律的正确表述是「构造不可达 + nonce 过期 + 扫描可检测」，权限位降级为**绊线**。**置信度：高**（三步实测闭环）。
2. **任何「设置 X 之后」的验收门，判据必须是行为断言不是命令 rc**：`icacls /deny` 返回 5 但生效；`takeown`/`/reset` 返回 0 且成功撤销。**置信度：高**。
3. **本机拿不到 holdout 读审计**：`icacls /audit` 不存在（rc=87）、SeSecurityPrivilege 禁用、4663 不指向我们的 canary、Mimosa 台账只记写不记读。替代方案 = harness 读台账 + canary 绊线 + 泄漏即证据。**置信度：高**（四条独立证据）。
4. **「扫描器零命中」不构成合格证据**：查全率必须用版本化注入语料实测。仓内两个现存字面量门（`ci_isolation.py:31`、`acceptor-agent/runner.py:113`）对改写的查全率为 0（后者实测 0/5）。**置信度：高**。
5. **自动作废线建议设在 8-gram 命中 ≥60，分诊带 [20,59]**：6 个负样本最大命中 45（零误报），6/9 注入变体可判红；行级碎片/单实体/base64 三类逃逸必须在规格里显式声明为「不在自动门覆盖内」。**置信度：中**（负样本只有 6 个、都是本仓文档语料，真实转录语料分布可能不同；首两轮必须用真实语料重标定）。
6. **PLAN §3.5 的三件套防「读题」不防「背题」与「特判」**，需补三条测试：资产反向扫描（含 git 历史）、反事实 nonce 复跑（建议进 smoke 层）、holdout/dev 泛化比门。**置信度：高**（推理 + 反作弊路径枚举完整；未实跑，因 harness 不存在）。

## 6. 给测试撰写者（GLM-5.3）的具体建议

1. **先写「威胁模型」再写测试。** 建议在测试规格开头放一张表：本门覆盖哪几类泄漏/作弊、**明确不覆盖哪几类**、不覆盖的由什么机制兜底。我的实测结论是：行级碎片泄漏、单实体/单 nonce 泄漏、base64/hex 编码泄漏这三类**超出字面量+shingle 自动门的覆盖**，不写清楚就等于默认覆盖。
2. **每个门行强制五字段**：`{id, kind: deterministic|holdout|human|unjudgeable, command, expected, evidence:{exit_code, ts, sha256}}`。缺字段由 runner 判红（MT-5）。这直接继承 TASK.md:70 的「不信任自报」。
3. **门矩阵按 §2 RC-9 的四类分栏写，并抄三条仓内先例**：顺序红路先跑（TASK.md:46）；人工门证据只有 `{签署人, 日期, 被签对象 sha256}`、**没有 `passed` 字段**（publish-approval-REQUEST.md:3）；阶段失败必须先归因再聚合（scorecard.md:76-86 的 3/3 范式）。
4. **把 §3.4 的实测表直接搬进规格作为「查全率基线」**，并要求每次扫描器或语料变更后**重算这张表**。同时把「6 个负样本语料的 id + sha256」钉进规格——否则「零误报」不可复核。
5. **写一条明确的「假红防护」条款**：所有涉及系统状态设置的门（ACL、环境变量、策略），判据是设置后的行为探针，不是命令 rc（依据 §3.1 的 rc=5 事件）。
6. **把反事实 nonce 复跑（RC-6.2）放 smoke 层**，并建议在 PLAN §3.4 的 smoke 行加一列 nonce。这是本镜头对规划的**主要增量建议**（PLAN 目前 smoke 只有单 nonce），价值在于把「增益真实性」从事后统计推断变成成对反事实。
7. **补三条 PLAN 没有的防作弊测试**：资产反向扫描含 **git 历史**（C8）、holdout/dev 泛化比门（C10 类）、「只报不调」的静态检查（C13）。其中 C13 的实现最简单：扫描迭代记录文本，检查是否引用了 holdout 指标。
8. **四信号的机判规格**：阈值放 `thresholds.toml`（可调），但**形状写死**——缺值 fail-closed、跨 evalbench 版本判 `不可判(装置变更)`、S2 带绝对下限带、S1 绑定当轮 model_set；每轮记录进 hash 链。配套 MT-1 用合成序列测零分母与版本跳变。
9. **元测试只做一层**（RC-11 的裁决）：判分器对人工金标，不再对「对拍程序」对拍；更上一层由变异测试承担。把这条写进规格，避免实施时无限递归。
10. **覆盖率纪律写三条**（端口门 5）：无恒过（每条门要写 `kills:` 与注入样本编号）、无恒败（红门要归因）、无双臂同过（bench 语境下的恒过 check 同样吃判分权重，轨迹3 A13 的 15.7% 是同族证据）。**不要引入行覆盖率门槛**——若 owner 坚持，作为独立决断项，不要默默塞进规格。
11. **落盘纪律照抄本仓 Windows 事故教训**（PLAN R-7 / BASELINE §7-1, §7-4）：测试产物一律 Python 显式 `encoding='utf-8', newline='\n'`；命令输出解码显式（本机中文 Windows 是 cp936，我第一次跑 `icacls` 就是被 UTF-8 解码炸的）；禁止 shell 重定向；Mimosa hook 会对写操作拦截（我本会话用 heredoc 写 `/tmp` 脚本被拦，改用 stdin heredoc 通过）。
12. **最后一条，也是我最想让你保留的一条**：把「验收测试的作者 ≠ 资产的作者 ≠ 裁判的作者」写成规格首条纪律。整套 holdout 体系的有效性最终取决于**没有一个人同时握有出题、调参、判分、验收四把钥匙**；仓内已有先例（TASK.md:69-74 的角色禁止列），把它延伸成测试侧的硬约束，是所有其它测试能否被信任的前提。
