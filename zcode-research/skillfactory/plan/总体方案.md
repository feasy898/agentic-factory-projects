## 一、执行摘要

**我们做什么。** skillfactory 是一条把 AI 能力封装为「可分发、可验证、可复用」技能资产的工厂。每个资产 = 一个符合 agentskills.io 开放标准的 skill 包（该标准已被 Claude/Codex/Cursor/Gemini CLI/TRAE 等 40+ 客户端采纳，格式壁垒当前不存在——侦察发现③；我方格式即 `SKILL-SPEC-v0.1.md`，自有扩展全部收进 `metadata`，SPEC §1.2）+ 一份可复跑的评测包（`eval/`）+ 一份体检报告。一次编写、多平台上架。

**护城河是什么。** skill 的价值主张是「对普通模型的增益」，而增益只有通过 with_skill / without_skill 同题对照才能被证明。四家被逆向的厂商（豆包/Qoder/Kimi/千问）都只做了格式与分发，**没有一家建立技能质量度量**（侦察发现② implications：触发命中率/正文密度/脚本实测覆盖四家全空白）；官方评测 SOP 与学术基准（SkillsBench，arXiv:2602.12670：87 任务×8 域×18 配置，no-skill 33.9%→curated-skill 50.5%，侦察发现③）提供了方法，但没有人把它做成消费者可见的凭证。我们把 SPEC §4 的五门验收线（确定性 exit 0｜盲评 Δ≥1.0 且胜率≥60%｜效率 token/耗时比率 ≤2.0 一票否决｜形式门｜断言复审门）做成每资产标配。**首批实测证明这条线有牙齿：4 进 1 出**——

- **meeting-minutes（会议纪要三段式）：接受为资产**。确定性评测通过，盲评 Δ=4.33（线为 ≥1.0）、胜率 1.0（线为 ≥0.60）——**全部对局获胜**，是「聚焦单能 skill + 确定性 oracle」增益画像的最强内部实证；
- **monthly-report-ppt（月度汇报生成器）：返工**。未通过确定性评测（任务下发口径），不进盲评；
- **ppt-method-router（PPT 方法意图路由）：拒**。确定性通过（路由机判与 oracle 一致率 20/20=100%，本会话实读 `_report_check/eval_ppt-method-router.json`），但盲评 Δ=0、胜率 0.33——**路由全对，端到端零增益**；
- **paper-to-skill（知识蒸馏器）：拒**。确定性通过，但盲评 Δ=−0.5、胜率 0——**挂上技能反而全线更差**，是「有 skill ≠ 更好」的最狠内部实证。

拒绝率 75% 不是坏消息：它证明「过验收」三个字有含金量；且四个数字（全胜/返工/零增益/负增益）恰好构成「为什么必须做对照评测」的完整内部证据链——这是所有竞争者（包括厂商官方库）都不拥有的东西。

**窗口期。** 当前所有 skill 分发平台全部免费、零分成：WorkBuddy 开放平台 2026-09-02 上线、Qoder 市场、TRAE、anthropics/skills 插件市场、MCP Registry 均无任何收费/分成证据（侦察发现④，逐家核实）；平台内卖 skill 零证据。行业处在「圈量期」——低成本铺量建立影响力的 6–12 个月窗口。动作：过验收资产全部免费上架（国内 WorkBuddy 第一优先），**每个 skill 附体检报告**——直接回应 ClawHub 恶意 skill 事件（约 15% 恶意感染率）之后「可审计的干净 skill 本身是卖点」的市场情绪（侦察发现④）。

**现状一页账（2026-09-29，本会话逐项实查核实；核查命令与结果见附录）。**
- 资产：首批 4 包实测，**接受 1 个**（meeting-minutes，Δ=4.33/胜率 1.0）；3 个被拒且拒因明确、返工路径清晰（§3.2）。
- 工程欠账（本会话实查）：① 四包 `SKILL.md` 均在 `package/` 子目录而非包根（SPEC §1.1 要求包根；逐包 `ls` 确认）；② 四包 `eval/` 内均无 `protocol.md` 与 `results/`，全部 skillfactory 内无任何 `benchmark.json` 落盘件（`find` 空结果）——SPEC §1.1 必选/§4 要求验收记录落盘；③ monthly-report-ppt 与 ppt-method-router 的 front-matter 仅 name+description（逐包提取确认），按形式门缺 version/license/permissions/metadata；meeting-minutes 与 paper-to-skill 六字段齐；④ `CHANGELOG.md` 仅 meeting-minutes 一包在位（`find` 确认），其余三包缺 SPEC §1.1 必选项；⑤ golden.json 为旧 schema（meeting-minutes 头部实读：`eval_inputs` 条目用 `case/input/output` 键，缺 SPEC §3.2 规定的 `id/type/prompt/checks`）；⑥ **monthly-report-ppt 存在一处待复裁张力**：本会话实读 `_report_check/eval_monthly-report-ppt.json`（2026-09-29 06:45 落盘）显示其 16 项确定性检查全部通过，而任务下发口径为 evalPassed=false——两者评测环境/口径可能有差，D0–30 需复现官方评测后裁决，**裁决前以任务下发口径为准**。
- 标准：SKILL-SPEC v0.1 定稿生效；黄金集版本化归档已有实践（`assets/meeting-minutes/eval/archive/` 实查存 golden-v1.0/golden-v1.1 两版）。
- 情报库：豆包 106 包全量解压+front-matter 盘点（`library/doubao/CATALOG.md` 220 行在位、`_analysis/fm.json` 95KB）、Qoder/Kimi/千问逆向报告（`library/qoder-kimi-qianwen.md` 196 行）入库（本会话实查在位）。
- 缺口：`build.py` 渠道变体生成器未建（SPEC §1.5.2 只有规则没有实现，`find` 无 build.py）；上架数 0、课程 0、bench 尚未做到双模型矩阵，首轮盲评未出 token/耗时比率数据。
- **90 天目标**：过五门验收资产 ≥10（净新增 ≥9，基线 1）、上架渠道 ≥4 且在架件次 ≥12、试点课程 2 门、体检报告覆盖 100%、自有「普通模型+skill」增益榜完成首轮双模型全量回归。

## 二、技能生产体系：三源管线

### 2.1 总览：三源汇入一条验收线

```
S1 开源生态借鉴提升 ──┐                       ┌→ 评测五门（SPEC §4）──→ assets/ 入库
S2 论文/书籍/PDF 蒸馏 ─┼→ 统一加工（SPEC §1 格式）┤
S3 厂商搬运+意图路由融合┘                       └→ 不合格 → 返工/迭代（monthly-report-ppt、
                                                   ppt-method-router、paper-to-skill 三个在案先例）
```

三源按「供给内容」分工，**不按难度或优先级分工**——任何来源的产物都必须通过同一条五门验收线才算资产（SPEC §0.2 第 4 条：无评测记录的 SKILL.md 是草稿，禁止进入分发管线）。首批 4 包 3 个被拒，恰是这条纪律的第一次真实执行。

| 源 | 供给什么 | 内容杠杆（证据） | 首批实例 |
|---|---|---|---|
| S1 开源生态借鉴提升 | 已被工程验证的方法与结构模式 | anthropics/skills（178.8k★，19 个官方技能，其中 docx/pdf/pptx/xlsx 四件套为 source-available 非开源）、VoltAgent/awesome-agent-skills（badge 1497+ 技能）、obra/superpowers（292.4k★，「强制工作流，不是建议」）、K-Dense（166 科学技能）——侦察发现③ | meeting-minutes（**通过，Δ=4.33/胜率 1.0**） |
| S2 论文/书籍/PDF 蒸馏 | 领域程序性知识（人向文档中的 know-how） | Repo-To-Skill（arXiv:2609.02749：1000 个 ML 仓库→5000+ 已验证技能，MLE-bench +134.3%）、K-Dense 每工具一技能范式——侦察发现③ | paper-to-skill（蒸馏器本身，**盲评 Δ=−0.5/胜率 0 全败，迭代中**） |

### 2.2 S1 开源生态借鉴提升管线 SOP

**来源。** 三个筛选池：anthropics/skills 官方仓（注意四件套 source-available——只学方法不复制代码，侦察发现③）；awesome-agent-skills 精选集（badge 1497+，含 Microsoft 133 个、Trail of Bits 安全套件）；obra/superpowers（多 harness 适配的工作流方法论）。选材标准：资产链活跃、许可明确（Apache-2.0/MIT）优先。

**加工。** 三步，核心纪律是「借鉴方法、重写实现」：
1. **结构移植**：官方六模板（gotchas 节、输出模板、多步 checklist、validation loop、plan-validate-execute、重复逻辑入 scripts/，侦察发现③ best-practices 实读）直接映射到 SPEC 附录 A 骨架（`SKILL-SPEC-v0.1.md:312-352`）。
2. **本土化重写**：description 三段式触发设计（能力段/触发段含 ≥3 个中文口语短语/边界段互相导流——SPEC §1.3，源自豆包 106 包最一致的成熟经验，侦察发现①）；正文压进 ≤500 行且 ≤10,000 字符（SPEC §1.4）；补上厂商验证过的可靠性条款（MUST RELOAD、写后回读三态、验收矩阵、脚本门卫——SPEC §2.2，条款出处见 SPEC 附录 C 的 path:line 证据索引）。
3. **增益注入**：superpowers 的启示是「强制工作流，不是建议」——把开源项目 README 里「建议」性的最佳实践改写为可机判的显式判据（如「校验不过禁止交付」）。这是从「借鉴」到「提升」的关键一步。首批通过的 meeting-minutes 即此模式：条目逐字引用原句+条数统计对账（`_report_check/eval_meeting-minutes.json` 的 20 项确定性检查含 `no_fabricated_entries` 逐字溯源判定），确定性可证才带来 Δ=4.33 的硬增益。

**质检。** 五门验收 + 断言复审（SPEC §4）；S1 额外自查：与上游的差异必须在 CHANGELOG 写明「借鉴了什么结构、改了什么、为什么」。

**入库。** `assets/<name>/` + 在 `library/` 相应来源的 CATALOG 索引登记（沿用 `library/doubao/CATALOG.md` 五列格式：名称/版本/一句话能力/结构特征/写法借鉴）。

### 2.3 S2 论文/书籍/PDF 蒸馏管线 SOP

**来源。** 两类：① 方法论文与官方文档（Repo-To-Skill 已验证「操作知识层」蒸馏路线可行，且规模越大越要检索式按需加载，侦察发现③）；② 领域权威公开物（官方 best-practices 结论：项目特定素材完胜通用最佳实践文章，纯靠 LLM 通用知识只会得到「handle errors appropriately」式空话——侦察发现③ 4.1 节）。选源排产看蒸馏语料库台账（§6 第 8 项），按「领域 × 能力族」矩阵挑高价值格子。

**加工（五步）。**
1. **选源登记**：metadata 三键必填（source / source-url / distilled-at，SPEC §5.1 第 1 条）。
2. **抽取边界**：只抽方法、流程、事实与结构；禁止复制受版权保护的表达（我方红线，与「禁整段复制官方文案」一致）；关键步骤可回溯到章节/页码；来源没有的补全必须标 `[补充]` 并附独立依据（SPEC §5.1 第 2–3 条）。
3. **结构分层**：薄入口 + references 按章节/方法分层；gotchas 节必备（来源明示的坑 + 蒸馏验证中实测踩到的坑，SPEC §5.1 第 5 条）。
4. **初稿生产**：计划由 paper-to-skill 资产承担初稿、人做忠实性复核（产线自己生产自己）。**诚实标注：该杠杆当前不可用**——paper-to-skill 首版盲评 Δ=−0.5、胜率 0（全部对局皆负），被盲评门拒绝，正在迭代；在它过线之前，S2 初稿由「人 + SPEC 附录 A 骨架 + oracle 配方」承担，蒸馏器作为并行迭代项而非依赖项。
5. **反空话终检**：每条指令必须携带来源中的具体细节（参数、阈值、顺序、坑），出现空话条款即打回（SPEC §5.1 第 4 条）。

**质检。** 五门之外，蒸馏产物增加两条专项：忠实性抽检（随机 5 条关键步骤对照来源位置复核）+ 数值断言内联来源检查（SPEC §3.2 schema 原生支持 `numeric_claim_has_source` check）。**S2 增加一条从首批教训来的规则：蒸馏产物必须过「误导检查」**——paper-to-skill 的全败（Δ=−0.5）与学术结论同构（arXiv:2608.11888：技能致害最大类是 Task-Implementation Fault 68.8%，即「相关但误导的流程」），蒸馏内容若把人向文档的表达误当成 agent 可执行流程，就会系统性拉低表现，归因裁决见 §3.6。

**入库。** 按「领域 × 能力族」组织层级库（对标 Repo-To-Skill 的 AREX-Skill Library：20 领域 × 178 能力族，侦察发现③）；分发侧一律检索式按需加载，**绝不做全量常驻注入**——Signal or Noise（arXiv:2608.23067）实测把技能文件注入每个 coding prompt 通常让 agent 更差（侦察发现③；该结论已被 paper-to-skill 在我方资产上复现）。

### 2.4 S3 厂商 skill 搬运融合管线 SOP

**来源。** 已入库的逆向情报：豆包 106 包（CATALOG.md 总览统计实读在位：name/description 106/106、version 仅 24/106、license 仅 9/106、evals 仅 5 包、description 中位数 182 字最长 976 字、正文最短 363 字最长 51,056 字、3 包带完整 .git）、Qoder 11 包、Kimi 7 包、千问 Skill 运行时（buildSkill 字段集逐字段复刻 Claude Code，侦察发现①②）。这个库是**写法规律矿**，不是素材库。

**搬运边界（红线）。** 只搬方法与规律，禁止把官方文案整段复制进我方产物（雇主纪律；SPEC §5.1 第 2 条同款；CATALOG.md 头部亦声明「一句话能力为压缩转述，非原文整段复制」）。具体做法：把 106 包提炼的规律**转化为生成器规则与检查单**——description 三段式、文档地图表、MUST RELOAD、写后回读三态、验收矩阵、脚本门卫、降级链、环境判定、agents interface yaml（display_name/short_description/default_prompt，豆包 20 包先例）、evals 结构化断言（wealth-planning 的 route_to/must_include/must_not_include）——这些已全部落进 SPEC §1–§2 条款（出处见 SPEC 附录 C）。S3 的「加工」因此大部分是**配置化生成而非手写**，这是三源中边际成本最低的一源。

**融合。** intent-router 大 skill 见 §2.6。

**质检。** 五门 + 融合专项（SPEC §5.2 第 5 条）：每个方法 ≥1 正例 + 1 近邻负例（route_to 断言到方法粒度）、≥1 条跨方法 ab_task（验证移交协议）、每个方法 ≥1 条 ab_task 度量端到端产物质量（首批教训，见 §2.6）。

**入库。** 同一条线；融合包与其子 skill 在 CATALOG 中互相登记 route-to。

### 2.5 产能模型

**单位与口径。** 产能按「过五门验收的资产数/周」计，不按写作数计——首批实测是活教材：4 个写了的包，只有 1 个过了（monthly-report-ppt 确定性未过、ppt-method-router 路由对了但端到端零增益 Δ=0、paper-to-skill 蒸馏产物反而全线更差 Δ=−0.5）。写了不算，过了才算。

**复用杠杆（六条，按当前可用性排序）。**
1. **eval runner 框架复用**：首批 4 包的 `eval/runner.py + golden.json` 已同构（本会话逐包 ls 确认），抽成共享框架后新资产只写用例不写执行器；评测器同时服务 bench 与季度回归（§3.4）。**可用**。
2. **生成式加工（S3）**：写法规律已条款化进 SPEC，S3 加工=按模板填空+生成。**可用，边际成本最低**。
3. **oracle 配方复用**：同域第二个 skill 直接复用确定性判定器（§6 第 4 项；首批 oracle.py 4/4 在位，monthly-report-ppt 的 make_inputs.py、ppt-method-router 的 gen_inputs.py+run_all.py 实查在位）。**可用**。
4. **build.py 渠道变体**：canonical 包只写一次，四渠道变体自动生成（SPEC §1.5.2）。**待建（D0–30 待办，find 确认未建）**。
5. **黄金集与 rubric 模式复用**：同域 rubric 维度、checks 模式直接继承（meeting-minutes 的「条目逐字引用原句」判定模式可迁移到公文/纪要类全家族）。**可用**。
6. **蒸馏器自举（S2）**：**当前不可用**（paper-to-skill 盲评全败被拒，见 §2.3 第 4 步），迭代过线后启用。

**单资产评测成本（真实约束）。** 按 SPEC §3.2/§3.3：ab_tasks ≥3 × 双臂 × 每臂 ≥3 重复 = 每资产 ≥18 次 agent 运行 + 本地确定性评测（分钟级）。这是产能的主要瓶颈，也是护城河的成本壁垒——没建这条线的竞争者每出一个 skill 都要重新发明评测，而厂商们根本没打算建。

**产能测算（计划假设，非实测批量数据；D30 复盘校准）。** 首批 4 包产生于流程探索期（含标准制定与一轮三连拒），不能线性外推。管线固化后按两档排产：
- 保守档：**2 个过验收资产/周**（S1+S3 模式化生产为主，含返工与复检占用）；
- 正常档：**3–5 个/周**（S3 生成式批量 + S2 每周 1 个蒸馏 + S1 按需）。

90 天净新增 ≥9 的 KPI（§7）即按保守档打八折设定，为课程与上架留工时。

**排产优先级：课程需求倒排。** 课程二（会议纪要）资产已以 Δ=4.33 全胜过验收 → 优先补齐其产线缺件；课程一（短视频）三件套待产；monthly-report-ppt 复裁+返工为课程四解锁；ppt-method-router 迭代关系到 S3 融合模式的成色证明。不服务课程的资产，按 S2 领域矩阵与窗口期流量排产。

### 2.6 intent-router 融合大 skill 设计模式

**为什么这是我们的差异化。** 多方法融合的难度不在写而在「路由得对 + 路由得可证 + 路由之后真的更好」。豆包有路由结构的先例（byted-mediakit-shared 纯路由入口、ppt 场景四分支、ultimate-guide 的 branches/ 总控，侦察发现①），但其融合包没有逐方法的评测断言；千问的 skillCreator 只管格式（侦察发现②）。我们把「意图路由 + 确定性可机判路由结果 + 对照评测」组合起来：ppt-method-router 输出 method/confidence/reasons 且路由决策由脚本承载、产物可复算（本会话读取其 SKILL.md 与 oracle/gen_inputs.py、run_all.py 确认），路由正确性可直接写进 golden.json 的 route_to 断言机判。

**首批实测的诚实结论（比 v1.0 口径更锐利）。** ppt-method-router 路由机判与 oracle **一致率 20/20=100%**（`_report_check/eval_ppt-method-router.json` summary 实读：agreement_rate 1.0，阈值 0.8），确定性门通过；但盲评 **Δ=0、胜率 0.33**——三局里只赢一局，均分与 baseline 完全持平。**「路由得对」已被 100% 证明，「路由之后端到端更好」被证明为零**。这给出该模式最重要的设计教训：**路由正确性是必要条件而非价值来源；增益只来自路由选中的方法 references 的执行质量**。迭代方向因此锁定：方法本体（三类制作方法的 references 与脚本）逐一增强并各自过盲评，路由逻辑不动。

**结构规范（SPEC §5.2 全文为执行依据，此处列设计要点）。**
1. **路由 SKILL.md 只留四件**：意图→方法路由表、方法边界表（逐方法列适用意图/输入/输出/不适用场景/与相邻方法排他条件）、移交协议（触发条件/必须携带的状态/移交后禁止事项）、文档地图表。
2. **约束**：方法 ≤4、每方法 references ≤3 份，超限必须拆为多个独立 skill + 一个总控路由 skill（依据：SkillsBench 实测聚焦技能 ≤3 模块胜过大而全捆绑，平均 +16.6pp，侦察发现③）。
3. **确定性优先**：路由决策用脚本（信号词规则表）承载而非让模型自由发挥；路由产物必须可复算（落盘 labels/method 文件——ppt-method-router 的 labels.json 20 条即此实践）。
4. **评测（含首批新增规则）**：每方法 ≥1 正例 + 1 近邻负例（route_to 到方法粒度）、≥1 跨方法 ab_task 验证移交协议（SPEC §5.2 第 5 条）；**另加：每个方法至少 1 条 ab_task 度量该方法产物的端到端质量**——防止「路由对、东西差」再过不了盲评门（ppt-method-router 的 Δ=0 就是这一课）。

**适用判据。** 当且仅当多个方法服务同一类用户意图且方法间存在真实互斥/排他关系时用融合路由；单纯的功能堆叠一律拆成独立 skill（一包一能，SPEC §0.2 第 3 条）。

## 三、评价与迭代体系

### 3.1 评测协议：直接引用标准，不另立门户

执行依据即 `skillfactory/standard/SKILL-SPEC-v0.1.md` §3（本会话全文读取）：
- **确定性评测**（§3.1）：`eval/runner.py` 读 golden.json 全量机判，输出逐条 pass/fail 与证据、汇总 pass_rate；只断言可机判对象，禁止用确定性断言判文风。
- **黄金集**（§3.2）：`eval_inputs` 三类用例缺一不可——positive（应触发且做对）/ negative（近邻不应触发，测 description 精度）/ adversarial（相关但误导；依据 arXiv:2608.11888 实测技能致害最大类是 Task-Implementation Fault 68.8%，仅测触发不测误导不够）；`ab_tasks` ≥3 条带 0–10 rubric；golden 冻结于验收版本，修订必须升版归档（禁止为让新实现通过而静默改断言——meeting-minutes 的 golden-v1.0/v1.1 双版归档即此实践，本会话实查 `eval/archive/`）。
- **双臂盲评**（§3.3）：with_skill vs without_skill 同模型同 prompt、独立子代理保证干净上下文；迭代版用旧版快照做 baseline；LLM 裁判盲态+评分证据+禁止同情分。
- **验收五门**（§4）：确定性 exit 0｜盲评 Δ≥1.0 且胜率≥60%｜效率 token 与耗时比率 ≤2.0（一票否决）｜形式门｜断言复审门。

### 3.2 首批实测：验收线有效性的第一次证明

首批 4 资产对照五门的实测结果（**任务下发口径，本方案唯一权威数据源**；确定性检查细节另经本会话实读 `_report_check/eval_*.json` 佐证）：

| 资产 | 确定性门 | 盲评门（线：Δ≥1.0 且胜率≥0.60） | 结论 | 拒因/去向 |
|---|---|---|---|---|
| meeting-minutes 会议纪要三段式 | ✓（20 项检查全过，含逐字溯源反幻觉判定） | **Δ=4.33，胜率 1.0（全胜）** | **接受** | 已入库；形式门欠账复检后分发 |
| monthly-report-ppt 月度汇报生成器 | ✗（任务下发口径；`_report_check` 复检显示 16 项全过，张力待复裁，见下） | 未进入 | **返工** | 资产或实现需返工；先复现官方评测裁决口径，再修实现与 oracle 对齐；课程四联动（§5.2） |
| ppt-method-router PPT 方法意图路由 | ✓（路由一致率 20/20=100%） | **Δ=0，胜率 0.33** | **拒** | 「技能本体或 spec 需迭代」；路由已证、增益为零（§2.6） |
| paper-to-skill 知识蒸馏器 | ✓（3 项检查过） | **Δ=−0.5，胜率 0（全败）** | **拒** | treatment 全面低于 baseline——当前版本挂上反而更差；先归因再裁决迭代或降级（§3.6） |

五条读数：
1. **每扇门都杀过东西**：确定性门拦下 1 个（monthly-report-ppt），盲评门拦下 2 个（ppt-method-router、paper-to-skill）。没有门是摆设——这是对内对外都可以出示的「验收线有效性」证据。
2. **paper-to-skill 的 Δ=−0.5/胜率 0 是全批最有信息量的数字**：它证明「有 skill」不等于「更好」，甚至可能全面更差——与学术结论（Signal or Noise：无差别注入通常更差；2608.11888：技能致害主要来自「相关但误导的流程」）在我方自己的资产上复现。这既是迭代的靶子，也是我们对外讲「为什么要对照评测」的最佳自家案例：**没有对照评测的 skill 市场，负增益技能会无感流通**——而豆包 106 包里只有 5 个带 evals（侦察发现①），全行业都处在这种无感状态。
3. **meeting-minutes 的 Δ=4.33/胜率 1.0 是增益上限的锚点**：全胜意味着在每条盲评任务上挂载技能都稳定更好——聚焦单能 + 确定性 oracle + 逐字溯源反幻觉的组合得到最强内部印证（SkillsBench「聚焦技能胜过大而全」结论的我方版本）。后续资产的质量目标即向此画像看齐。
4. **ppt-method-router 的「100% 路由一致 + Δ=0」组合是最清晰的模式教训**：机判全对却零增益，证明路由不产生价值、方法本体才产生价值——这直接改写了 S3 融合模式的评测规则（每方法必须单独过端到端盲评，§2.6）。
5. **通过项与拒绝项都「死得明白」**：四个资产各自的门禁结论、拒因与迭代路径全部可指认——验收线不是黑箱打分，而是可复算的证据链（确定性部分已有 `_report_check` 落盘佐证）。

**对首批评测产物的诚实披露（本会话实查）。** ① 四包 `eval/` 内均无 `protocol.md` 与 `results/benchmark.json` 落盘件、全库无 benchmark.json（`find` 空结果）、golden.json 为旧 schema——首批评测先于 SPEC 定稿执行，过程可信（结果由任务下发台账记录）但产物未按 v0.1 归位；② 效率门本轮未出数（任务下发结果只含 evalPassed/abDelta/winRate，无 token/耗时比率）；③ **monthly-report-ppt 的张力**：`_report_check/eval_monthly-report-ppt.json`（2026-09-29 06:45 落盘，.err 为空）显示其 16 项确定性检查全部通过，与任务下发 evalPassed=false 不一致——可能原因包括官方评测当时的环境/依赖差异或 runner 与 oracle 复检口径差异，本会话无法裁定；D0–30 以同版 golden 复现官方评测后裁决，**裁决前分发与课程排期均按「未过」口径执行**。补齐落盘与 schema 迁移后，验收记录才构成可出示的完整证据链。

### 3.3 黄金集是资产

三层资产化：
1. **版本化**：golden.json 冻结+归档（已在 meeting-minutes 实践，`eval/archive/` 存 golden-v1.0-20260929 与 golden-v1.1-20260929 两版，本会话实查），这是评测可信度的根基，也是对外可承诺「同一把尺子」的前提。
2. **可复用**：同域 rubric 维度（正确性/完整性/可验证性三基维，SPEC §3.2 规则 2）、checks 模式（file_exists/json_valid/route_to/numeric_claim_has_source/逐字溯源……）按域沉淀进 oracle 配方库（§6 第 4 项），新资产搭评测的成本从「天」降到「小时」。
3. **会生长**：课程学员的真实任务数据（征得同意、脱敏后）回流扩充黄金集——真实任务提取正是官方 best-practices 认定的第一蒸馏路径（侦察发现③ 4.1）。这使我们的黄金集随课程规模复利增长，而竞争者的评测集是静态的。

### 3.4 「普通模型 + skill」对照 bench：护城河的工程化

**定位。** 这是雇主核心论点的落地：skill 是对普通模型的增益，**增益必须被测量才能被出售**。四家厂商都没有质量度量（侦察发现②）；学界有方法（SkillsBench：87 任务×8 域×18 配置，no-skill vs curated-skill 配对，33.9%→50.5%，侦察发现③）但没有产品化。我们把它做成常态化基础设施。

**bench 设计（吸收三条学术教训）。**
1. **矩阵**：资产 × ≥2 个模型 × {with, without} × ≥3 重复；**报告每配置增益而非只报平均**（SkillsBench 用 18 个 model-harness 配置证明各配置增益差异大：+4.1~+25.7pp，侦察发现③）。
2. **三类用例齐备**（SPEC §2.1/§3.2）：正例、近邻负例、相关但误导（adversarial）——后者直击 68.8% 的 Task-Implementation Fault。
3. **效率是一等公民**：token 与耗时比率门 ≤2.0 一票否决（SPEC §4 第 3 门；教训：SWE-Skills-Bench token 开销最高 +451%，arXiv:2608.11888 实测 62.6% 失败为效率回退、Context Bloat 几乎全由强制正文造成——侦察发现③）。
4. **判分纪律**：可编程断言优先；LLM 裁判必须附证据；恒过/恒败断言剔除（官方 SOP 四条 pattern 规则，侦察发现③ 3.1）。

**运行节奏。** 验收时逐资产跑（入门即测）；此后每季对全部在架资产全量回归一轮；新模型发布即插入矩阵测一轮（新增增益数据点）。**当前差距（诚实标注）**：首批评测为单裁判单模型臂，且未出 token/耗时数据；双模型矩阵、效率门数据与首轮全量回归是 D31–60 待办（§7）。

**对外呈现。** 聚合为自有「skill 增益榜」（§6 第 10 项）：每行一个资产，列出双臂均分、Δ、胜率、token/耗时比率、评测模型与日期。首批四行数据（+4.33 全胜 / 确定性未过 / 0 / −0.5）本身就是榜的雏形与传播素材。它是阶段 0 影响力物料、阶段 3 托管公信力的地基。

### 3.5 体检报告即分发物料：「每个 skill 附体检报告」的差异化

**是什么。** 每个资产分发时附带一份人类可读的 REPORT.md，由 `eval/results/benchmark.json` + 验收单自动渲染，内容：五门逐项结论与证据、双臂均分±标准差与逐对胜负、token/耗时比率、golden 版本、失败归因与已知局限、来源与许可（与 MANIFEST.json 同级的信任件）。

**为什么是差异化（三重市场空白证明）。**
- 豆包 106 包仅 5 个带 evals、仅 28/106 有任何版本号、license 仅 9/106（侦察发现①，CATALOG.md 总览统计实读在位）——全球最大单体 skill 库自己就不提供质量凭证；
- 四家厂商 loader 全部无质量度量（侦察发现②）；
- ClawHub 无审计导致约 15% 恶意感染率事件之后，「可审计的干净 skill」成为采购情绪（侦察发现④）。体检报告 = 质量凭证 + 安全自证（配合 MANIFEST 逐文件 sha256，SPEC §2.5）双角色。

**三种用途。** 对内：迭代信号（§3.6）；对外：分发物料与内容营销素材（「我们的每个技能都有体检报告，被拒的也会公示拒因」本身就是传播点——首批「4 进 1 出：全胜/返工/零增益/负增益」恰好是第一篇内容的完整叙事）；对客户：验收单即合同的基础件（研究报告 `oss-research-report.md:453`「验收单即合同」建议的落地形式）。

**前置欠账（诚实标注）。** 本会话实查四包无 `results/benchmark.json` 落盘件、无 `protocol.md`。D0–30 先补落盘与渲染脚本，报告机制才能转起来（§7.1）。

### 3.6 迭代循环：三信号修订 + 失败归因

1. **三信号喂修订**：失败断言 + 人工 feedback.json + 执行 transcript 喂给 LLM 提修订案（官方 SOP 迭代循环，侦察发现③ 3.1）；pass rate 平台期时**先试删指令**（官方指南方向：避免「失败就加规则」的过度约束）。
2. **失败自动归因**：借鉴 SkillTriage 五类归因（指令误导实现/工件放错/环境不匹配/过度流程/上下文膨胀，子类准确率 88.8%/72.5%，侦察发现③），归因结果写回体检报告「已知局限」节。
3. **误导优先修**：adversarial 用例失败 > 触发失败的优先级，因为 68.8% 的致害来自「相关但误导的流程」（arXiv:2608.11888）。
4. **正文瘦身**：Context Bloat 25.3% 几乎全由强制正文造成（同上）——每轮迭代后复查正文 ≤10,000 字符红线，超限下沉 references（SPEC §1.4）。
5. **首批三个被拒资产即迭代循环的第一批输入（各自路径不同）**：
   - **monthly-report-ppt**：先复裁（同版 golden 复现官方评测，裁决 `_report_check` 张力）→ 若确认未过，按「资产或实现返工」路径修 oracle 与实现的对齐，再全量回归；
   - **ppt-method-router**：按「技能本体迭代」路径走——三类制作方法 references 的执行质量逐Method 增强、各自过端到端盲评，路由逻辑与 100% 一致的机判层不动（§2.6 结论）；
   - **paper-to-skill**：先归因（Δ=−0.5 且全败指向系统性误导而非个别用例——skill 内容可能在教模型做错事，正是 Task-Implementation Fault 模式）再裁决「迭代 or 降级为纯脚手架工具」。

## 四、商业模式演进

### 4.1 前提：平台全部免费，圈量期判断

侦察发现④逐家核实的分发现状（引用时保持其口径）：腾讯 WorkBuddy 开放平台（2026-09-02 上线，五大生态能力含 Skill，官网与协议页均无分成/收费表述）；Qoder 技能市场（可上架，无分成机制发现）；TRAE（内置技能市场，无变现机制发现）；anthropics/skills 插件市场（官方页面无收费/分成）；OpenAI Apps（早期只允许跳转站外卖实物，数字商品「exploring」）；MCP Registry（零门槛、API 已冻结 v0.1）；ModelScope MCP 广场（页面 JS 渲染未能核实，如实存疑）。**结论：平台内卖 skill 零证据，行业处圈量期。** 历史对照（App Store 30%→15%、GPT Store 分成跳票后产品线被整体替换、Cursor 补贴退坡、微信 iOS 虚拟支付 8 年禁令）指向三条纪律——**不赌分成、不签独家、把任何平台的免费流量当期限资产**（侦察发现④ implications）。

### 4.2 阶段 0（现在 → 约 D90）：免费铺量建立影响力

- **动作**：全部过验收资产经 build.py 生成变体后免费上架——国内 WorkBuddy 第一优先（2026-09-02 刚开放、生态冷启动期目录曝光红利，侦察发现④；研究报告 §3.3 确认其原生 SKILL.md、个人实名+人脸即可入驻）、Qoder CN 与 TRAE 同步（零成本纯获客，他山团队 20 项科研 skill 18 个已上架 Qoder 的先例）、GitHub 开源仓为 canonical 源（Claude Code 生态主流安装路径）、MCP Registry 发布元数据占位；每个 skill 附体检报告；CATALOG/增益榜页公开。
- **收入形态**：0 元。定位为获客资产而非收入来源。
- **进入条件**：无——当前即此阶段。
- **先验证的假设**：① 免费上架能否产生可度量影响力（见下指标）；② 「附体检报告」是否提升采用率（同资产带/不带报告对照曝光——这本身就是一次 with/without 实验，与我们评测方法论同构）；③ 上架通道摩擦（WorkBuddy 实名+人脸入驻、审核时长——门槛已核实为低，细则未披露，研究报告 §3.3）。
- **influence 量化指标（当前无收费通路下的度量体系）**：
  - **上架数**：渠道数 × 在架件次（目标见 §7 KPI 表）；
  - **调用证据**：各平台后台计数（若可得——WorkBuddy 未披露流量数据，按可得性降级并如实注明）、GitHub star/fork/clone、issue 与 PR（外部用户跑通/报障是最硬的调用证据）、被 awesome 类列表收录；
  - **内容证据**：体检报告页/增益榜页访问、引用与转发；
  - **北极星**：出现 ≥3 条「外部用户把我们的 skill 装进自己的 agent 并留下对话/issue 证据」。
- **退出条件（升阶段 1）**：北极星达成或免费层引流数据达到课程招生所需基线（邮件/私域列表 ≥300 人，计划假设值，D60 复核）。

### 4.3 阶段 1（约 D90–D180）：课程变现

- **动作**：开卖端到端成果课。首发两门按研究报告开发序（`oss-research-report.md:448` §5.4 第 1 条：先课程二后课程一）：课程二（会议纪要一条龙——对应资产 meeting-minutes 已以 Δ=4.33/胜率 1.0 过验收，产线资产链最稳：FunASR 官方 MCP 20.5k★/MarkItDown 187k★/n8n 206k★，研究报告课程二节）与课程一（日更短视频量产——资产链最强五环全 10k★+）；课程五（技能封装工坊）随后（§5）。
- **收入形态**：课程费，定价 199–1999 元带（免费 0 元单点 → 低价成果课，避开 3980–7980 差评集中带；研究报告 §1 定价建议，其价格锚点为聚合来源口径）；结业验收单即合同（Agent Release 六要素清单，研究报告 §5.4 第 6 条）。
- **进入条件**：① ≥2 门课的端到端产线可复跑且现场验收彩排通过（研究报告已标注：课程一「现场 10 条」为待试跑目标值，开课前必须计时试跑）；② 对应 skill 资产过五门（meeting-minutes ✓；短视频三件套待产）；③ 免费层引流达基线；④ 收款通路就绪（国内小额收款无开源方案，短期人工发货+私域/知识星球过渡——研究报告 §5.4 第 7 条）。
- **先验证的假设**：① 付费意愿（侦察发现④与研究报告均标注为未验证假设——靠免费层数据先行验证，不预设）；② 成果验收通过率 ≥80%（每期现场用学员真实素材验收）；③ 199–1999 带的转化率支撑班期模型。
- **退出条件（升阶段 2）**：≥2 期课程交付、学员池形成、≥1 个学员案例可公开。

### 4.4 阶段 2（约 6–12 月）：订阅与定制

- **动作与收入形态**：三线并行——
  1. **skill 持续升级订阅**：consent-first 轨迹回流（学员显式开观测开关换技能免费持续升级）——生态空位已核实：没有团队做「consent-first + 权益交换 + 轨迹自动沉淀为 skill 升级数据集」的完整闭环（研究报告 §3.1 第 9 条，8 次中英检索未发现）；
  2. **ToB 定制与部署**：证据最强的个人/小团队变现路径（侦察发现④：Coze 草根团队定制单、智能体代运营 999 元/月/店等报道案例）；我们以「模板工程 + 治理随行包 + 体检报告」提高交付溢价；
  3. **模板工程按件计价**：公司 VI PPT 模板固化、公文格式校验——研究报告确认的开源空白（§2.2 空白③、§5.4 第 5 条），天然付费壁垒。
- **进入条件**：① 阶段 1 完成且学员池 ≥ 阈值；② 治理随行包 v1 落地（consent shim + 观测 shim，§6 第 9 项）；③ fork 自维护清单完成（Office-Word-MCP-Server 已归档、excel-mcp-server 单人维护——付费交付前必须 fork+回归，研究报告 §5.2）；④ ≥1 个 ToB 标杆案例。
- **先验证的假设**：① consent 率（学员愿意开观测开关换升级——研究报告判断基准第 3 条的核心赌注）；② 定制交付边际成本可控（研究报告 §3.4 第 8 条四大难点：验收标准/错误累积/边际成本/维护责任）；③ 订阅续费率。
- **退出条件（升阶段 3）**：≥3 个付费复购客户且托管运维工时模型跑平。

### 4.5 阶段 3（12 月+）：治理面托管

- **动作与收入形态**：完整 agent + 治理面托管，按月订阅或按成果计价（对齐 Lovable credits 模式，研究报告 §3.4 第 7 条）。交付物 = Agent Release 六要素版本化（模型及路由/编排/Prompt 与 Skill 版本/工具与权限/Runtime/评估基线——阿里云 AI Agent Handbook 范式，研究报告 §3.2）+ 治理随行包（观测/consent/验收基线）+ 自有 bench 基线。
- **进入条件**：① 治理随行包产品化（从课程配件变独立产品）；② 增益榜/基准对外发布并积累公信力；③ 按月订阅毛利模型为正。
- **先验证的假设**：企业愿意为「可审计、可复现、带评估基线」付长期订阅（阿里云手册治理篇的判断——「可观测、安全和评估是运行前提，而不是上线补丁」，研究报告 §3.2 第 8 条——说明需求真实存在，付费意愿待验证）；托管运维成本 < 订阅收入。

### 4.6 风险与红线（全阶段有效）

1. **不赌分成**：即便未来出现 15%–30% 分成也是平台利润而非作者红利（App Store 历史只往下压）——现金流永远设计在平台外（课程/订阅/定制）。
2. **不签独家**：当前无平台要求独家，也不主动承诺；核心 know-how 与客户关系（私域/邮件列表）留平台外——GPT Store builders 是前车之鉴。
3. **平台换赛道**：任何平台流量是期限资产；补贴期建立的分发必须在退坡前转化为自有渠道（Cursor 教训）。
4. **审核与供应链**：skill 含可执行代码；上架前五步自检 + MANIFEST + 体检报告自证安全（SPEC §2.5）；ClawHub 类事件推动审核收紧是概率事件，我们的报告机制本来就是预案。
5. **格式演进**：每季对照 agentskills.io spec 复核（SPEC §6.2）；build 管线只依赖 name/description/SKILL.md 三要素，平台私有增强一律编译期可剥离（SPEC §1.5.2 通用规则 4）。
6. **「90% 作者收入不足 1000 元」的警示**（smzdm 口径，二手未验证，侦察发现④）：技术强≠变现强。我们的对策是把收入设计在「交付/验收/担保」层（研究报告 §3.4：知识本身已免费，付费点只能在交付），而非技能件本身。
7. **负增益风险自我管理**：paper-to-skill 的全败证明我方产线也会产出负增益资产——**任何资产在过盲评门前不对外分发**（SPEC §4 门禁即红线），避免「无感流通的负增益 skill」反噬品牌；这也是体检报告必须随行分发的原因。

## 五、课程体系：与上一轮 5 门课打通

### 5.1 三条打通逻辑

1. **免费技能即引流**：每门课的免费单点能力直接取自工厂过验收资产——不再临时打包。课程免费层与资产上架共用同一产物，一次生产两处复用（研究报告 §4 各课「免费单点能力」节：课程一「打字幕/我的声音/素材入库」三件、课程二「录音转文字/文档转 Markdown/Word 成品」三件、课程四「大白话查表/Excel 机器人/PPT 半成品」三件、课程五「脚手架生成器/网页转 Markdown/上架检查单」三件）。工厂按此清单排产，产出的每个免费件同时服务于多平台上架影响力。
2. **付费交付端到端成果，成果中直接使用自家 skill 与治理随行包**：学员下课带走的不是知识点，是「产线 + 自家 skill 包（带体检报告）+ consent/观测 shim + Agent Release 六要素验收单」。这同时是产品活样板的规模化分发——每一期课程都在给资产做真实环境压测与传播。
3. **高级课学员产出反哺资产工厂**：技能封装工坊（课程五）学员按 SPEC 五门验收后，其技能包可入库资产工厂（确认许可与署名，学员获署名与升级权益）。工坊=工厂的外包车间+人才漏斗——研究报告对课程五的战略判断（「课程产物即雇主产品线活样本」，研究报告课程五节）在工厂语境下升级为「学员产能反哺」。

### 5.4 课程即评测场

## 六、除 skill 外应建立的资产清单

十项，每项：是什么 / 为什么 / 复用在哪。均为「一次建设、处处复利」的基础设施，与 skill 资产同等对待（带版本与台账）。

1. **黄金评测集**。是什么：跨 skill 的 eval_inputs/ab_tasks 用例库 + rubric 模板 + 学员回流脱敏样本，按域组织。为什么：评测可信度的根基；静态评测集是竞争者最难复制的部分（抄得走 SKILL.md 抄不走 87 任务级的黄金集——SkillsBench 的规模即护城河量级参照）。复用：新资产小时级搭评测、季度全量回归（§3.4）、对外基准、课程验收。
2. **eval runner 框架**。是什么：通用 runner.py（确定性判定引擎）+ benchmark.json 聚合器 + 体检报告渲染器 + bench 调度器（双臂×N 模型×N 重复）。为什么：首批 4 包已各自实现同构 runner（本会话实查），不抽框架则每资产重复造轮子且判定口径漂移——monthly-report-ppt 的复裁张力（§3.2）正是口径不统一的现实代价。复用：每个新资产零成本接入；bench 与回归同一套代码；课程五学员直接用（教学件即生产件）。
3. **spec 模板库**。是什么：SKILL.md 骨架（SPEC 附录 A）、验收检查单（附录 B）、CHANGELOG/MANIFEST/protocol.md 模板、agents interface yaml 模板的可填充版本。为什么：S3 生成式加工与课程五教学的前提；保证「出厂即合规」（首批 3 包缺 CHANGELOG、2 包 front-matter 不齐——本会话实查——说明手写必漏，必须模板化）。复用：三源全部管线、build.py 的输入、学员反哺产出的质量控制。
4. **oracle 配方库**。是什么：每域一个确定性判定器配方（会议纪要=逐字引用率+结构三段；PPT=模板保真/不跑版；路由=route_to 标签一致；转写=字错率抽检……），含输入生成器（monthly-report-ppt 的 make_inputs.py、ppt-method-router 的 gen_inputs.py+run_all.py——本会话实查在位）。为什么：确定性门的判定质量决定资产可信度；「oracle 先行」让评测先于实现存在。复用：同域新 skill、bench、课程验收自动化、ToB 交付的验收合同。
