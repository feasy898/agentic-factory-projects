## 第 0 步：输入要求与登记

- 输入必须是 **Markdown 文本稿**（UTF-8，容忍 BOM）。PDF/docx/HTML 不直接支持——先转成文本稿再进流程。
- 有来源 URL 就带上：`--url` 会写进产物 front-matter 的 `metadata.source_url` 与「来源引用」节，缺了溯源链就断。
- 登记：把 `--source`、来源 URL、蒸馏日期记入成品 front-matter 的 `metadata`（`source` / `source-url` / `distilled-at` 三键，企业标准 §5.1 必填）。
- 红线：抓取来源网页由使用者完成，脚本与流程**不做联网**；拿不到文本稿就停下向用户要，禁止凭记忆编造来源内容。

## 第 1 步：建骨架（脚本契约）

```bash
python package/scripts/distill.py --source <来源.md> --outdir <输出目录> [--url <来源URL>]
```

- 成功判据（全部满足才算过）：退出码 0；stdout 恰好 5 行 `[oracle] ...`（source / title / stats / wrote ×2，spec R1.3 冻结口径）；`<outdir>/outline.json` 与 `<outdir>/draft_skill/SKILL.md` 存在。
- 失败判据：源文件不存在/不可读 → stderr 含 `ERROR`、退出码非 0、**不创建输出目录、不产出任何文件**（无半成品）。
- 确定性：脚本无网络、无随机、无时间戳；同输入同参重跑 `outline.json` 字节一致（换 `--outdir` 重跑仅 `SKILL.md` 因内嵌重跑命令而不同）。复跑不一致 = 实现被改坏，先修脚本，禁止手改产物。
- 产物格式：`outline.json` 顶层固定 8 键（`generator` / `generator_version` / `deterministic` / `source` / `source_url` / `source_title` / `stats` / `outline`）；`stats` 固定 13 键（行数、字符数、各级标题数、列表项总数与无序/有序、代码块数与行数、语言分布、表格行数），口径细节见 `../spec.md` §5。

## 第 2 步：读骨架与信息取舍

1. 先读 `outline.json` 的 `outline` 标题树：一屏看清章节骨架；`stats` 给出体量。
2. 再读 `draft_skill/SKILL.md`：它已按规则摘好 H1/H2 主题清单（≤8 条）、「分步方法」章节切片（每节前 2 条列表项）、警示关键词命中句（≤6 条）——但**只是摘取**（超长硬截＋`…`），不是成品。
3. 逐节判定收/弃/补（对照 `../SKILL.md`「信息取舍」表）：
   - 收：操作顺序、命令、参数名、阈值、字段约束、反例、警示句。每条记 `原文 L<行号>`。
   - 弃：背景故事、营销话术、与能力无关的整章。弃得果断——技能是常驻上下文里的操作手册，不是摘要。
   - 补：来源没写但照做必需的步骤，标 `[补充]` 并给出独立依据（另一份可信文档或实测结果）。
4. 表格别漏：脚本的坑候选池与章节切片都不含表格行；黄金例中 name 字段约束的表格版（`原文 L29-36`）只存在于源表格，人工蒸馏必须单独读取。
5. 判定能力边界：一句话说清「本技能做什么、不做什么、不做的转交给谁」。写不出来的能力不要勉强成包。

## 第 3 步：步骤化（可判定改写）

把收下的内容改写成编号步骤。**每一步必须过"三选一"可判定标记**（与 `../eval/runner.py` check 2 同款）：

1. 溯源标记：`原文 L<数字>`——适合从来源直接摘取的约束与结论；
2. 成对反引号包裹的命令或路径——适合动作本身（如 `python package/scripts/distill.py --source <md> --outdir <dir>`）；
3. 产物文件名（`.py`/`.md`/`.json`/`.txt`/`.csv`/`.docx`/`.pptx`/`.xlsx` 扩展名）——适合成功判据。

改写模板：`N. <动作短语>：<命令或操作>（溯源/判据）`。反例（禁止交付的写法）：

- 空话步骤：「妥善处理错误，注意边界情况」——无动作、无判据、无标记。
- 不可回溯步骤：「按规范设置名称」——哪个规范？哪条？改成「name 仅小写字母/数字/连字符，且与目录同名（原文 L66-70）」才合格。
- 只有口号没有判据：「认真校验」——改成「运行 `skills-ref validate ./my-skill`，退出码 0 为过（原文 L269-275）」。

## 第 4 步：触发词设计

`description` 是技能唯一的常驻触发界面，按三段式写，宁强勿弱：

1. **能力段**：是什么 + 覆盖哪些任务（清单式，可数）。
2. **触发段**：「当用户……时使用」+ 至少 3 个具体口语触发短语（中英文都要有），每个短语能映射到一个真实任务说法。
3. **边界段**：「不用于 X；X 转交 `<对方skill-name>`」——把近邻能力显式推开，互斥技能互相点名导流。

硬约束：单行标量、≤1024 字符、禁块标量；禁止把正文指令混入 description；禁止「相关时/必要时」式模糊触发。好例与坏例的差距见 `../example/SKILL.md` 所引 `（原文 L114）`（好例）与 `（原文 L120）`（坏例 "Helps with PDFs."）。

## 第 5 步：坑点提炼

- 底稿 = 草稿「常见坑」节。脚本选法：候选池 = 标题＋列表项＋段落（**不含表格行**），命中 24 个警示关键词（大小写不敏感子串）即入选，按文档顺序取前 6 条，前 60 字符小写为键去重，超 120 字符截断。
- 已知局限（人工复核不可省）：①命中即整句收录、不判语境——标题带 "security" 就会整条入坑（黄金 blog 例实测如此）；②表格约束进不了候选池（见第 2 步第 4 条）；③上限 6 条，第 7 条以后的坑永远进不了底稿。
- 人工补坑：蒸馏过程实际踩到的坑（命令报错、口径误解、环境差异），每条写「现象 → 原因 → 正确做法」，禁止只写现象。
- 复核动作：对底稿每条问一句「照着它做会错吗？」——不会错的是误收（删），会错而没写的是漏（补）。

## 第 6 步：来源引用规范与验收

来源引用节固定 4–5 条 bullet：源文件（`--source` 原样）、来源 URL（给了 `--url` 才有）、源标题、结构统计（H1/H2/列表要点/代码块四数＋指向 `outline.json`）、生成方式（generator＋完整重跑命令，命令可原样执行）。

验收（全过才交付）：

1. 五要素自查：front-matter（name+description）、触发描述 ≥20 字、分步方法（每步可判定）、常见坑（实质条目）、来源引用——对照 `../example/SKILL.md` 逐项核对。
2. 有资产根 eval 时：`python eval/runner.py <被测out> <参照out>`，退出码 0 为过（统计偏差 ≤30%＋五要素＋步骤可判定）。
3. A/B 对照（`../eval/golden.json` 的 ab_tasks）：treatment 组先完整读 `../example/SKILL.md` 再写，baseline 组直接写；同 instruction 同 input，按 rubric 逐条 0/1 判分对比。
4. 定性红线复查：无整段复制来源文字；所有 `[补充]` 标注在位；name 与技能目录名一致且合规。

## 质量自查单

- [ ] `outline.json` 同参重跑字节一致
- [ ] 每条保留内容带 `原文 L` 或 `[补充]`
- [ ] 每个编号步骤过「三选一」可判定标记
- [ ] description 三段式、≥3 触发短语、≤1024 字符、单行标量

- [ ] name 与技能目录名一致，合规（小写/数字/连字符，≤64，无首尾/连续连字符）
