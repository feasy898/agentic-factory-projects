# PPT 方法意图路由（ppt-method-router）

## 1. 名称与一句话描述

**PPT 方法意图路由**：给定一条用户的 PPT 制作意图文本，按信号词规则在
`editable_pptx`（数据驱动可编辑汇报）/ `template_fill`（套用既有公司模板）/
`visual_report`（图文海报/信息图）三类制作方式中**确定性地**选出最优路径，
并给出置信度与逐条裁定理由。本技能是"多方法融合大 skill"的**路由层**：
只决定选哪条路，不执行任何一条路。

## 2. 何时使用

满足任一条件即应使用本技能：

- 用户提出"做 PPT / 做汇报 / 做海报 / 做信息图 / 做一页图"类制作需求，需要先决定制作路径；
- 需求措辞里同时出现多种制作信号（如"数据 + 海报"），需要按固定优先级消解冲突；
- 需求措辞没有任何制作信号（如"帮我做个 PPT"），需要给出低置信兜底判定并提示澄清；
- 批量处理一组意图文本，需要可复算、可评测的路由产物（`out/labels.json`）。

**歧义澄清策略**（配合脚本输出使用）：

- 脚本对"无信号"输入会返回兜底判定（`editable_pptx`，confidence 0.4），
  reasons 中明确提示"建议先向用户澄清用途再进入执行"——此时应先向用户确认
  ①交付形态（可编辑文稿 / 套模板 / 海报图）②使用场合，拿到新措辞后**重新运行路由**，
  而不是直接采纳兜底判定进入制作；
- 脚本对"多类信号冲突"输入会按优先级裁定并把 confidence 压到 ≤0.75，
  reasons 中会点名被压制的类别并建议人工复核——此时若对话上下文已能确认用户
  真实意图偏向被压制类（例：用户明说"就要发朋友圈"），应以用户显式意愿为准改道，
  并在回复中说明"规则路由与用户显式意愿不一致，已按用户意愿执行"；
- 澄清话术只问缺失的关键维度，不逐条复述关键词命中明细（那是 reasons 的职责）。

## 3. 三类方法的定义与适用场景

| method | 含义 | 适用场景 | 能力边界（不该选它的情形） | 路由后的移交方式 |
|---|---|---|---|---|
| `editable_pptx` | 数据驱动可编辑汇报 | 数据、表格、台账、月报、图表、汇报类需求；后续要反复改数字、加页 | 不适合对外传播的单页视觉物料；无模板资产时无法沿用既有品牌版式 | 移交给"数据汇报 PPT 生成"执行链：结构化数据 → 大纲 → 母版/版式 → 逐页图表化；交付可编辑 .pptx 源文件 |
| `template_fill` | 套用既有公司模板 | 用户已有公司模板 / 品牌 VI / 需贴合品牌调性的对外材料 | 模板资产不存在或不可用时无法执行；不适合自由版式的创意物料 | 移交给"模板填充"执行链：定位模板资产 → 提取版式与占位符 → 内容映射 → 校验品牌规范；交付沿用模板的 .pptx |
| `visual_report` | 图文海报/信息图 | 海报、一页图、信息图、朋友圈/转发类传播物料；重视觉冲击、轻可编辑性 | 不适合需要多页、可改数据的汇报；文字层不可深度编辑 | 移交给"视觉物料"执行链：提炼单页信息层级 → 视觉编排 → 导出长图/图片；交付图片或设计源稿 |

三类方法互斥：一次路由只返回一个 method；若用户确需"既可编辑又可传播"，
按 `editable_pptx` 路由后在执行链内追加导图步骤，而不是拆成两次路由。

## 4. 路由决策规则摘要

**信号词识别**：对意图全文做**子串匹配**，文本与关键词均先 `lower()`（大小写不敏感）。
三组信号词（R1）：

| 类别（优先级序） | 信号词 |
|---|---|
| `template_fill`（最高） | 模板、公司VI、套用、品牌 |
| `editable_pptx`（次之） | 数据、表格、台账、月报、图表、汇报 |
| `visual_report`（最低） | 海报、一页、信息图、视觉、朋友圈、转发 |

匹配细节：子串匹配、不做分词与语义理解——"品牌VI模板"命中 `品牌`+`模板` 但**不命中**
"公司VI"（"公司"与"VI"不连续）；这是预期行为。每组信号词各计一次（命中即算，
不按出现次数重复计）。

**裁定规则**：

1. **单类命中**：method = 该类；`confidence = 0.80 + 0.05 × (命中词数 − 1)`，上限 **0.95**；
2. **多类命中**：按固定优先级 **`template_fill > editable_pptx > visual_report`** 取最高类；
   `confidence = 0.60 + 0.05 × (各类命中词总数 − 2)`，上限 **0.75**（信号冲突压低置信度）；
   reasons 必须披露：每类命中词 → 优先级链与裁定结果 → 冲突说明与人工复核建议；
3. **无任何命中（无信号兜底）**：method = `editable_pptx`，`confidence = 0.40`；
   reasons 必须如实写明"未命中任何类别关键词"与兜底默认，**不得编造命中词**。

confidence 是确定性公式值（保留两位小数，序列化省略尾零），不具备统计概率语义。
同一输入重复运行输出逐字节一致；路由过程不调用 LLM、不依赖网络。

## 5. 使用步骤

以下命令均在资产根目录 `skillfactory/assets/ppt-method-router/` 下执行
（相对路径按当前工作目录解析，也可传绝对路径）：

1. **单条路由**：把意图文本存为 .txt（UTF-8，容许 BOM），运行
   `python package/scripts/route.py --input <意图.txt>`
   → stdout 恰一行 JSON（见 §6）；文件不存在时退出码 2、stderr 提示。
2. **批量路由**：`python package/run_all.py`
   → 逐条以 subprocess 调用 route.py 处理 `package/inputs/case1.txt … case20.txt`，
   产出 `package/out/labels.json`（恰 20 条，顺序 case1 → case20）。
3. **验证**：`python eval/runner.py package/out oracle/out`
   → 与参照判定按 case 比对 method，**一致率须 ≥ 80%**，同时校验 20 条齐全、
   schema 合法、reasons 非空；全部通过 exit 0 并打印 JSON 检查明细。

新意图接入流程：写成新的 .txt → 单条路由看 method/confidence/reasons →
按 §2 澄清策略处理低置信或冲突 → 需要回归时把新样例加入批量目录重跑 run_all + runner。

## 6. 输出契约

`route.py` 成功时 stdout **恰一行** JSON（UTF-8，非 ASCII 原样输出），退出码 0：

```json
{"method": "template_fill", "confidence": 0.65, "reasons": ["…", "…"]}
```

| 字段 | 语义 |
|---|---|
| `method` | 三值枚举之一：`editable_pptx` / `template_fill` / `visual_report` |
| `confidence` | 数值 ∈ [0,1]，确定性公式值，两位小数（如 0.9、0.4） |
| `reasons` | 非空字符串数组：逐条写明命中关键词、裁定依据（单类/优先级/兜底）与冲突提示 |

失败语义：`--input` 缺失或文件不存在/不可读 → **退出码 2**，stderr 提示，stdout 无 JSON。
stdout 除该行 JSON 外不得输出任何内容（进度、日志一律走 stderr）。
批量产物 `out/labels.json` 为 JSON 数组，每条
`{"case": "case1", "method": "…", "confidence": 0.95, "reasons": ["…"]}`，
`case` 恰为 case1…case20，无缺失/重复/多余。

## 7. 边界与非目标

边界（明确未定义 / 不保证的行为）：

- 纯子串匹配、不做分词与语义理解：措辞变化导致的漏检/误检是**预期行为**
  （如"公司VI"不连续不命中）；
- 信号词全为中文（"公司VI"含字母）；大小写不敏感仅对字母字符有实际意义；
- 输入编码仅保证 UTF-8（±BOM）；GBK 等其它编码的中文会被错误解码，行为未定义；
- `confidence` 是确定性公式值，不具备统计/概率语义，不保证校准；
- 多行文本合并为单意图处理，不做多意图拆分。

非目标（本技能不做）：

- 不生成 / 渲染任何 PPT、海报或信息图（三类 method 对应路径的执行不在本技能范围）；
- 不做模板资产、品牌 VI 库的管理与检索；
- 不调用 LLM/模型做语义路由——路由层保持确定性、可离线复算。

## 8. 与 oracle / eval 的关系

- **参照实现**：`../oracle/`（其中 `oracle/oracle.py` 为确定性关键词路由的参照脚本，
  `oracle/inputs/` 为黄金集输入，`oracle/out/labels.json` 为参照判定）。
  本 package 的 `inputs/case1-20.txt` 按 `../spec.md` §8 的黄金输入全文逐条创建
  （UTF-8 无 BOM、每文件单行+换行；spec §7.3 规定 §8 为该一致性的唯一权威来源），
  生成脚本仅使用 spec §8 文本，未读取 `../oracle/` 的任何代码文件与 `oracle/out`
  参照产物，本 package 亦未修改 `../oracle/` 与 `../eval/` 的任何文件。
- **评测入口**：`../eval/runner.py`（用法 `python eval/runner.py package/out oracle/out`，
  质量门槛：20 条齐全、schema 合法、reasons 非空、与参照 method 一致率 ≥ 80%）。
- 规格与契约：`../spec.md`（行为规则 R1–R6 与逐条可判定验证）、`../contract.md`
  （冻结的目录布局、命令行契约、产物 schema 与 SKILL.md 必备结构）。
- 三类方法的执行要点详见 `references/methods.md`（路由裁定后的移交参考）。
