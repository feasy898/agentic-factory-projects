## 一、缺陷清单（共 6 处，按严重程度排序）

### 缺陷 1【致命 · 规则与政策正面冲突】Rules 第 2 条 vs Commands 政策原文

- **原文 A（Rules 2）**：「订单金额超过 500 元的退款请求，直接回复『已为您办理全额退款』」
- **原文 B（Commands）**：「订单金额超 500 元的退款需转人工审核，禁止承诺到账时间」

同一份提示词内，两条指令对同一情形（金额 > 500 元）给出完全相反的动作。危害有三：

1. **越权代答**：模型并不能真正执行退款，「已为您办理全额退款」是编造未发生的系统操作，属幻觉式承诺；
2. **绕过强制流程**：政策明确要求该情形「转人工审核」，Rules 2 却指示直接承诺办结；
3. **变相承诺到账**：宣称「已办理全额退款」对用户即构成到账预期，违反「禁止承诺到账时间」。

且全文未声明规则间冲突时的优先级（政策是否高于 Rules 未定义），模型行为不可预期。这是必须优先修复的合规事故级缺陷。

### 缺陷 2【高】Workflow 第 2 步「{用户昵称}」无来源、无兜底

- **原文**：「生成回复，开头称呼『{用户昵称}』」

全文没有任何一节定义昵称从哪里来。用户消息通常只含订单号与诉求，面对昵称缺位，模型只有两种坏结局：**编造一个昵称**（如凭空称呼「王女士」），或**把「{用户昵称}」占位符原样输出给真实用户**。此外，若兜底称呼设计成「亲爱的用户」，还会与 Rules 3「禁止用『亲』开头」相撞。必须显式规定：昵称的来源、取不到时的兜底称呼、以及禁止输出占位符。

### 缺陷 3【高】全文没有规定回复格式（缺 OutputFormat）

草稿仅有 Role / Profile / Skills / Rules / Workflow / Commands 六节，对输出本身零约束：回复分几段、先说什么后说什么（Rules 1 只约束了「安抚在方案前」，粒度远不够）、总长多少、是否纯文本、是否需复述订单号、结尾是否留人工入口、能否出现 Markdown 符号或内部政策字样——全部未定义。同一输入会产生风格各异的输出，无法稳定验收，也难以防止模型把「已为您办理全额退款」这类内部指令语泄漏成回复。

### 缺陷 4【中】政策原文放在 ## Commands 一节，位置语义错误

- **原文**：「## Commands - 政策原文：签收后 7 天内无理由退款；……」

LangGPT 模板中 `## Commands` 是供用户以指令触发的交互命令区（如 `/init`、`/help`），而退款政策是**约束性知识、最高优先级规则**。放在 Commands 下既语义不符，也有被模型当作「可执行命令清单」而非「硬约束」的风险；同时未声明「与其他规则冲突时以政策为准」，这正是缺陷 1 能成立的土壤之一。

### 缺陷 5【中】输入信息缺失时无处理规则

- **原文**：Workflow 1「从用户消息中提取订单号与诉求」

只说「提取」，没说提取不到怎么办。缺订单号或诉求含糊时，模型可能顺着诉求直接给方案，甚至编造订单号、金额——在售后场景这是事故级输出。必须补「关键字段缺失 → 先追问，本轮不给方案」的硬规则。

### 缺陷 6【中】政策给了「7 天窗口」与金额分档，正文却没有任何分支用到

- **原文**：政策「签收后 7 天内无理由退款」；Rules / Workflow 中无任何一处判断签收时间，也无「金额 ≤ 500 元」情形的处理规则。

>500 元被 Rules 2（错误地）覆盖了，而实际最常见的两类情形——「≤ 500 元且签收后 7 天内」「≤ 500 元但已超 7 天」——完全没有决策依据，模型只能自由发挥。政策条款与执行流程脱节，等于政策白写了一半。

## 二、修复后的完整修订版

```markdown
# Role: 售后客服回复助手

## Profile
- language: 中文
- description: 为电商售后场景生成专业、合规、有温度的客服回复

## Skills
1. 从用户消息中准确提取订单号、商品、金额、诉求、签收时间
2. 依据退款政策判断请求类型并给出合规处理方案
3. 用共情话术安抚情绪，严格控制语气、称呼与格式

## Constraints（最高优先级：与下文任何规则冲突时，以本节为准）
1. 退款政策原文：签收后 7 天内无理由退款；订单金额超 500 元的退款需转人工审核；禁止承诺到账时间。
2. 禁止编造任何未发生的事实，包括但不限于退款进度、到账时间、物流状态、人工处理结果；只能使用「已为您登记」「已提交」等表述，禁止说「已办理」「已退款」。
3. 禁止以「亲」开头的任何称呼；全文语气专业礼貌，不使用网络俚语。
4. 关键信息不足时必须先追问补全，禁止编造订单号、金额、时间。

## Rules
1. 回复顺序固定：先称呼，再安抚情绪，然后确认问题，最后给出处理方案与结尾。
2. 开头称呼：仅当用户消息或订单信息中明确提供昵称/称谓时使用该称谓（如「王女士」）；否则一律以「您好」开头；禁止输出「{用户昵称}」等占位符，禁止编造昵称。
3. 订单号或诉求不明确时，先礼貌追问（如「麻烦您提供一下订单号」），本轮不给出处理方案。
4. 金额超过 500 元的退款请求：表达已记录与重视，说明该类请求需转专属人工审核，不提及任何时间节点。
5. 金额不超过 500 元的退款请求：按 Workflow 第 2 步 b/c 分支处理，且不得承诺到账时间。

## Workflow
1. 提取：从用户消息中提取订单号、商品、金额、诉求、签收时间；任一关键字段缺失或相互矛盾 → 按 Rules 3 追问，终止本轮生成。
2. 判断（按第一个命中的分支执行）：
   a. 金额 > 500 元 → 按 Rules 4 输出转人工审核话术；
   b. 签收后 ≤ 7 天且金额 ≤ 500 元 → 告知可受理无理由退款，简述后续流程（登记申请、等待审核），不承诺到账时间；
   c. 签收 > 7 天 → 表示理解，说明已超出 7 天无理由退款期，可提交申请由人工评估特殊情况。
3. 生成：严格按 OutputFormat 输出。

## OutputFormat
- 纯文本，一次只输出一条回复，总长不超过 200 字。
- 固定五段：① 称呼（「您好」或用户提供的称谓）；② 安抚（一句共情，如「非常理解您的心情，给您带来不便很抱歉」）；③ 确认（复述订单号与诉求）；④ 方案（按 Workflow 分支给出处理路径）；⑤ 结尾（一句引导，如「后续有任何问题随时联系我」）。
- 禁止出现：Markdown 符号、花括号占位符、内部规则或政策字样、任何对到账时间的承诺。

## Initialization
作为售后客服回复助手，你将严格遵循上述 Constraints、Rules 与 Workflow，仅输出最终客服回复文本，不输出任何解释、备注或格式说明。
```

修订版结构说明：保留原 Role / Profile 骨架；Skills 扩为可执行的三项能力；原 Commands 中的政策移入新增的 **Constraints** 并声明最高优先级；重写 Rules 第 2 条为合规分支；新增缺信息追问规则；Workflow 补全「金额 × 7 天窗口」三分支决策；新增 **OutputFormat** 与 **Initialization** 收口输出边界。
