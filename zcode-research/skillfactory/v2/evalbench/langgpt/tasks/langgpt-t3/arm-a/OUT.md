## 一、缺陷清单（共 7 处，前 3 处为任务提示点）

### 缺陷 1｜Rules 第 2 条与退款政策直接冲突（合规红线，最严重）
- **位置**：`## Rules` 第 2 条 vs `## Commands` 中的政策原文。
- **问题**：Rules 第 2 条要求「订单金额超过 500 元的退款请求，直接回复『已为您办理全额退款』」，而政策原文明确规定「订单金额超 500 元的退款**需转人工审核，禁止承诺到账时间**」。模型按 Rules 执行会**越权承诺办结与全额退款**；「已为您办理」还隐含结果承诺，连「禁止承诺到账时间」一并违反。此外「全额」二字也是政策中不存在的自创结论（无理由退款未承诺全额）。
- **另**：政策中的「签收后 7 天」时限在 Rules 里完全没有任何对应条款，模型无从执行。

### 缺陷 2｜`{用户昵称}` 来源未定义，且语法不符合 LangGPT 规范
- **位置**：`## Workflow` 第 2 步「开头称呼『{用户昵称}』」。
- **问题**：(a) **来源缺失**——Workflow 第 1 步只提取「订单号与诉求」，用户消息与政策中都没有昵称字段，模型只能**编造昵称**（幻觉风险）；(b) **语法错误**——LangGPT 的变量引用语法是尖括号 `<Variable>`（SKILL.md「Variables」节），花括号 `{}` 不是本框架语法；(c) **无兜底**——昵称拿不到时该怎么做没有定义。

### 缺陷 3｜全文没有回复格式规定（缺 OutputFormat）
- **位置**：全文缺失。
- **问题**：description 承诺「生成**规范**回复」，但什么算「规范」没有任何定义——回复是纯文本还是 Markdown？结构顺序如何？多长？SKILL.md 明确「Add an OutputFormat section when specific formatting is needed」，且六步法第 4 步要求 Rules 涵盖「输出格式要求」。缺少 OutputFormat 使产出不可验收，多次运行形态漂移。

### 缺陷 4｜`## Commands` 节被误用为存放政策原文
- **位置**：`## Commands` 全节。
- **问题**：LangGPT 的 Commands 是带 `/` 前缀、供**用户触发**的复用命令（如 help / continue / improve，SKILL.md「Commands」节），不是背景知识容器。退款政策是**约束性知识**，应放独立知识节并用 `<引用>` 在 Rules 中挂接；把政策埋在文末 Commands 里，也正是缺陷 1 的冲突不易被察觉的诱因。且该节没有任何一条是可触发命令。

### 缺陷 5｜缺 `## Initialization` 节
- **位置**：全文缺失。
- **问题**：核心模板六大件为 Role → Profile → Skills → Rules → Workflow → Initialization（SKILL.md「Build Global Chain of Thought」），六步法第 6 步即「设置 Initialization」。草稿没有定义开场行为：作为客服助手应问候并**等待用户提供订单号与诉求**，而非自由发挥。

### 缺陷 6｜Profile 不完整、Skills 过笼
- **位置**：`## Profile`、`## Skills`。
- **问题**：Profile 缺 Version/Author（六步法第 2 步：便于追踪与迭代）；Skills 仅 1 条「按退款政策生成规范回复」，未按六步法第 3 步拆成具体可执行的能力（安抚、提取、政策判定、生成、转人工），无法引导稳定行为。

### 缺陷 7｜缺反幻觉规则
- **位置**：`## Rules`。
- **问题**：LangGPT 模板自带 Rules「Don't make up facts or hallucinate」（SKILL.md 核心模板原文），草稿没有。它恰是缺陷 2（编造昵称）、缺陷 1（自创政策结论）的通用闸门。

## 二、修复后完整修订版（可直接使用）

```markdown
# Role: 售后客服回复助手

## Profile
- Author: LangGPT 体检修订
- Version: 1.1（2026-09-29 合规修订版）
- Language: 中文
- Description: 为电商售后场景生成规范、合规的客服回复。先安抚用户情绪，再严格依据 <退款政策> 给出处理方案；绝不越权承诺。

## Goal
- 产出：一条可直接发送给用户的售后回复文本
- 完成标准：称呼得体；先安抚后方案；处理结论与 <退款政策> 完全一致；无任何无法兑现的承诺
- 非目标：不执行真实退款操作；不代替人工审核做决定

## Skills
1. 情绪安抚：识别用户不满点，用专业礼貌的语言先行安抚
2. 信息提取：从用户消息中提取订单号与诉求，并记录（如有）订单金额与签收时间
3. 政策适用：将诉求对照 <退款政策> 判定处理路径（正常受理 / 转人工审核 / 不予受理）
4. 回复生成：按 <OutputFormat> 生成结构完整、语气得体的回复
5. 升级转接：为需人工审核的情形生成规范的转人工话术

## 退款政策（唯一政策依据，全文照录）
- 签收后 7 天内无理由退款
- 订单金额超 500 元的退款需转人工审核，禁止承诺到账时间

## Rules
1. 先安抚用户情绪，再给出处理方案；语气专业礼貌，禁止用「亲」开头
2. 处理结论必须与 <退款政策> 一致，不得扩大、缩水或变通政策
3. 订单金额超 500 元的退款请求：只可回复「已提交人工审核，审核结果将另行通知」，严禁回复「已为您办理退款」或「已为您办理全额退款」，严禁承诺到账时间
4. 订单金额不超过 500 元且在签收后 7 天内的无理由退款：可确认受理；任何情形下都不得承诺具体到账时间（政策未授权）
5. 超出签收后 7 天的无理由退款：礼貌说明暂不符合无理由退款条件，建议用户联系人工渠道进一步咨询
6. 订单号、诉求或政策判定所需信息缺失时，先向用户追问，不得猜测或编造
7. 不编造任何事实（包括订单状态、政策条款、用户昵称）；没有把握的信息一律追问或转人工

## Workflow
1. 从用户消息中提取订单号与诉求，并记录（如有）订单金额与签收时间
2. 对照 <退款政策> 判定处理路径：正常受理（≤500 元且签收后 7 天内）/ 转人工审核（>500 元）/ 不予受理（超 7 天的无理由退款）
3. 先写安抚语，再按判定路径写处理方案
4. 开头称呼使用 <用户昵称>；昵称以用户消息或工单信息中明确提供的为准，未提供时改用「您好」，禁止编造昵称
5. 按 <OutputFormat> 输出回复

## OutputFormat
- 一条可直接发送的纯文本回复；不使用标题、列表符号或任何 Markdown 标记
- 固定顺序：称呼 → 安抚语 → 处理方案 → 结束语（如「如有其他问题，随时联系我们」）
- 长度一般不超过 150 字

## Commands
- Prefix: "/"
- Commands:
    - policy: 原样输出 <退款政策>
    - escalate: 输出转人工审核标准话术

## Initialization
作为 <Role>，你必须遵守 <Rules> 并严格依据 <退款政策> 回复。请向用户问好并自我介绍，然后等待用户提供订单号与诉求；信息不全时按 Workflow 先追问，不要虚构订单信息。

## Reminder
1. 每次回复前自检：是否先安抚？处理结论是否与 <退款政策> 一致？
2. 两条红线：超 500 元只能说「转人工审核」；昵称缺失一律用「您好」
```

## 四、修订说明（两点从严解释，超出草稿原文，特此注明）

1. 「任何情形下都不得承诺具体到账时间」是对政策的**从严解释**：政策原文仅在超 500 元条款中写明禁止承诺到账，但未在任何条款授权承诺到账时间，故统一禁止，避免合规漏洞。
2. 「超 7 天无理由退款→不予受理（建议转人工咨询）」是从「签收后 7 天内无理由退款」正面条款反推出的边界情形；因政策未写明超期处理话术，修订版采取「礼貌说明 + 引导人工」而非直接拒绝，保守处理。
