# 「3.9 需求评审会」排会命令清单（lark-cli · Asia/Shanghai）

> 需求：2026-10-12（周一）～ 2026-10-16（周五）工作时间内，为 4 位参会人（`ou_wang001,ou_li002,ou_zhao003,ou_sun004`）安排 60 分钟会议，配一间可容纳 6 人的会议室，议程三项写入日程描述。
>
> 本清单按序执行即可完成排会；所有 `{占位符}` 均注明来源，未编造任何命令或 flag。

## 0. 验证情况与环境说明（如实陈述）

- 本机已装 lark-cli `1.0.97`。清单中 Step 1/2/3 的命令均已在本机用 `--dry-run`（只打印请求、不执行）逐条验证：flag 全部被接受，请求推进到认证检查层（返回 `config/not_configured`）。对照组：故意传错误 flag 时返回 `validation/invalid_argument`，证明上述命令的参数写法确已通过解析。
- 本机当前未绑定租户凭据（`lark-cli whoami` → `not_configured`），因此**未实际执行任何真实 API 调用**；请在已认证的环境按序执行。
- 命令全部写成单行，cmd / PowerShell / bash 通用（不使用续行符）。
- 时间一律传 **ISO 8601 带偏移**字符串（`2026-10-12T09:00:00+08:00`），换算规则与坑见第 2 节。

## 1. 流程总览（顺序不可调换）

```
+suggestion（定共同空闲时段）→ 用户确认时段 → +room-find（在确定时间块内找 ≥6 人会议室）
→ 用户确认「时段+会议室」组合 → +create（4 位参会人 + 会议室一次性带上）→ 依据返回直接反馈
```

## 2. 时间换算方式与坑（北京时间 → 时间戳）

**首选方式：不换算。** 三个命令的时间参数都直接收 ISO 8601 带偏移字符串，把北京时间原样写成 `2026-10-12T09:00:00+08:00` 即可，全程无需手工算时间戳。依据：`+create` 文档明确 `--start/--end` "**必须带时区偏移**……不带偏移会按进程时区解析致偏移"；`+suggestion` 文档的时间格式表首行即 `ISO 8601：2026-03-19T08:40:29+08:00（精确包含日期、时间及带冒号的时区偏移）`。注意 `+create` **没有** `--timezone` 参数（`+create --help` 中无此 flag），时区只能靠 `+08:00` 偏移表达；`+suggestion`/`+room-find` 有 `--timezone`，已显式传 `Asia/Shanghai`。

**确需 Unix 时间戳时**（仅当改走完整 API：Lark 日历 v4 完整命令的时间参数是 **Unix 秒字符串**，非 ISO 8601）：必须调用外部工具换算并显式指定时区，官方 skill 为强制要求——"涉及日期（时间）字符串与时间戳的相互转换时，务必调用系统命令或脚本代码等外部工具进行处理……换算**禁止依赖容器默认时区**（常为 UTC，会导致 8 小时偏移）"。本机已实测验证：

```powershell
[DateTimeOffset]::Parse('2026-10-12T09:00:00+08:00').ToUnixTimeSeconds()
# 实测输出：1791766800（= 北京时间 2026-10-12 09:00:00，本机验证通过）
```

```bash
python -c "from datetime import datetime; print(int(datetime.fromisoformat('2026-10-12T09:00:00+08:00').timestamp()))"
```

**坑清单：**

1. **默认时区坑（最致命）**：不带 `+08:00` 的时间会按进程/容器时区解析，容器常为 UTC → 整体偏移 8 小时。所有 `--start/--end` 必须显式带 `+08:00`。
2. **单位坑**：Lark 日历 v4 时间戳为**秒级**，不要传毫秒。
3. **日期简写坑**：只传日期时 `--start` 取 `00:00:00`、`--end` 取当日 `23:59:59`——适合查询范围，不能用来表达创建日程的精确时刻。
4. **格式坑**：ISO 8601 偏移须**带冒号**（`+08:00`），不能写 `+0800`。
5. 中国无夏令时，Asia/Shanghai 全年固定 +08:00；偏移量不变，但**必须写**，不能省。

## 3. 命令清单（按序执行）

### Step 1 · 用时间建议命令定「共同有空」的候选时段 —— `+suggestion`（read）

```bash
lark-cli calendar +suggestion --as user --start "2026-10-12T09:00:00+08:00" --end "2026-10-16T18:00:00+08:00" --attendee-ids "ou_wang001,ou_li002,ou_zhao003,ou_sun004" --duration-minutes 60 --timezone "Asia/Shanghai" --format json
```

**理由（一句）**：在 10-12～10-16 的范围里为 4 位参会人找 60 分钟的共同可用时段，必须用智能时间建议而不是只查忙闲——官方文档明确 `+freebusy` "只回答'哪些区间空着'，**不判断该区间是否适合排会**"，而 `+suggestion` "综合**工作时间段、忙碌时间段、休息时间段**来推荐"，天然把「工作时间内」这一约束落进推荐逻辑，无需手工在忙闲结果上再叠加工作时间过滤。

**为什么仅查忙闲不够（展开）**：`+freebusy common_free` 的交集里会包含深夜、午休等"日历空着但不该开会"的区间，选段时还得人工判断适不适合；`+suggestion` 直接产出"适合排会"的候选块并附推荐理由（含冲突提示），一步到位。另按官方工作流：**选定时段后无需再调 `+freebusy` 复核**。

**产出**：返回 JSON 中的推荐时间块，记为 `{候选时段1}`、`{候选时段2}`…（**来源：Step 1 返回**）。每个块形如 `2026-10-13T14:00:00+08:00~2026-10-13T15:00:00+08:00`。
**硬性动作**：把候选时段结构化展示给用户并等待选择（官方 skill 将"未确认不得创建"列为 BLOCKING REQUIREMENT）；若某候选含忙闲冲突，必须如实告知，不得说成完全空闲。

### Step 2 · 在**确定的**时间块内找 ≥6 人会议室 —— `+room-find`（read）

```bash
lark-cli calendar +room-find --as user --slot "{候选时段1起}~{候选时段1止}" --slot "{候选时段2起}~{候选时段2止}" --attendee-ids "ou_wang001,ou_li002,ou_zhao003,ou_sun004" --min-capacity 6 --timezone "Asia/Shanghai" --format json
```

`--slot` 对 Step 1 用户确认保留的每个候选块重复传入一次（格式 `开始~结束`，例：`--slot "2026-10-13T14:00:00+08:00~2026-10-13T15:00:00+08:00"`；多个 `--slot` 由 CLI 并发查询后聚合输出）。

**理由（一句）**：会议室可用性是按具体时间块判定的，把候选时段一次性交给 `+room-find` 批量查询、并用 `--min-capacity 6` 落实"容纳 6 人"的硬性要求，才能拿到每个时段下的可用房间清单。

**为什么这个顺序不能反（先定时段、再查会议室）**：

1. **接口约束**：官方文档明文 "`+room-find` 的时间输入必须是**确定时间块**，不是时间区间搜索"、`--slot` 为必填；时间未定时调用属于误用，必须先 `+suggestion` 拿到时间块——"即使用户最初只说'查会议室'且未带时间，也必须强制走 suggestion → room-find 路径"。
2. **业务模型**：会议室是日程的一种**资源型参与人（resource attendee）**，"不能脱离日程单独预定"——没有确定时间，"订会议室"这个动作本身不成立。
3. **实际后果**：先选房后定时间，则房间在最终时段是否可用完全未知，时间一变可用性全变、只能推倒重查；先定时间块再查房，一次查询即返回该块的全部可用房间，用户一轮即可同时拍板"时段 + 房间"。

**产出**：`{room_id}`（`omm_` 前缀，创建日程时用）、`room_name`、`capacity`（**来源：Step 2 返回 JSON**；向用户展示时 `room_name` 必须逐字透传）。
**硬性动作**：按官方要求的"时间块 → 可用会议室"分行结构化展示，等用户确认组合后再创建（BLOCKING REQUIREMENT）。

### Step 3 · 创建日程：4 位参会人与会议室一并带上 —— `+create`（write）

```bash
lark-cli calendar +create --as user --summary "3.9 需求评审会" --start "{确认时段起}" --end "{确认时段止}" --attendee-ids "ou_wang001,ou_li002,ou_zhao003,ou_sun004,{room_id}" --description "会议议程：1) 3.9 需求范围确认；2) 接口依赖评审；3) 排期确认。"
```

**理由（一句）**：`+create` 的 `--attendee-ids` 支持用户（`ou_`）、群组（`oc_`）、**会议室（`omm_`）三种前缀混传**，把 Step 2 选定的 `{room_id}` 直接拼进参会人列表，一条命令即完成"4 位参会人 + 会议室"的一体化创建，无需第二步补挂房间。

- `{确认时段起/止}`：**来源：Step 1 确认、Step 2 已验证有房的时段**，必须带 `+08:00`（见第 2 节）；时长 60 分钟。
- `{room_id}`：**来源：Step 2 返回并经用户选定的会议室**。
- 议程已按任务要求写入 `--description`；若想让议程在日程里渲染为 Markdown 有序列表，可改用文件形式（`--description` 支持 `@file`）：先把三行议程存为 `agenda.md`，再传 `--description @agenda.md`。
- 标题 `--summary` 按官方要求不含时间/地点/人物，故只写"3.9 需求评审会"。
- 风险级别为 `write`（非 `high-risk-write`），按本 CLI 规则**不需要** `--yes`。命令默认自动附加飞书视频会议、会前 5 分钟提醒、忙碌状态，无需额外参数。
- 异常分支（仅当返回提示会议室需审批时）：`+create` 不暴露 `approval_reason`，按官方文档应先创建日程（不含会议室），再用 `lark-cli calendar event.attendees create --as user` 添加会议室并传 `approval_reason`。

### Step 4 · 创建成功后直接反馈结果（不做二次确认查询）

**动作**：依据 Step 3 返回 JSON（`event_id`、`start/end`、参会人与会议室回显）直接向用户反馈：会议时间（北京时间）、会议室名称（`room_name` 原值）、4 位参会人、议程已写入描述。
**依据**：官方工作流明文——"创建、更新、删除、RSVP 等写操作完成后，直接基于命令返回结果反馈用户；不要为了'确认是否生效'主动发起二次查询"。
（仅当用户后续还要分享该日程时，才执行 `lark-cli calendar events share_info --calendar-id primary --event-id {event_id}` 获取日程分享链接；本任务不需要。）

## 4. 占位符来源汇总

| 占位符 | 来源 |
|---|---|
| `{候选时段N 起/止}` | Step 1 `+suggestion` 返回的推荐时间块（经用户选择保留） |
| `{room_id}` | Step 2 `+room-find` 返回的 `room_id`（`omm_` 前缀，经用户选定） |
| `{确认时段起/止}` | Step 1 确认且 Step 2 验证有房的最终时段 |
| `{event_id}` | Step 3 `+create` 返回的日程 ID（仅分享时使用） |

## 5. 补充说明

- **身份**：全部命令 `--as user`，日程落在当前登录用户的主日历（组织者=登录用户）；4 位参会人 open_id 为任务给定，无需查询。若组织者本人也需计入忙闲，把其 open_id 追加进各命令的 `--attendee-ids`（可用 `lark-cli whoami` 查当前身份）。
- **bot 剔除**：不要把任何 bot open_id 混入 `--attendee-ids`（文档明确 bot 无忙闲语义、不占席位，会干扰推荐结果）；本清单 4 位均为 `ou_` 用户，已符合。
- **无固定会议室/城市偏好**：任务未指定楼宇/楼层/城市，故不传 `--building/--floor/--city/--room-name`，只按容量过滤；`+room-find` 在带筛选条件时也可能返回邻近楼层候选，属文档说明的正常行为，不视为异常。
